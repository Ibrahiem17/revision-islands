Schema design is genuinely the highest-leverage decision in a database's life. Get it wrong and every feature built on top inherits the pain — a bad schema shows up months later as slow queries, duplicated data, and features that are unreasonably hard to add. This tab is "start from a blank page" basic: no assumed knowledge, just the actual step-by-step process, in order.
🪜 The Actual Process — 6 Steps, In Order
1
Find the entitiesthe "nouns" of your app
Read your app's requirements and circle every noun that needs to be remembered: User, Post, Comment, Order, Product. Each one usually becomes its own table. If a "thing" has its own identity and its own data, it's an entity.
2
List the attributeswhat does each entity need?
For each entity, list the facts you actually need to store about it. A User needs an email and a password hash. A Post needs a title, body, and a creation date. Don't add a column "just in case" — every unused column is a maintenance cost forever.
3
Work out the relationships1:1, 1:N, N:N
For every pair of entities, ask "how many of A can relate to how many of B?" A User has many Posts (1:N). A Post can have many Tags, and a Tag can belong to many Posts (N:N) — this last shape always needs a third table. See the concept cards below.
4
Pick a primary keyfor every single table
Default to a surrogate key — an auto-incrementing integer or a UUID that means nothing on its own — instead of a "natural" key like email. Natural keys change (people change emails); surrogate keys never do.
id BIGSERIAL PRIMARY KEY
5
Add foreign keyswire the relationships together
For every 1:N relationship, put a foreign key column on the "many" side, pointing back at the "one" side's primary key. A posts table gets a user_id column referencing users.id.
user_id BIGINT REFERENCES users(id)
6
Normalize, then selectively denormalizesee the next tab
Organize your tables so each fact lives in exactly one place (normalization). Only after that's working and you've measured a real performance problem do you deliberately break that rule in specific spots (denormalization) — never the other way around.
🧩 Concept: Relationship Types
1️⃣One-to-One (1:1)Rare, but real
Each row in table A matches exactly one row in table B, and vice versa. Example: a users table and a user_profiles table — every user has exactly one profile. Usually you'd just merge these into one table unless one side is huge/rarely-read (e.g. splitting off a big "bio" text field so the hot users table stays small).
users.id = user_profiles.user_idFK is also UNIQUE
🔢One-to-Many (1:N)The most common shape
One row in table A can match many rows in table B, but each row in B points back to only one row in A. One user writes many posts; each post has exactly one author. The foreign key always lives on the "many" side.
posts.user_id → users.idFK on the "many" table
🕸️Many-to-Many (N:N)Needs a junction table
Many rows in A can relate to many rows in B — a post can have many tags, and a tag can be on many posts. Neither table can hold a single foreign key for this, so you create a third table (a junction / join table) with just two foreign keys, one to each side.
post_tags(post_id, tag_id)composite PK on both columns
🩺 Worked Example — Designing a Tiny Blog, Start to Finish
The requirement: "Users can write posts. Other users can comment on posts. Posts can have multiple tags." That's the entire spec — watch how directly it turns into tables.
-- Step 1 & 2: entity "users", with the attributes it actually needs CREATE TABLE users ( id BIGSERIAL PRIMARY KEY, email VARCHAR(255) UNIQUE NOT NULL, password_hash VARCHAR(255) NOT NULL, created_at TIMESTAMP NOT NULL DEFAULT now() ); -- Step 3 & 5: "posts" — one user has many posts (1:N), so the FK lives here CREATE TABLE posts ( id BIGSERIAL PRIMARY KEY, user_id BIGINT NOT NULL REFERENCES users(id), title VARCHAR(255) NOT NULL, body TEXT NOT NULL, created_at TIMESTAMP NOT NULL DEFAULT now() ); -- "comments" — one post has many comments, one user writes many comments CREATE TABLE comments ( id BIGSERIAL PRIMARY KEY, post_id BIGINT NOT NULL REFERENCES posts(id), user_id BIGINT NOT NULL REFERENCES users(id), body TEXT NOT NULL, created_at TIMESTAMP NOT NULL DEFAULT now() ); -- "tags" — just a name, nothing else needed CREATE TABLE tags ( id BIGSERIAL PRIMARY KEY, name VARCHAR(50) UNIQUE NOT NULL ); -- posts <-> tags is many-to-many, so it gets its own junction table CREATE TABLE post_tags ( post_id BIGINT NOT NULL REFERENCES posts(id), tag_id BIGINT NOT NULL REFERENCES tags(id), PRIMARY KEY (post_id, tag_id) );

🚫 Common Mistakes
😰 Beginner schema
Storing tags as tags: "sql, career, backend" in one text column on the posts table. Storing a user's email as the primary key. No foreign keys at all — just matching IDs "by convention" with nothing enforcing it. One giant table with 40 columns because "joining is slow."
✅ What actually holds up
A real tags table + junction table, so you can query, count, and rename tags safely. A surrogate id primary key, with email as a separate UNIQUE column. Real FOREIGN KEY constraints, so the database itself refuses bad data. Multiple focused tables, joined when needed — modern databases join fast when indexes are in place (see the Indexing tab).
🎯 Interview Q&A
S1Walk me through how you'd design a schema for a new feature, from scratch.▼
ANSWER
I follow the same six steps every time: find the entities (the nouns in the requirement), list each entity's real attributes, work out how entities relate to each other (1:1, 1:N, N:N), give every table a surrogate primary key, wire up foreign keys for every relationship, then normalize the result. I don't add speculative columns or tables — only what the actual requirement needs right now.

entities → attributes → relationships → keys → FKs → normalize
S2Why use a surrogate key (auto-increment id) instead of a natural key like email?▼
ANSWER
Natural keys can change — a user might change their email, but their identity in the system shouldn't have to change with it. If email is the primary key, every table that references the user now has to update too. A surrogate id never changes, is smaller and faster to index, and keeps identity separate from data that's allowed to be edited.

identity ≠ data that can changesmaller, faster FK joins
S3How do you actually model a many-to-many relationship?▼
ANSWER
Neither side can hold a single foreign key for a many-to-many relationship, so you create a third "junction" table containing just two foreign keys, one pointing to each side. The junction table's primary key is usually the combination of both foreign keys (a composite key), which also naturally prevents the same pair being linked twice.

post_tags(post_id, tag_id)
🏗️
Entities → attributes → relationships → keys → foreign keys → normalize
Every schema, no matter how big, is built from exactly these six mechanical steps repeated table by table. Once you can do this on paper for a tiny blog, you can do it for anything.

⚡ Quick Recap — The Normal Forms Cheat Table
FormRuleFixes
1NFEvery column holds one atomic value — no comma-separated lists in a cell."Repeating groups" like tags: "sql,career" in one column.
2NF1NF, plus every non-key column depends on the whole primary key (only matters with composite keys).A column that really only depends on half of a composite key.

🪜 When Should You Actually Denormalize?
1
Start fully normalizedalways the default
Build the schema correctly first. Normalized data is easier to reason about, and bugs from stale duplicated data are some of the hardest to track down.
2
Measure a real problemnot a guess
Denormalizing is a trade-off, not a free win. Only reach for it once you've actually measured a slow query — e.g. a product page that needs 4 JOINs and 200ms just to show an order count.
3
Denormalize the smallest possible piecesurgical, not sweeping
Duplicate one column, add one summary table, or precompute one counter — whatever removes the specific slow JOIN. Don't flatten the whole schema "just in case."
4
Own the write-side costsomeone has to keep it in sync
Every duplicated value now has to be updated in two places whenever the original changes — in application code, a trigger, or a scheduled job. Decide explicitly who's responsible before you ship it.
🛠️ Three Real Denormalization Techniques
🔢Denormalized Counter Columnsavoid COUNT() on every read
Instead of running SELECT COUNT(*) FROM comments WHERE post_id = 5 on every single page view, store a comment_count column directly on the posts row, and increment it whenever a comment is inserted (in the same transaction, or via a trigger).
-- when a comment is added, in the same transaction: UPDATE posts SET comment_count = comment_count + 1 WHERE id = 5;
📋Duplicated Columnsavoid a JOIN for one common field
If every single query listing a post also needs the author's display name, store author_name directly on the posts row too — even though it technically belongs on users. Update it (or accept it going stale, if that's acceptable) when the user changes their name.
📊Summary / Materialized Tablesprecompute the expensive aggregate
For a dashboard showing "sales per day," don't re-aggregate millions of orders on every page load — maintain a daily_sales_summary table (or a real materialized view) that's updated on a schedule or via triggers, and query that instead.
CREATE MATERIALIZED VIEW daily_sales AS SELECT order_date, SUM(total) AS revenue FROM orders GROUP BY order_date; -- refreshed on a schedule: REFRESH MATERIALIZED VIEW daily_sales;

🔍 An index in one sentence
📖
A book's index page
Jump straight to it, instead of reading every page
→
🌳
Stored as a B-tree
Sorted, so lookups skip most of the data
→
⚖️
Faster reads, slower writes
Every index is upkeep, not free
Without an index, SELECT * FROM users WHERE email = 'x@y.com' means the database checks every single row, one at a time — a "full table scan." On a 10-row table that's instant. On a 50-million-row table, that's the difference between 2ms and 8 seconds. An index is a separate, sorted structure the database maintains alongside your table specifically so it doesn't have to do that.
🌳 What an Index Actually Looks Like — the B-Tree
Verified against real indexing documentation (use-the-index-luke.com): almost every database index (PostgreSQL, MySQL/InnoDB, SQL Server, Oracle) is a B-tree — a balanced, sorted tree structure. Think of it like the sorted tabs in a phone book: you don't read every name, you jump to the "M" section, then narrow down from there.
[ M ] ← root node: one quick comparison / \ [ D | H ] [ R | W ] ← branch nodes: narrow further / | \ / | \ [A,B][E,F][I,K] [N,P][S,T][X,Y,Z] ← leaf nodes: hold the actual sorted values + a pointer to the real row
Finding "S" takes 3 comparisons (M → R/W → S), not 26. On a table with a million rows, a B-tree lookup takes roughly ~20 comparisons instead of up to a million — that's what "logarithmic" means in practice.
🪜 Creating Indexes — the Actual Syntax, Step by Step
1
A basic single-column indexthe default move
Index any column you filter on (WHERE) or sort by (ORDER BY) regularly.
CREATE INDEX idx_users_email ON users(email);
2
A unique indexenforces + speeds up
Guarantees no two rows share that value AND speeds up lookups on it — two benefits from one line.
CREATE UNIQUE INDEX idx_users_email_unique ON users(email);
3
A composite (multi-column) indexcolumn order matters!
Covers queries filtering on both columns together, or just the first column alone — this is the "leftmost prefix" rule, see below.
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at);
4
A partial indexindex only the rows you'll query
If 95% of orders are "completed" and you only ever query the "pending" ones quickly, only index those — smaller, faster, cheaper to maintain.
CREATE INDEX idx_orders_pending ON orders(created_at) WHERE status = 'pending';
5
A covering indexskip the table entirely
INCLUDE extra columns your query needs to return, so the database can answer straight from the index — an "index-only scan" — without ever touching the table.
CREATE INDEX idx_orders_covering ON orders(user_id) INCLUDE (status, total);
📐 The Leftmost Prefix Rule — Column Order Actually Matters
An index on (user_id, created_at) speeds up queries filtering on user_id alone, or user_id AND created_at together — because the index is physically sorted by user_id first, then created_at within each user_id. It does NOT help a query that filters on created_at alone, because that column isn't the leftmost/first one in the sort order.
✅ Uses the index
WHERE user_id = 5
WHERE user_id = 5 AND created_at > '2026-01-01'
❌ Skips the index entirely
WHERE created_at > '2026-01-01' — created_at isn't leftmost, so this index is useless for this query.
🔬 Reading EXPLAIN Output — What The Database Is Actually Doing
Verified against the real PostgreSQL documentation: the exact output format below is how EXPLAIN genuinely prints — this isn't simplified for teaching, it's the real thing.
-- Without an index on email: EXPLAIN SELECT * FROM users WHERE email = 'x@y.com';
Seq Scan on users (cost=0.00..8945.00 rows=1 width=244) Filter: (email = 'x@y.com'::text)
"Seq Scan" = sequential scan = it read every row and checked each one. Cost 8945.00 is high — that's the full table.
-- After: CREATE INDEX idx_users_email ON users(email); EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'x@y.com';
Index Scan using idx_users_email on users (cost=0.29..8.30 rows=1 width=244) (actual time=0.030..0.031 rows=1 loops=1) Index Cond: (email = 'x@y.com'::text)
"Index Scan" — it used the B-tree, jumped almost straight to the row. Cost dropped from 8945.00 to 8.30. EXPLAIN ANALYZE (vs. plain EXPLAIN) actually runs the query and shows actual time in real milliseconds — 0.031ms here — alongside the planner's estimated cost.
⚠️ When Indexes Actually Hurt
🐌Every Index Slows Down Writesthere's no free lunch
Every INSERT, UPDATE, or DELETE has to update every index on that table too, not just the table itself. A table with 8 indexes means every write does up to 9x the work. Index only the columns you actually query by — not every column "just in case."
reads get fasterwrites get slowermore disk space used
🎯 Interview Q&A
I1A query is slow. Walk me through how you'd actually speed it up.▼
ANSWER
First, run EXPLAIN ANALYZE on it — never guess. If it shows a Seq Scan on a large table with a selective WHERE clause, that's the signal: add an index on the column(s) in that WHERE clause. Re-run EXPLAIN ANALYZE to confirm it switched to an Index Scan and the cost/actual time dropped. If it's a composite condition, make sure the index column order matches the leftmost-prefix rule.

EXPLAIN ANALYZE first, alwaysmeasure before and after
I2Why not just index every column to be safe?▼
ANSWER
Because every index has a write cost — it has to be updated on every INSERT/UPDATE/DELETE — plus disk space. Over-indexing can make an app with heavy writes (like an orders table) noticeably slower without any read benefit, since most of those indexes are never actually used by a query.

index what you query, not everything
I3What's a "covering index" and why would you use one?▼
ANSWER
A covering index includes every column a specific query needs, either in the index key itself or via an INCLUDE clause — so the database can answer the query straight from the index without ever reading the actual table row. This is called an "index-only scan" and is the fastest possible read.

index-only scanno table lookup needed
🔍
B-tree → CREATE INDEX → EXPLAIN ANALYZE → confirm it's actually used
Never add an index on a hunch, and never leave one you can't prove is used. EXPLAIN ANALYZE before and after is the entire discipline.
✂️ Sharding in one sentence
🗄️
One filing cabinet got too full
So you buy more cabinets
→
📏

Each cabinet holds a defined slice
→
🧭
You must know which cabinet
Before you can find anything
A single database server has hard physical limits — CPU, RAM, disk, and connection count. Once you outgrow one machine, you have two options: get a bigger machine (vertical scaling — eventually hits a ceiling and gets absurdly expensive), or split your data across multiple machines — that's sharding. This tab is specifically about how it's actually done in practice, not just the theory.
🪜 The Four Real Sharding Strategies
1
Range-based shardingsplit by value range
Users A–M go to shard 1, N–Z go to shard 2. Simple to reason about and great for range queries, but easy to get an uneven ("hot") shard if data isn't evenly distributed — e.g. way more users with names starting S-Z.
user_id 1–1,000,000 → shard_1
2
Hash-based shardingthe most common default
Run the shard key through a hash function, then mod by the number of shards. Spreads data very evenly (no hot spots), but range queries ("give me all orders from March") now have to hit every shard, since consecutive values land on unrelated shards.
shard = hash(user_id) % 4
3
Directory-based (lookup) shardinga map you control
A separate lookup table/service says "user 8821 lives on shard 3." Most flexible — you can move individual users between shards without a formula change — but that lookup service is now a critical piece of infrastructure that must stay fast and available.
4
Geo-based shardingshard by location
EU users' data lives on EU servers, US users' data on US servers. Common for latency (serve users from a nearby region) and legal reasons (data residency laws like GDPR).
🧭 How It's Actually Implemented — Real Tools, Not Just Theory
ApproachHow it worksReal examples
Application-levelYour own app code computes the shard and connects to the right database directly. Full control, but you build and maintain the routing logic yourself.Custom sharding logic in a service layer
Proxy-levelA middleware layer sits between your app and many database instances, routing queries automatically. Your app mostly doesn't know sharding exists.Vitess (MySQL), Citus (PostgreSQL)

🩺 Worked Example — Sharding a Users Table by ID
// A tiny app-level shard router — this is genuinely close to how it's done const SHARD_COUNT = 4; const SHARD_HOSTS = ['db-shard-0', 'db-shard-1', 'db-shard-2', 'db-shard-3']; function getShardFor(userId) { const shardIndex = hash(userId) % SHARD_COUNT; return SHARD_HOSTS[shardIndex]; } // looking up a user now means: find the shard first, THEN query it const shard = getShardFor(8821); const user = await db.connect(shard).query('SELECT * FROM users WHERE id = ?', [8821]);
⚠️ The Hard Parts — What Actually Makes Sharding Difficult
🔀Cross-Shard Joins Are Hard (or Impossible)the #1 real-world pain point
If orders is sharded by user_id but you need "top 10 products across all users," that data is scattered across every shard — no single SQL JOIN can do that anymore. You either query every shard and merge results in application code (a "scatter-gather" query), or maintain a separate denormalized reporting store just for this.
🔥Hot Shards from a Bad Shard Keychoose the key carefully
Sharding by signup_date means today's shard gets 100% of new-signup traffic while old shards sit idle — a "hot" shard. A good shard key spreads both data AND traffic evenly; user_id (hashed) is usually safer than a time-based value.
📦Resharding — Adding Shards Laterconsistent hashing solves this
Plain hash(id) % 4 breaks catastrophically the moment you go from 4 shards to 5 — almost every key now maps somewhere new, meaning almost all data has to move. Consistent hashing is the real-world fix: it's designed so adding one shard only reshuffles roughly 1/N of the keys, not nearly all of them.
🎯 Interview Q&A
SH1How would you choose a shard key for a multi-tenant SaaS product?▼
ANSWER
tenant_id (the customer/company ID) is usually the right choice — almost every query in a multi-tenant app is already scoped to one tenant, so that tenant's data lands entirely on one shard, meaning most queries never need to cross shards at all. I'd avoid a shard key like created_at since it concentrates all new traffic on one shard.

shard key = your most common WHERE clause
SH2What actually happens when one shard runs out of space, or gets too hot?▼
ANSWER
You need to either split that shard into two, or rebalance data across existing shards — both mean moving a lot of live data without downtime, which is genuinely one of the hardest operational tasks in distributed systems. Consistent hashing minimizes how much data has to move; some systems (like Vitess) have built-in tooling specifically for live resharding.

consistent hashing minimizes data movement
✂️
Pick a shard key that matches your real query pattern, hash it, and use consistent hashing
Sharding is a last resort, not a first move — reach for indexing (this tab's neighbor) and read replicas first. Only shard once a single, well-indexed machine genuinely can't keep up.
🧩 Partitioning in one sentence

Queries touch fewer drawers
"Partition pruning" does the work
Partitioning and sharding are constantly confused, and the difference is genuinely simple once said out loud: partitioning splits one huge table into smaller pieces on the SAME server; sharding splits data across MULTIPLE servers. Partitioning is about making one giant table manageable — not about scaling beyond one machine.
⚖️ Partitioning vs Sharding — Side by Side
FactorPartitioningSharding
ServersOne server, stillMultiple servers
SolvesA single table that's become huge/unmanageableA whole database that's outgrown one machine's capacity
ComplexityLower — the database engine handles most of itHigher — routing, cross-shard queries, resharding
Can combine?Yes — each individual shard can itself be partitioned internally. They're not mutually exclusive.
🪜 The Three Partition Types — Real Syntax
1
Range Partitioningmost common — by date
Split by a range of values — almost always a date. A logs or orders table becomes one partition per month or year, so queries filtering by date only ever touch the relevant partition.
2
List Partitioningby an explicit set of values
Split by a fixed, known list of values — e.g. one partition per country code, or per subscription tier.
3
Hash Partitioningfor even distribution
Same idea as hash sharding, but within one server — used when there's no natural range/list to split on and you just want rows spread evenly across partitions.
-- Range partitioning a large "orders" table by date, real PostgreSQL syntax CREATE TABLE orders ( id BIGSERIAL, user_id BIGINT NOT NULL, total NUMERIC(10,2), created_at TIMESTAMP NOT NULL ) PARTITION BY RANGE (created_at); -- each partition is its own real table underneath CREATE TABLE orders_2025 PARTITION OF orders FOR VALUES FROM ('2025-01-01') TO ('2026-01-01'); CREATE TABLE orders_2026 PARTITION OF orders FOR VALUES FROM ('2026-01-01') TO ('2027-01-01'); -- this query only ever touches the orders_2026 partition — "partition pruning" SELECT * FROM orders WHERE created_at >= '2026-06-01';
CREATE TABLE CREATE TABLE CREATE TABLE Query returned successfully, only scanned partition: orders_2026
✅ Why Bother — Two Real Wins
🎯Partition Pruningskip whole chunks of data instantly
When a query filters on the partition key, the database doesn't even look at the other partitions — it knows they can't possibly contain matching rows. A query for June 2026 orders never touches 2025's data at all, even without an index.
🗑️Instant, Cheap Deletesdrop a partition instead of DELETE
Need to purge data older than 2 years for compliance? DROP TABLE orders_2023; is nearly instant. Compare that to DELETE FROM orders WHERE created_at < '2024-01-01' on a huge table — that has to scan and delete millions of rows one at a time, generating a massive amount of transaction log along the way.
🎯 Interview Q&A
P1What's the actual difference between partitioning and sharding?▼
ANSWER
Partitioning splits one large table into smaller physical pieces on the same server — it's a way of organizing a single database. Sharding splits an entire dataset across multiple separate servers — it's a way of scaling beyond one machine's capacity. They solve different problems and can be combined: each shard can internally be partitioned too.

partitioning = one serversharding = many servers
P2When would you reach for partitioning?▼
ANSWER
When one table has grown so large that queries and maintenance (backups, index rebuilds) are getting slow, but the server itself still has capacity to spare. It's especially good for time-series data where old data is rarely queried and eventually needs to be archived or purged in bulk.

one huge table, not a whole-server capacity problem
🧩
Same server, smaller physical chunks, queries that skip what they don't need
Partitioning is usually the easier, lower-risk win to try before reaching for full sharding — it needs no new servers and no cross-shard query logic.
🍪 Sessions & cookies in one sentence
🤷
HTTP has amnesia
Every request forgets the last one
→
🎟️
Cookie = the claim ticket

Session = what's on file
The server's memory of you
HTTP is stateless — like a cashier with total amnesia who forgets you the second your transaction ends. Every single request is treated as if it's from a total stranger, even the one you sent one second ago. Cookies and sessions are the mechanism the entire web uses to fake "the server remembers me" on top of a protocol that fundamentally doesn't.
🍪 What a Cookie Actually Is — the Real HTTP Header
Verified against the real MDN HTTP documentation: the header below is the literal, real syntax a server sends — not simplified.
Set-Cookie: session_id=a3f9c1e8b2d4; Domain=example.com; Path=/; Max-Age=3600; Secure; HttpOnly; SameSite=Lax
AttributeWhat it actually does
Domain / PathWhich site and which URL path the browser is allowed to send this cookie back to.
Max-Age / ExpiresHow long the cookie survives. No value at all = a "session cookie," deleted when the browser closes.
SecureOnly ever sent over HTTPS, never plain HTTP — stops it being sniffed on an insecure connection.
HttpOnlyJavaScript on the page cannot read this cookie at all (document.cookie won't show it). The single biggest defense against session-stealing via XSS.
SameSiteStrict/Lax/None — controls whether the cookie is sent on requests coming from a different site, which is the core defense against CSRF attacks.
🪜 How Login Actually Works, Step by Step
1
You submit your username + password
A normal HTTP POST request — at this point the server has no idea who you are yet.
2
Server validates the credentials
Checks the password hash in the users table matches. If it does, the server now needs a way to recognize you on your next request without asking for the password again.
3
Server creates a sessiona session store
A random, unguessable session ID is generated and saved server-side — in Redis, an in-memory store, or a database table — along with which user it belongs to and when it expires.
SET session:a3f9c1e8 { user_id: 42, expires: ... }
4
Server sends the session ID back as a cookie
The Set-Cookie header from above — the session ID itself, not your password or user data, is what gets handed to the browser.
5
Every future request, the browser attaches that cookie automatically
The server looks up that session ID in its session store, finds "oh, this is user 42," and now knows who's asking — without a password in sight.

🔒 The Two Attacks You're Actually Defending Against
🎯 XSS (Cross-Site Scripting)
Malicious JavaScript gets injected into your page (e.g. through an unescaped comment field) and tries to read document.cookie to steal the session ID. Defense: the HttpOnly flag — it makes the cookie completely invisible to any JavaScript, even malicious injected JavaScript.
🎯 CSRF (Cross-Site Request Forgery)
A different, malicious site tricks your browser into sending a request to your bank while you're still logged in — the browser attaches your real cookie automatically. Defense: the SameSite flag — Strict/Lax stops the cookie being sent on requests that originated from another site.
🎯 Interview Q&A
C1Explain the actual difference between a cookie and a session.▼
ANSWER
A cookie is a small piece of data the browser stores and sends back on every request — it lives on the client. A session is server-side state — usually just "which user does this session ID belong to" — stored in something like Redis or a database. The cookie's whole job is just to carry the session ID back and forth; the actual meaningful data lives on the server.

cookie = client-side carriersession = server-side state
C2Why does the session ID get stored in Redis instead of just in memory on one server?▼
ANSWER
Once you have more than one app server behind a load balancer, a session stored only in that one server's memory becomes invisible to the other servers — a user could get logged out just because their next request landed on a different machine. A shared store like Redis means every app server can look up the same session.

shared session store = works across multiple servers
C3Why is HttpOnly on the session cookie so important?▼
ANSWER
Without HttpOnly, any JavaScript running on your page — including malicious JavaScript injected through an XSS vulnerability — can read document.cookie and steal the session ID directly, letting an attacker impersonate that user with zero password needed. HttpOnly makes the cookie completely invisible to JavaScript, closing that entire attack path.

HttpOnly blocks document.cookie access
🍪
Login → session created server-side → cookie carries the ID → server looks it up every request
The cookie is never the data — it's just the claim ticket. The real state always lives in the session store on the server.

PR1A query that was fast last week is suddenly slow. Walk me through your investigation.▼
APPROACH
1. Run EXPLAIN ANALYZE on it right now — is it still using the index it used to, or has it silently switched to a sequential scan?
2. Check if the table has grown massively, or if statistics are stale — an out-of-date query planner can pick a bad plan. Run ANALYZE tablename to refresh stats.
3. Check if an index was accidentally dropped, or if a recent migration changed a column type in a way that stopped the index from being used.
4. Check overall server load — is it this one query, or is the whole database under pressure from something else?

EXPLAIN ANALYZE firstcheck stats freshnessconfirm the index still exists
PR2Two transactions just deadlocked each other. What actually happened, and how do you prevent it?▼
APPROACH
Transaction A locks row 1, then wants row 2. Transaction B locks row 2, then wants row 1. Neither can proceed — each is waiting on the other. The database detects this and forcibly kills one transaction (rolling it back) so the other can continue.

Prevention: always acquire locks in the same order across every part of your codebase (e.g. always lock the lower ID first). Keep transactions short. Consider lower isolation levels where correctness allows it, since stricter isolation means more locking.

consistent lock orderingshorter transactions
PR3Your primary database server just went down. What's your actual recovery plan?▼
APPROACH
This is why you run replication — one or more read replicas continuously copying the primary's data. When the primary dies: promote a replica to be the new primary (either automatically via a tool like Patroni/orchestrator, or manually), point application traffic at the new primary, then bring the old primary back later as a replica once it's healthy.

The real interview trap: acknowledging that failover means a brief window of downtime (detection + promotion time) and possibly losing the last few unreplicated writes, depending on whether replication was synchronous or asynchronous.

replica promotionsync vs async replication trade-off
PR4What's the N+1 query problem, and how do you actually spot and fix it?▼
APPROACH
Loading 50 posts, then looping through them and running a separate query for each post's author — that's 1 query + 50 more = 51 queries for data that could've been fetched in 1 or 2. It's incredibly common with ORMs that lazy-load relationships by default.

Spot it: log/count actual queries per request in dev — a request doing 50+ queries for one page is the classic smell.
Fix it: use a JOIN, or your ORM's "eager loading" feature (e.g. .includes(), JOIN FETCH) to grab everything in one or two queries instead of one-per-row.

1 query + N loop queries = N+1fix: JOIN or eager load
PR5Your app is getting "too many connections" errors from the database. What's going on?▼
APPROACH
Every database has a hard cap on simultaneous connections. This usually means either: connections aren't being closed/returned properly (a leak), you're opening a new connection per request instead of reusing a pool, or you genuinely have more traffic than your connection limit allows.

Fix: use a connection pool (like PgBouncer for Postgres) so requests share a small, fixed set of real database connections instead of each request opening its own. Audit code for connections that are opened but never explicitly released.

connection pooling (PgBouncer)check for connection leaks
PR6You need to add a column to a table with 200 million rows, in production, with zero downtime. How?▼
APPROACH
The danger is that some migration types (like adding a column with a non-null default in older MySQL versions) rewrite the entire table, locking it for the whole duration. The safe pattern: add the column as nullable, with no default first (usually instant), backfill the data in small batches in the background, then add the NOT NULL constraint once every row is filled in.

nullable first, backfill in batches, constrain last
PR7When would you actually choose a NoSQL database over a relational one?▼
APPROACH
When your data doesn't naturally fit rows and fixed columns (deeply nested/variable documents), when you need to scale writes horizontally more easily than a relational database typically allows, or when you don't need multi-table transactions or complex JOINs. Common real fits: a product catalog with wildly different attributes per category (document store), a cache/session store (key-value), or time-series metrics (column-family). If you need strong consistency and complex relationships, relational is almost always still the right default.

variable/nested data → document storeneed strong consistency → stick with SQL
PR8Disk usage on the database server is at 95% and climbing. What do you actually check, in order?▼
APPROACH
1. Check what's actually using the space — table sizes, index sizes, and write-ahead-log/binlog size (these can balloon if replication is stuck or lagging).
2. Check for bloat — deleted rows in some databases (like PostgreSQL with MVCC) aren't immediately reclaimed; a VACUUM may be overdue.
3. Check for old, unpruned partitions or unarchived data that should have been dropped already (see the Partitioning tab).
4. Short-term: free up space safely. Long-term: set up monitoring and alerts well before 95%, and automate partition/log cleanup.

check WAL/binlog sizecheck for table bloat / VACUUM
