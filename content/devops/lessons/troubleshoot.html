🧠 How to think, before you touch anything
Every problem below follows the exact same thinking process. Learn this once, and it works on almost anything, not just these 5:
1. What changed? — a deploy, an edit, a reboot, or genuinely nothing? This alone solves half of all problems.
2. Make it happen again — if you can reliably reproduce it, you can reliably confirm when it's actually fixed.
3. Check the cheap, obvious thing first — before anything complicated, before Googling, before panicking.
4. Change one thing at a time — then check again. Change three things at once and you'll never know which one actually fixed it.
5. Ask "why did this happen" — a fix that stops it from happening again beats a fix that just makes today's fire go away.
🐧 5 Everyday Linux Problems, Solved the Same Calm Way
These are genuinely the ones you'll hit most — not exotic edge cases, just Tuesday.
1. 😟 "My app isn't responding"
The symptom: you (or a user) try to reach the app and get nothing — a hang, a timeout, "connection refused."
🧠 How to think about it: don't jump to anything complicated yet — network, DNS, a bug in the code. Start at the simplest possible layer first: is the program even running at all? That one question rules out or confirms the most common cause in seconds.
$ systemctl status myapp ● myapp.service - inactive (dead)
What you found: the app crashed and simply isn't running anymore — nothing to do with the network at all.
🔧 The fix: systemctl restart myapp — it's back up immediately. Why it happened: apps crash — an unhandled error, running out of memory, someone stopping it manually and forgetting to start it again. Prevent it next time: run it under something that auto-restarts on crash (systemd, pm2) instead of a plain terminal process.
▶️ APPLYING THE FIX — STEP BY STEP
devops@server: ~ (fixing it)
$ systemctl restart myapp $ systemctl status myapp ● myapp.service - active (running) $ curl localhost:3000 Hello World ↳ responding again — fixed!
2. 😟 "No space left on device"
The symptom: a command fails with that exact message, or the app can't save uploads or write logs anymore.
🧠 How to think about it: disk space almost never disappears in one dramatic moment — it quietly fills up over weeks from logs, temp files, and old backups nobody's cleaning up. Your job is just to find WHERE it went.
$ df -h /dev/sda1 50G 49G 0G 100% / $ du -sh /var/log/* | sort -rh | head -3 9.8G /var/log/app-debug.log 120M /var/log/nginx 40M /var/log/syslog
What you found: the root filesystem is completely full, and one single debug log file is responsible for almost all of it.
🔧 The fix: > /var/log/app-debug.log empties it instantly without deleting the file (safer than rm while something might still be writing to it). Why it happened: debug logging was left on and nothing was ever set up to rotate or delete old logs. Prevent it next time: set up logrotate, or reuse the cleanup script from the 🤖 Bash Automation tab.
▶️ APPLYING THE FIX — STEP BY STEP
devops@server: ~ (fixing it)
$ > /var/log/app-debug.log $ df -h /dev/sda1 50G 39G 11G 78% / ↳ 11GB free again — fixed!
3. 😟 "Permission denied"
The symptom: running a script or opening a file gives you exactly that: Permission denied.
🧠 How to think about it: this is never mysterious — it's always a plain, checkable fact about two things: who owns this file, and who you actually are right now. Don't guess, don't immediately reach for sudo — look first.
$ ./deploy.sh bash: ./deploy.sh: Permission denied $ ls -l deploy.sh -rw-r--r-- 1 root root 842 deploy.sh $ whoami devops
What you found: the file has no execute permission for anyone (notice there's no "x" anywhere in -rw-r--r--), and it's owned by root, not you.
🔧 The fix: chmod +x deploy.sh if it just needs to be executable, or sudo chown devops deploy.sh if you genuinely need to own it. Why it happened: the file was created by a different user (often root, during setup) and the execute bit was never set. Prevent it next time: when you write a new script, make it executable in the same breath you save it — it becomes a habit fast.
▶️ APPLYING THE FIX — STEP BY STEP
devops@server: ~ (fixing it)
$ chmod +x deploy.sh $ ls -l deploy.sh -rwxr-xr-x 1 root root 842 deploy.sh $ ./deploy.sh ✓ Deploying... ↳ runs fine now — fixed!
4. 😟 "Command not found"
The symptom: you type a command you're SURE exists, and bash says command not found.
🧠 How to think about it: there are only ever two real explanations, so check both in order: either the tool genuinely isn't installed on this machine, or it IS installed, but bash doesn't know which folder to look in for it.
$ docker --version bash: docker: command not found $ which docker (nothing printed — not found anywhere on PATH) $ echo $PATH /usr/local/bin:/usr/bin:/bin
What you found: which came back empty, meaning it's genuinely not installed at all — not a PATH problem this time.
🔧 The fix: install it — sudo apt install docker.io. (If which HAD found it somewhere, the fix instead would be adding that folder to PATH: export PATH=$PATH:/that/folder.) Why it happened: a fresh server, or a fresh SSH session as a different user with a different setup than you expected. Prevent it next time: bake required tools into your server setup script (see 🏗️ Terraform for DevOps or the AMI/user-data pattern) instead of installing things by hand after the fact.
▶️ APPLYING THE FIX — STEP BY STEP
devops@server: ~ (fixing it)
$ sudo apt install docker.io Setting up docker.io ... $ docker --version Docker version 24.0.7 ↳ found it now — fixed!
5. 😟 "The server is really slow"
The symptom: everything feels sluggish — pages take forever, even typing over SSH feels laggy.
🧠 How to think about it: "slow" isn't a real answer — it's a feeling. Your actual job is turning that vague feeling into one specific, measurable number: is it CPU maxed out? Memory full? One command usually tells you immediately which resource is actually the problem.
$ top %CPU %MEM COMMAND 98.2 4.1 node 0.3 1.2 sshd 0.1 0.8 bash
What you found: one single node process is eating 98% of the CPU — that's the actual bottleneck, not the whole server being generically "slow."
🔧 The fix: restart that one process (systemctl restart myapp) to relieve it immediately, then go look at what it was actually doing — often an infinite loop or a runaway request. Why it happened: a bug causing wasted CPU work, a memory leak, or the server genuinely outgrew its size for real traffic. Prevent it next time: set up monitoring and alerts (📡 Prometheus + Grafana) so you find out before a user complains, not after.
▶️ APPLYING THE FIX — STEP BY STEP
devops@server: ~ (fixing it)
$ systemctl restart myapp $ top %CPU %MEM COMMAND 2.1 4.0 node ↳ CPU usage back to normal — fixed!
6. 😟 "I can't SSH into my server"
😟 THE PROBLEM
You type your normal ssh command and... nothing. It just hangs forever, or says "connection refused."
🧠 How to think about it: don't panic and don't assume the server is dead. Ask one simple question first: is the server even reachable at all, or is it just this one door (port 22) that's closed? Those are two very different problems.
devops@laptop: ~
$ ssh devops@203.0.113.45 ssh: connect to host 203.0.113.45 port 22: Connection timed out $ ping 203.0.113.45 64 bytes from 203.0.113.45: icmp_seq=1 time=12ms ↳ it answered! the server itself is alive and reachable
What you found: the server answers ping just fine — it's alive. So it's not a dead server, it's specifically port 22 being blocked.
🔧 THE FIX
Open port 22 in the firewall — sudo ufw allow 22 if it's a Linux firewall, or add an inbound rule for port 22 in the AWS Security Group if it's a cloud server. Why it happened: the port simply was never opened, or a firewall rule changed. Prevent it next time: when you launch a new server, opening port 22 (just for your IP, not the whole internet) is the very first thing to check.
▶️ APPLYING THE FIX — STEP BY STEP
devops@laptop: ~ (fixing it)
$ sudo ufw allow 22 Rule added $ ssh devops@203.0.113.45 Welcome to Ubuntu 22.04 LTS devops@server:~$ ↳ connected — fixed!
7. 😟 "I changed the code, but nothing happened"
😟 THE PROBLEM
You edit a file, save it, refresh the page — and it's still showing the old version, like your edit never happened.
🧠 How to think about it: saving a file and a program actually USING that file are two completely separate things. A program reads your code once, when it starts — editing the file afterward doesn't magically update a program that's already running.
devops@server: ~
$ curl localhost:3000 Hello World ← the OLD text — my edit isn't showing $ ps aux | grep node devops 1044 node app.js ↳ started 3 hours ago — BEFORE I edited the file
What you found: the process still running is the OLD one, from before your edit — it has no idea the file changed underneath it.
🔧 THE FIX
Restart it — systemctl restart myapp (or however you started it). Why it happened: this trips up genuinely everyone at some point — it's such a common gotcha it's almost a rite of passage. Prevent it next time: make "did I restart it?" your automatic first question anytime an edit doesn't seem to be working.
▶️ APPLYING THE FIX — STEP BY STEP
devops@server: ~ (fixing it)
$ systemctl restart myapp $ curl localhost:3000 Hello DevOps! (updated) ↳ new code is live — fixed!
8. 😟 "The app crashes right after I start it"
😟 THE PROBLEM
You start the app and it just... dies. Instantly. No idea why.
🧠 How to think about it: resist the urge to guess. Almost every crash prints an actual error message explaining exactly what went wrong — the answer is usually sitting right there on screen, you just have to actually read it instead of skimming past it.
devops@server: ~
$ node app.js Server starting... Error: Cannot find module 'express' at Function.Module._resolveFilename (...)
What you found: the very first line already tells you exactly what's wrong — a required piece of code ("express") is missing.
🔧 THE FIX
Run npm install to install whatever's missing, then start it again. Why it happened: the code was copied onto this server, but the dependencies it needs never got installed here. Prevent it next time: always read the FIRST error line before doing anything else — it's almost always the real answer, and everything printed after it is just extra noise.
▶️ APPLYING THE FIX — STEP BY STEP
devops@server: ~ (fixing it)
$ npm install added 57 packages in 4s $ node app.js Server starting... Listening on port 3000 ↳ running clean, no crash — fixed!
9. 😟 "It works when I run it myself, but not through cron"
😟 THE PROBLEM
You run your script by hand and it works perfectly. You schedule it with cron to run automatically — and it silently fails every time.
🧠 How to think about it: when YOU type a command, your terminal quietly hands it a ton of setup for free (your normal folder, your normal shortcuts). Cron gets none of that — it starts from a completely bare, empty setup, so anything your script assumed was "just there" might not be.
devops@server: ~
$ ./backup.sh ✓ Backup saved ↳ works fine when I run it myself $ crontab -l 0 2 * * * backup.sh ← just the filename, no folder
What you found: the crontab line just says backup.sh — no folder in front of it. Cron has no idea where to even look for that file.
🔧 THE FIX
Use the FULL path in cron: 0 2 * * * /home/devops/scripts/backup.sh. Why it happened: cron simply doesn't know your normal folder or shortcuts the way your own logged-in terminal does. Prevent it next time: always write full, exact paths inside anything meant to run automatically — never rely on it "just knowing where things are."
▶️ APPLYING THE FIX — STEP BY STEP
devops@server: ~ (fixing it)
$ crontab -e # changed to: 0 2 * * * /home/devops/scripts/backup.sh $ tail -3 /var/log/cron.log ✓ Backup saved to /home/devops/backups/... ↳ runs automatically now — fixed!
10. 😟 "I can't find where a file or log actually is"
😟 THE PROBLEM
Someone says "check the log file" — but you have no idea which folder it's actually sitting in.
🧠 How to think about it: you don't need to guess or click through folder after folder by hand. Linux can just search the whole machine for you in seconds — let it do the work instead of you doing it manually.
devops@server: ~
$ cat app.log cat: app.log: No such file or directory ↳ not here, where did it go? $ find / -name "app.log" 2>/dev/null /var/log/myapp/app.log ↳ found it!
What you found: the file was never in the folder you were sitting in — it lives somewhere else entirely, and find located it instantly.
🔧 THE FIX
find / -name "filename" 2>/dev/null — searches the entire machine and quietly ignores any "permission denied" folders along the way. Why it happened: different apps store logs in different default places, and there's no reason you'd have them memorized. Prevent it next time: reach for find immediately instead of guessing — it's faster than clicking around ever will be.
▶️ APPLYING THE FIX — STEP BY STEP
devops@server: ~ (fixing it)
$ tail -f /var/log/myapp/app.log [INFO] Server running smoothly ↳ found it, now watching the live log — fixed!
🔎 5 Things To Always Check, No Matter What Broke
All 10 problems above really come down to just these 5 questions. Keep this list in your head — it works on almost anything:
1. Is it even running? — ps aux or systemctl status
2. What do the logs actually say? — don't guess, go read the real error
3. Is there room to work with? — df -h for disk, free -h for memory
4. Are you actually allowed to do this? — file permissions, firewall rules, who owns what
5. Did something about the environment change? — different user, manual run vs. cron, a fresh server vs. an old one
🧠 How to think, before you touch anything
Networking problems feel scary because there are more moving parts — but the same calm process still works. A few extra habits that help specifically here:
1. Split it in half: is it DNS, or is it the server? — test the raw IP directly. If the IP works but the domain doesn't, it's DNS. If neither works, it's the server.
2. "Refused" and "timed out" mean different things — refused means something answered and said no (check what's listening). Timed out usually means a firewall or a dead host (nothing answered at all).
3. Test the network path directly — curl, ping, nc. Don't trust a vague app error — go check the actual connection yourself.
4. If it's random, there's probably more than one path — intermittent failures usually mean multiple IPs or servers, and only one of them is actually broken.
🌐 5 Everyday Networking Problems, Solved the Same Calm Way
Same style as the Linux tab — the problem, how to think about it, the real commands, and then watching the actual fix happen.
1. 😟 "The website works for me, but nobody else can reach it"
😟 THE PROBLEM
You just moved your app to a new server. It loads fine for you — but everyone else swears the site is down.
🧠 How to think about it: DNS is like a phonebook that everyone shares — but that phonebook takes a little time to update everywhere. It's very possible the phonebook still has the OLD address written in it for most people.
devops@laptop: ~
$ dig myapp.com myapp.com. 300 IN A 203.0.113.10 ↳ the OLD server $ curl ifconfig.me # run ON the new server 203.0.113.99 ↳ this is the NEW server's real address
What you found: DNS is still pointing everyone at the OLD server — that's the entire mismatch. Nothing is actually broken, the phonebook is just outdated.
🔧 THE FIX
Update the DNS A record to point at the new server's IP. Why it happened: nobody updated the phonebook entry after moving to the new server. Prevent it next time: update DNS BEFORE fully shutting down the old server, so there's overlap instead of a gap.
▶️ APPLYING THE FIX — STEP BY STEP
devops@laptop: ~ (fixing it)
# updated the A record in the DNS dashboard to 203.0.113.99 $ dig myapp.com myapp.com. 300 IN A 203.0.113.99 ↳ now pointing at the right server — fixed!
2. 😟 "Connection refused" when one service calls another
😟 THE PROBLEM
Your app tries to call another service on the network and gets Connection refused — instantly, every time.
🧠 How to think about it: "refused" is actually good news — it means the network path works fine, and something on the other end is awake enough to actively say no. So the real question is: is that service listening where you think it is?
devops@server: ~
$ curl http://192.168.1.50:5000/api curl: (7) Failed to connect: Connection refused $ ss -tuln | grep 5000 tcp LISTEN 127.0.0.1:5000 ↳ only listening to itself!
What you found: the service IS running — but it's only listening on 127.0.0.1 (itself), so no other machine on the network can ever reach it, no matter what.
🔧 THE FIX
Change the service's bind address to 0.0.0.0 (all interfaces) instead of 127.0.0.1, then restart it. Why it happened: a lot of frameworks default to localhost-only for safety. Prevent it next time: decide on purpose whether a service should be reachable from the network — don't leave it to a default.
▶️ APPLYING THE FIX — STEP BY STEP
devops@server: ~ (fixing it)
# changed config: HOST=0.0.0.0 (was 127.0.0.1) $ systemctl restart myservice $ ss -tuln | grep 5000 tcp LISTEN 0.0.0.0:5000 $ curl http://192.168.1.50:5000/api {"status":"ok"} ↳ reachable now — fixed!
3. 😟 The site shows "Not Secure" / a certificate warning
😟 THE PROBLEM
The site still loads, but the browser shows a scary warning — "Not Secure," or a certificate error.
🧠 How to think about it: HTTPS certificates aren't permanent — they expire on a schedule (often every 90 days for free ones). If nothing automatically renews it, one day it just quietly stops being valid.
devops@laptop: ~
$ curl -vI https://myapp.com 2>&1 | grep expire * SSL certificate expire date: Jul 10 2026 (EXPIRED)
What you found: the certificate genuinely expired — plain and simple, nobody renewed it in time.
🔧 THE FIX
Renew it — certbot renew for a free Let's Encrypt certificate — then reload the web server so it picks up the new one. Why it happened: renewal was never automated, so it silently expired. Prevent it next time: set renewal on a cron job so it happens automatically, well before expiry.
▶️ APPLYING THE FIX — STEP BY STEP
devops@server: ~ (fixing it)
$ sudo certbot renew Congratulations, all renewals succeeded $ sudo systemctl reload nginx $ curl -vI https://myapp.com 2>&1 | grep expire * SSL certificate expire date: Oct 08 2026 ↳ valid again — fixed!
4. 😟 The app server can't reach the database server
😟 THE PROBLEM
Your app tries to connect to the database on another server, and it just... hangs. Then eventually times out.
🧠 How to think about it: a hang and a timeout (not an instant "refused") is a very specific clue — it usually means something in between the two machines is silently dropping the traffic, most often a firewall.
devops@app-server: ~
$ nc -zv 10.0.1.20 5432 nc: connect to 10.0.1.20 port 5432 timed out ↳ not "refused" — just silence. Something is blocking it.
What you found: total silence, not a rejection — a strong sign a firewall or security group between the two servers is quietly dropping the connection before it ever reaches the database.
🔧 THE FIX
Add a firewall/security group rule allowing port 5432 FROM the app server's IP TO the database server. Why it happened: the database's firewall was locked down (correctly!) and this app server was just never added to the allow list. Prevent it next time: whenever you add a new server that needs to talk to another, opening that specific path is part of the setup, not an afterthought.
▶️ APPLYING THE FIX — STEP BY STEP
devops@app-server: ~ (fixing it)
# added rule: allow port 5432 from app-server IP $ nc -zv 10.0.1.20 5432 Connection to 10.0.1.20 5432 port succeeded! $ psql -h 10.0.1.20 -U admin mydb mydb=> ↳ connected — fixed!
5. 😟 "It works sometimes, and fails randomly"
😟 THE PROBLEM
Same request, same everything — but sometimes it works fine, and sometimes it just fails. No obvious pattern.
🧠 How to think about it: a problem that isn't ALWAYS broken is a big clue on its own — it usually means there's more than one possible path your request could take, and only one of those paths is actually broken.
devops@laptop: ~
$ dig myapp.com myapp.com. 300 IN A 203.0.113.10 myapp.com. 300 IN A 203.0.113.11 ↳ two different servers answer for the same domain! $ curl -I http://203.0.113.11 curl: (7) Connection refused ↳ found the broken one
What you found: DNS is actually handing out TWO different server addresses for the same domain, and one of the two is dead. Roughly half of all requests randomly land on the broken one.
🔧 THE FIX
Fix or restart the dead server, or remove it from DNS until it's healthy again, so only working servers ever receive traffic. Why it happened: one server in the group quietly crashed or was never fully set up, but nothing was checking its health. Prevent it next time: use a load balancer with health checks (see the Networking for DevOps tab) instead of raw DNS with multiple IPs — it automatically stops sending traffic to anything unhealthy.
▶️ APPLYING THE FIX — STEP BY STEP
devops@laptop: ~ (fixing it)
# removed the dead 203.0.113.11 record from DNS $ dig myapp.com myapp.com. 300 IN A 203.0.113.10 ↳ only the healthy server remains — fixed!
🔎 5 Things To Always Check When The Network Is The Suspect
All 5 problems above really come down to these 5 questions. Keep this list in your head:
1. Does the raw IP work? — tells you instantly if it's DNS or the server itself
2. Refused, or timed out? — refused = something answered. Timed out = probably a firewall, or nothing's there
3. Is it actually listening where you expect? — ss -tuln, and on which address (0.0.0.0 vs 127.0.0.1)
4. Is a certificate involved, and is it still valid? — curl -vI shows the expiry date
5. Is there more than one path? — multiple DNS records or backend servers means only one might be the broken one
🧠 How to think, before you touch anything
Git panics are almost always worse in your head than in reality. A few habits that make every one of these calmer:
1. Nothing is usually lost — git almost never actually deletes your work. It just changes what's currently pointing at it. Most "I lost everything" moments are recoverable.
2. Has it been pushed yet? — this one question decides everything. Not pushed = safe to rewrite history freely. Already pushed/shared = don't rewrite it, add a new commit instead.
3. Read the actual error — git's messages are unusually specific and literal. "Rejected," "conflict," "detached" all mean exactly what they say.
4. When git refuses to do something, that's it protecting you — not being annoying. Understand why before you force anything.
🌿 10 Everyday Git Problems, Solved the Same Calm Way
Same style as Linux and Networking — the problem, how to think about it, the real commands, and then watching the actual fix happen.
1. 😟 "I committed to the wrong branch"
😟 THE PROBLEM
You made changes and committed — then realized you were sitting on main, not the feature branch you meant to be on.
🧠 How to think about it: don't redo any work — the commit already exists and is perfectly fine. You just need to move it to where it should actually live.
devops@laptop: ~/app
$ git log --oneline -1 a3f9d2c Add login page $ git branch * main feature/login
What you found: confirmed — the commit is sitting on main instead of feature/login.
🔧 THE FIX
Create the correct branch right here (it takes the commit with it), then remove the commit from main. Why it happened: forgetting to check which branch you're on before starting work — extremely common. Prevent it next time: glance at your branch name (most terminals show it) before your very first edit.
▶️ APPLYING THE FIX — STEP BY STEP
devops@laptop: ~/app (fixing it)
$ git branch feature/login $ git reset --hard HEAD~1 $ git checkout feature/login Switched to branch 'feature/login' $ git log --oneline -1 a3f9d2c Add login page ↳ now on the right branch — fixed!
2. 😟 "I have a merge conflict and don't know what to do"
😟 THE PROBLEM
You run git merge and git says CONFLICT — and now there's weird <<<<<<< text inside your file.
🧠 How to think about it: a conflict just means two branches changed the exact same line differently, and git genuinely can't guess which one you want. It's not broken — it's politely asking you to decide.
devops@laptop: ~/app
$ git merge feature/login Auto-merging app.js CONFLICT (content): Merge conflict in app.js $ cat app.js <<<<<<< HEAD const port = 3000; ======= const port = 8080; >>>>>>> feature/login
What you found: both branches changed the same line to a different value — git is showing you both versions, side by side, waiting for you to pick.
🔧 THE FIX
Open the file, delete the <<<<<<< / ======= / >>>>>>> markers, keep whichever line (or combination) is actually correct, then add and commit. Why it happened: two people (or two branches) genuinely changed the same line — completely normal on any real team. Prevent it next time: pull and merge often, in small chunks — tiny conflicts are easy, giant ones are scary.
▶️ APPLYING THE FIX — STEP BY STEP
devops@laptop: ~/app (fixing it)
# edited app.js — removed markers, kept: const port = 8080; $ git add app.js $ git commit ✓ Merge made by the 'recursive' strategy. ↳ conflict resolved — fixed!
3. 😟 "I accidentally committed a secret file"
😟 THE PROBLEM
You committed .env — with a real API key inside — and realized it right after.
🧠 How to think about it: the single most important question is: has it been pushed yet? If not, this is simple and completely private. If it HAS been pushed, the key is already exposed and deleting it later doesn't erase it from history — treat it as compromised and rotate it.
devops@laptop: ~/app
$ git log --oneline -1 b7e21ab Add .env with API keys $ git status On branch main Your branch is ahead of 'origin/main' by 1 commit. ↳ good — this hasn't been pushed yet
What you found: the risky commit is still only local — nobody else has seen it yet, so it can be cleanly undone.
🔧 THE FIX
Undo the commit, remove .env from tracking, and add it to .gitignore so this can't happen again. Why it happened: .gitignore either didn't exist yet or didn't list this file. Prevent it next time: set up .gitignore as literally the first thing in any new project, before the first commit.
▶️ APPLYING THE FIX — STEP BY STEP
devops@laptop: ~/app (fixing it)
$ git reset --soft HEAD~1 $ git rm --cached .env $ echo ".env" >> .gitignore $ git add .gitignore $ git commit -m "Add .gitignore, remove .env" ✓ committed cleanly ↳ secret removed before it was ever pushed — fixed!
4. 😟 "I forgot to add a file to my last commit"
😟 THE PROBLEM
You committed, then noticed one file never actually got included.
🧠 How to think about it: since you haven't pushed yet, you don't need a whole separate commit for one forgotten file — you can just quietly fold it into the one you just made.
devops@laptop: ~/app
$ git status Untracked files: utils.js ↳ this file never got committed
What you found: confirmed — utils.js was sitting there the whole time, just never staged.
🔧 THE FIX
Add the file, then git commit --amend — it folds into the previous commit instead of creating a new one. Why it happened: forgot to git add it before committing. Prevent it next time: run git status right before every commit, as a habit, to see exactly what's about to be included.
▶️ APPLYING THE FIX — STEP BY STEP
devops@laptop: ~/app (fixing it)
$ git add utils.js $ git commit --amend --no-edit $ git show --stat HEAD utils.js | 12 ++++++++++++ ↳ now included in the same commit — fixed!
5. 😟 "git push says 'rejected — non-fast-forward'"
😟 THE PROBLEM
git push fails: "Updates were rejected because the remote contains work that you do not have locally."
🧠 How to think about it: this isn't an error in your code at all — it just means someone else pushed before you, and git is refusing to silently overwrite their work. That's a safety feature, not a bug.
devops@laptop: ~/app
$ git push ! [rejected] main -> main (non-fast-forward) error: failed to push some refs
What you found: the remote branch has commits your local branch doesn't — a teammate pushed first, and your local history is now behind.
🔧 THE FIX
Pull their changes first (merge or rebase them in), then push. Why it happened: completely normal on any team — two people worked at the same time. Prevent it next time: pull before you start working, and again right before you push, to minimize surprises.
▶️ APPLYING THE FIX — STEP BY STEP
devops@laptop: ~/app (fixing it)
$ git pull --rebase Successfully rebased and updated refs/heads/main. $ git push ✓ main -> main ↳ pushed cleanly — fixed!
6. 😟 "I want to undo my last commit"
😟 THE PROBLEM
You made a commit and want it gone — maybe it was a mistake, or you're not ready for it yet.
🧠 How to think about it: this splits into two completely different tools depending on one question: has anyone else seen this commit? Not pushed yet → safe to rewrite. Already pushed/shared → don't rewrite it, add a new commit that undoes it instead.
devops@laptop: ~/app
$ git log --oneline -1 c4f8a21 Bad commit $ git status Your branch is ahead of 'origin/main' by 1 commit. ↳ not pushed yet — safe to rewrite
What you found: this commit is still local-only — nobody else has it, so rewriting history here is completely safe.
🔧 THE FIX
git reset --soft HEAD~1 — removes the commit but keeps all your changes, ready to redo the commit properly. If it HAD already been pushed: use git revert HEAD instead — it adds a brand new commit that undoes the old one, without erasing shared history. Prevent it next time: keep this rule in your head permanently — pushed changes what's safe.
▶️ APPLYING THE FIX — STEP BY STEP
devops@laptop: ~/app (fixing it)
$ git reset --soft HEAD~1 $ git status Changes to be committed: modified: app.js ↳ commit undone, all changes kept — fixed!
7. 😟 "I'm in a weird 'detached HEAD' state"
😟 THE PROBLEM
You checked out an old commit, and git warns: "You are in 'detached HEAD' state."
🧠 How to think about it: nothing is broken — you're just looking at an old snapshot instead of standing on a branch. The only real danger is committing here without realizing it, since those new commits aren't attached to anything and can get lost.
devops@laptop: ~/app
$ git checkout a3f9d2c Note: switching to 'a3f9d2c'. You are in 'detached HEAD' state... $ git branch * (HEAD detached at a3f9d2c) main
What you found: confirmed — you're standing on a specific commit, not a branch. Any commits made right now wouldn't be tracked by anything.
🔧 THE FIX
Just looking around? git checkout main gets you back, nothing lost. Already made commits you want to keep? Create a branch right here FIRST, before doing anything else. Why it happened: checking out a specific commit or tag instead of a branch name. Prevent it next time: if you only meant to look at old code, you never needed to check it out at all — git show a3f9d2c shows it without moving anywhere.
▶️ APPLYING THE FIX — STEP BY STEP
devops@laptop: ~/app (fixing it)
$ git checkout -b rescued-work Switched to a new branch 'rescued-work' ↳ any work made here is now safely on a real branch — fixed!
8. 😟 "I want to change my last commit message"
😟 THE PROBLEM
There's a typo in your last commit message — or it's just genuinely unclear what it did.
🧠 How to think about it: same rule as always — if it hasn't been pushed, changing it is completely painless.
devops@laptop: ~/app
$ git log --oneline -1 a3f9d2c fix bugg
What you found: a typo, and honestly not a very useful message either way.
🔧 THE FIX
git commit --amend -m "new message" replaces it entirely. Why it happened: typed quickly without a second look. Prevent it next time: write commit messages like you're explaining the change to a teammate six months from now — because eventually, you are.
▶️ APPLYING THE FIX — STEP BY STEP
devops@laptop: ~/app (fixing it)
$ git commit --amend -m "Fix login validation bug" $ git log --oneline -1 e91c4a2 Fix login validation bug ↳ message updated — fixed!
9. 😟 "I accidentally deleted a branch"
😟 THE PROBLEM
You ran git branch -d feature/login — and then realized you still needed it.
🧠 How to think about it: remember the golden rule — git almost never actually throws work away. Deleting a branch just removes the LABEL pointing at those commits; the commits themselves usually still exist for a while, and git keeps a record of everywhere HEAD has recently pointed.
devops@laptop: ~/app
$ git branch -d feature/login Deleted branch feature/login (was a3f9d2c). $ git branch * main ↳ gone from the branch list — but the commit isn't actually gone yet
What you found: the branch is gone, but git told you the exact commit hash it was pointing at — that's everything needed to bring it back.
🔧 THE FIX
Use git reflog to find the commit, then recreate the branch pointing at it. Why it happened: deleted the wrong branch, or forgot it hadn't been merged yet. Prevent it next time: git actually warns you with -d if a branch has unmerged work — only -D (force) skips that warning, so avoid reaching for capital D out of habit.
▶️ APPLYING THE FIX — STEP BY STEP
devops@laptop: ~/app (fixing it)
$ git reflog a3f9d2c HEAD@{0}: commit: Add login page $ git branch feature/login a3f9d2c $ git branch * main feature/login ↳ branch recovered — fixed!
10. 😟 "I have unfinished changes but need to switch branches right now"
😟 THE PROBLEM
You're mid-way through changes, an urgent fix comes in on another branch, and git won't let you switch cleanly.
🧠 How to think about it: you don't have to choose between "commit unfinished, half-broken work" or "lose it entirely" — there's a shelf for exactly this in-between situation.
devops@laptop: ~/app
$ git checkout main error: Your local changes would be overwritten by checkout.
What you found: git is protecting your unfinished work by refusing to just throw it away — it needs somewhere to put it first.
🔧 THE FIX
git stash shelves your unfinished changes and gives you a clean slate. Switch, do the urgent fix, come back, then git stash pop brings everything back exactly as it was. Why it happened: real work rarely lines up neatly with when you need to switch context. Prevent it next time: nothing to prevent — stash exists precisely for this, completely normal.
▶️ APPLYING THE FIX — STEP BY STEP
devops@laptop: ~/app (fixing it)
$ git stash Saved working directory and index state WIP on feature: a3f9d2c $ git checkout main Switched to branch 'main' # ...did the urgent fix, switched back... $ git checkout feature $ git stash pop ↳ unfinished changes are back, exactly as left — fixed!
🔎 5 Things To Always Check When Git Is Acting Up
All 10 problems above really come down to these 5 questions. Keep this list in your head:
1. Has it been pushed? — git status tells you instantly if you're ahead of the remote
2. What branch am I actually on? — git branch, before you do anything else
3. What does the log actually say? — git log --oneline for a quick, honest history
4. Is it really gone, or just unreachable right now? — git reflog before you assume anything is lost
5. Am I about to rewrite shared history? — if others have it, add a new commit instead of rewriting the old one
