📋 All Dockerfile Instructions
INSTRUCTION WHAT IT DOES
FROMFirst line. Sets the base image. FROM node:18-alpine, FROM python:3.11
WORKDIRSet working directory inside image. Subsequent commands run from here.
COPYCopy files from host into image. COPY . /app. Most common instruction.
ADDLike COPY but also supports URLs and auto-extracts tar files. Use COPY unless you need extras.
RUNExecute commands at build time. RUN npm install. Creates a cached layer.
CMDDefault command when container starts. Can be overridden at docker run.
ENTRYPOINTMain executable. Unlike CMD, can't be fully overridden — only arguments change.
ENVSet environment variable available at runtime. ENV NODE_ENV=production
ARGBuild-time variable only. Pass via docker build --build-arg KEY=val. Not in final image.
EXPOSEDocument which port the app listens on. Doesn't actually publish it — -p flag does that.
VOLUMECreate a mount point for persistent storage. Data in volumes survives container restarts.
USERSet user to run as. Security best practice — never run as root in production.
LABELAdd metadata key-value pairs to the image. Good for versioning and documentation.
HEALTHCHECKHealth probe command. Docker marks container unhealthy if it fails. Kubernetes uses this.
🔍 Example Dockerfile — Explained Line by Line
FROM node:14
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 3000
CMD ["npm", "start"]
Base image: Node.js v14
Working dir: /app inside container
Copy deps first (cache optimization!)
Install deps (cached if package.json unchanged)
Copy app code (changes most often = last)
Document port 3000 (doesn't publish)
Start command when container runs
⚡ Layers & Caching — The Performance Secret
Each Dockerfile instruction creates a layer. Unchanged layers are cached — Docker skips rebuilding them.

The golden rule: Put rarely-changing things first (base image, deps install), frequently-changing things last (app code). If you change your code but not package.json, only the last COPY and CMD layers rebuild. Saves huge time.
🗄️ Docker Concepts
Volumepersistent storage
Containers are ephemeral — when they stop, their filesystem is gone. A Volume is persistent storage mounted into a container. Data in volumes survives restarts, crashes, and container recreation. Essential for databases.
$ docker run -v mydata:/app/data myapp
Networkcontainer comms
Docker networks allow containers to talk to each other or the external world. Containers on the same network can reach each other by container name. By default, containers are isolated — you must connect them.
$ docker network create mynet $ docker run --network mynet myapp
docker-composemulti-container
Orchestrates multiple containers together (app + db + cache) via a single YAML file. One command spins up the entire local dev stack. Great alternative to Kubernetes for local development.
$ docker-compose up -d   # start all $ docker-compose down   # stop all
Architectureclient/host/registry
Docker Client — the UI you interact with (docker build, docker run).
Docker Host (Daemon) — background process that manages containers on the host system.
Docker Registry — centralized store for Docker images (Docker Hub, AWS ECR, GCR).

Why Docker? The Core Problem it Solves
Without Docker: "works on my machine" — env differences between dev/staging/prod cause bugs.
With Docker: same image, every environment. Build once, run anywhere. Isolation, portability, reproducibility.
🌐 Docker Networking
TYPEWHAT IT DOES
bridgeDefault network. Containers on the same bridge network can talk to each other by container name. Isolated from host network.
hostContainer shares the host's network stack directly. No isolation. Container's port 3000 IS host's port 3000. Fastest, least secure.
overlaySpans multiple Docker hosts (used in Swarm/K8s). Allows containers on different machines to communicate as if on the same network.
🔥 Multi-Stage Builds — Reduce Image Size
Build with all dev tools, then copy only the final artifact into a tiny production image. Result: images go from ~1GB → ~50MB.
# Stage 1: Build (heavy, has compilers/tools)
FROM node:18 AS builder
WORKDIR /app
COPY . .
RUN npm install && npm run build

# Stage 2: Production (tiny, only the artifact)
FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
CMD ["node", "dist/index.js"]

🔒 Docker Security Best Practices
Never run as rootUSER instruction
By default containers run as root — a container escape could give root access to the host. Always add USER appuser at the end of your Dockerfile.

RUN addgroup -S app && adduser -S app -G app
USER app
Never use :latestpin versions
In production, always pin exact image versions. node:18-alpine not node:latest. Latest can change unexpectedly and break your build. Pin both base images and dependencies.
.dockerignoreexclude files
Like .gitignore but for Docker build context. Exclude node_modules, .git, test files, docs. Prevents accidentally copying secrets into the image and speeds up build.
Scan imagesvulnerabilities
docker scout cves myapp:v1 or trivy image myapp:v1 — scan for known CVEs in your image layers. Run in CI to catch vulnerable base images before pushing to production.

🛡️ Docker Security Best Practices
Never run as rootcritical
Add USER node (or another non-root user) at the end of your Dockerfile. If an attacker escapes the container, they only have that user's permissions — not root. Always the last instruction before CMD/ENTRYPOINT.
RUN addgroup -S app && adduser -S app -G app USER app
.dockerignoresize + security
Like .gitignore but for Docker. Prevents sensitive files from being copied into the image. Also reduces image size significantly.
.git node_modules .env *.pem tests/ docs/
Scan imagesvulnerability
Scan images for known CVEs before pushing to registry. Integrate into CI pipeline — fail the build if critical vulnerabilities found.
$ docker scout cves myapp:v1 $ trivy image myapp:v1 $ snyk container test myapp:v1
Pin base image versionsreproducible
Never use FROM node:latest — it changes every time and breaks reproducibility. Pin to a specific version: FROM node:18.19.0-alpine3.19. Your build should produce the exact same image 6 months later.
📊 Container Resource Limits
Without limits, one runaway container can consume all CPU/RAM on the host and take down every other container. Always set limits in production.

docker run --memory="512m" --cpus="0.5" myapp
# 512MB RAM max, 50% of 1 CPU max

# Check live resource usage:

docker stats <container-id>           # specific container only

D1How do Docker layers work?▼
ANSWER
SHORT ANSWER
An image is a stack of read-only sheets. A container is that stack plus one blank sheet on top that it can write on.
EXPLAIN IT SIMPLY
Think of transparent plastic sheets stacked on an overhead projector.
• Sheet 1: the base operating system
• Sheet 2: the libraries you installed
• Sheet 3: your code
• Top sheet (blank, writable): whatever the running container creates
Look down through the stack and you see one complete picture. That's your filesystem. The bottom sheets are locked — nobody can edit them. Only the top blank sheet can be written on, and that sheet is thrown away when the container is deleted.
THE DETAILS
What creates a layer: RUN, COPY, ADD. These change files.
What doesn't: ENV, WORKDIR, CMD, EXPOSE, LABEL. These only add notes.
Layers are shared. If you run 50 containers from the same image, they all share the same bottom sheets. Only their top blank sheets cost extra space. This is why containers are so much lighter than virtual machines.
Layers are cached. Docker gives each layer a fingerprint. On rebuild, if the instruction and its inputs are unchanged, it reuses the old layer instead of redoing the work.
Cache breaks downward. The moment one layer changes, every layer below it is rebuilt. This is why order matters so much.
The trap everybody hits: deleting a file doesn't shrink the image.
RUN wget bigfile.tar.gz # +500 MB RUN rm bigfile.tar.gz # image is STILL 500 MB bigger
The file is still sitting on the earlier sheet. The second layer just draws a black box over it. To actually remove it, do both in one step:
RUN wget bigfile.tar.gz && tar -xzf bigfile.tar.gz && rm bigfile.tar.gz
COMMANDS
# Shows every layer and how much space it added. # This is how you find which line made your image huge. $ docker history myimage # Same, but shows the full command instead of cutting it short. $ docker history --no-trunc myimage # Ignore the cache and rebuild everything. # Use this when you suspect an old cached layer is causing a weird bug. $ docker build --no-cache -t myapp .
SAY THIS

"An image is a stack of read-only layers. A container is that stack plus one thin writable layer on top."

"Layers are cached, and changing one layer rebuilds everything below it — so I order my Dockerfile from least-changing to most-changing."

"Deleting a file in a later layer only hides it. The cleanup has to happen in the same RUN that created it."
read-only + 1 writable layercache breaks downwarddelete ≠ shrinkdocker history
D2Why use a multi-stage build?▼
ANSWER
SHORT ANSWER
Build the app with a big toolbox, then ship only the finished product in a tiny box.
EXPLAIN IT SIMPLY
Think of building furniture in your garage. To build a table you need a saw, a drill, a sander, sawdust everywhere, offcuts of wood — that's the build stage. To use the table, you need... the table. That's the runtime stage.
You don't deliver the customer's table with the saw taped to it and sawdust in the drawers. But that's exactly what a single-stage Docker build does. Multi-stage lets you write both in one file: do the messy work in stage 1, then carry only the finished table into a clean stage 2.
HOW IT WORKS
You write two FROM lines. Each FROM starts a fresh, empty stage.
FROM golang:1.22 AS builder # stage 1: has the whole Go compiler RUN go build -o /app/server FROM alpine:3.20 # stage 2: fresh and empty COPY --from=builder /app/server /server
COPY --from=builder is the magic line. It reaches back into stage 1 and takes only what you name. Everything else in stage 1 gets thrown away.
WHAT YOU GAIN
SizeA Go app: 800MB → 10MB. A React app: 1.2GB → 30MB.
SecurityNo compiler, no curl, no git, sometimes no shell at all. Far less for an attacker to use.
Source doesn't shipYour .js and .go files stay in stage 1.
Build secrets don't leakA private-repo token used in stage 1 never reaches the final image.
Faster deploysSmall images pull faster. Matters a lot when starting 50 copies.
SAY THIS

"Multi-stage separates the build environment from the runtime environment. I build with a fat image and ship with a thin one."

"COPY --from= is the whole trick. Everything else in the earlier stage is discarded."
multiple FROM linesCOPY --from=fat build, thin shipsmaller + safer
D3Write and explain a multi-stage Dockerfile.▼
ANSWER
NODE.JS VERSION
# ---------- STAGE 1: build ---------- FROM node:20 AS builder # Full Node image. Has everything needed to compile. # "AS builder" names this stage. WORKDIR /app COPY package*.json ./ # Manifests first, so the install below stays cached. RUN npm ci # Install EVERYTHING including dev tools, because we need them to build. COPY . . RUN npm run build # Produces the compiled output in /app/dist # ---------- STAGE 2: run ---------- FROM node:20-alpine # Fresh tiny image. Nothing from stage 1 is here yet. WORKDIR /app ENV NODE_ENV=production COPY package*.json ./ RUN npm ci --omit=dev && npm cache clean --force # This time skip dev tools. We only need what the app needs at runtime. COPY --from=builder /app/dist ./dist # The key line. Only the built output crosses over. # Source code and dev tools are left behind in stage 1. USER node EXPOSE 3000 CMD ["node", "dist/server.js"]
GO VERSION (the most dramatic size drop)
FROM golang:1.22 AS builder WORKDIR /src COPY . . RUN CGO_ENABLED=0 go build -o /app/server # CGO_ENABLED=0 makes a single self-contained file with no external dependencies. # That's what lets it run on a nearly-empty base image. FROM alpine:3.20 COPY --from=builder /app/server /server ENTRYPOINT ["/server"]
800MB → about 12MB.
JAVA VERSION
FROM maven:3.9-eclipse-temurin-21 AS builder WORKDIR /build COPY pom.xml . RUN mvn dependency:go-offline # Downloads dependencies in their own cached layer, before the source is copied. COPY src ./src RUN mvn package -DskipTests FROM eclipse-temurin:21-jre-alpine # JRE only. No Maven, no compiler. COPY --from=builder /build/target/*.jar app.jar ENTRYPOINT ["java", "-jar", "app.jar"]
USEFUL TRICK
# Build ONLY up to stage 1 and stop. # Great for debugging: build to the point just before the failure, # then shell in and look around. $ docker build --target builder -t debug .

ANSWER
SHORT ANSWER
Measure first, then: multi-stage build, smaller base image, clean up in the same step, and add a .dockerignore.
STEP 0 — FIND OUT WHAT'S ACTUALLY BIG
Don't guess.
# Ranked list of what each line added. The culprit is usually obvious. $ docker history myimage
THE FOUR BIG LEVERS, IN ORDER OF IMPACT
1. Multi-stage build — usually the biggest single win. Ship the app, not the toolchain. Often cuts 60–90%.
2. Smaller base image
BaseSize
node:20~1.1GB
node:20-slim~200MB
node:20-alpine~130MB
alpine:3.20~7MB
One line change, 900MB saved. Honest warning: Alpine uses a different C library (musl instead of glibc). It can break certain native libraries and has caused DNS oddities. -slim is the safer default. Use Alpine once you've tested it.
3. Clean up in the same step
RUN apt-get update \ && apt-get install -y --no-install-recommends curl \ && rm -rf /var/lib/apt/lists/*
• --no-install-recommends skips optional suggested packages. Often saves 100+ MB.
• rm -rf /var/lib/apt/lists/* deletes the package index, about 40MB.
• All in one RUN, because cleanup in a separate step doesn't shrink anything.
4. Add a .dockerignore
.git node_modules *.log tests/
A .git folder alone is often hundreds of MB.
SMALLER EXTRAS
pip install --no-cache-dir -r requirements.txt # don't keep downloads npm ci --omit=dev # skip test tools go build -ldflags="-s -w" # strip debug symbols apt-get install --no-install-recommends # skip optional packages

Python app, 1GB → 180MB:

D5Volumes vs bind mounts vs tmpfs — what's the difference?▼
ANSWER
SHORT ANSWER
All three keep data alive outside the container. Volume = Docker manages it. Bind mount = you point at a folder on your computer. tmpfs = stored in memory only, never on disk.
EXPLAIN IT SIMPLY
Your container is a hotel room. When you check out, housekeeping throws everything away.
• Volume = the hotel safe. The hotel manages it, it's in their storage room, and it's still there next time you check in.
• Bind mount = a window into your own house. Whatever you change in the room appears at home instantly, and vice versa. Convenient, but the room now has access to your house.
• tmpfs = a whiteboard. Useful while you're there, wiped completely the second you leave, and no copy exists anywhere.
THE COMPARISON
VolumeBind mounttmpfs
Where data livesDocker's own folderAny folder on your computerRAM only
Who manages itDockerYouDocker
Survives container deleteYesYesNo
Works on any machineYesNo, path must exist thereN/A
Speed on Mac/WindowsGoodSlowFast
Best forProduction data (databases)Local developmentPasswords, temp files
THE THREE POINTS THAT COME UP IN INTERVIEWS
1. Volumes don't care about your folder structure. A bind mount hardcodes /home/ali/project. That breaks on the CI server and on your colleague's Mac. A volume just works everywhere.
2. A bind mount HIDES what was already there. A volume FILLS IN. Mount an empty folder from your computer onto /app? /app inside the container is now empty, even if the image had files there. Mount an empty volume onto /app? Docker copies the image's /app contents into the volume first. Opposite behaviors — worth saying out loud.
3. tmpfs never touches the hard drive. That's the point. A decrypted password in tmpfs cannot be recovered from the disk later. Linux only.
COMMANDS
# --- Volume --- $ docker volume create pgdata # Create a named volume. $ docker run -d -v pgdata:/var/lib/postgresql/data postgres:16 # -v NAME:PATH_INSIDE_CONTAINER # No slash at the start of the left side = it's a named volume. $ docker volume ls # list them $ docker volume inspect pgdata # see where it lives on disk $ docker volume rm pgdata # delete it $ docker volume prune # delete all unused ones — CAREFUL, deletes data # --- Bind mount --- $ docker run -it -v "$(pwd)":/app node:20 sh # $(pwd) = your current folder. # A slash or ./ or $(pwd) on the left = it's a bind mount. # Edit a file on your laptop, it changes inside the container instantly. # --- tmpfs --- $ docker run -d --tmpfs /app/cache:size=64m myapp # Lives in RAM, capped at 64MB, gone when the container stops. # --- Check what a container has mounted --- $ docker inspect mycontainer --format '{{json .Mounts}}' # If this shows [] then you have no volume at all.
IN DOCKER-COMPOSE
services: db: image: postgres:16 volumes: - pgdata:/var/lib/postgresql/data # volume - ./init.sql:/docker-entrypoint-initdb.d/init.sql:ro # bind mount, read-only volumes: pgdata: # you must declare named volumes down here
SAY THIS

"Bind mounts for development, named volumes for production data, tmpfs for secrets."

"Volumes are managed by Docker and portable. Bind mounts depend on the host's folder layout, so they break when you move machines."

"A bind mount hides whatever was at that path. An empty volume gets filled from the image instead."
volume = Docker-managedbind = host pathtmpfs = RAM onlybind hides, volume fills
D6How do containers communicate with each other?▼
ANSWER
SHORT ANSWER
Put them on the same user-defined network, then use the container name as the hostname.
EXPLAIN IT SIMPLY
Containers are computers on a small private office network. If two computers are plugged into the same switch, they can talk. If they're on different switches, they can't. That's it.
And Docker runs a little phone book on that network: type the container's name, get its address. So your app connects to postgres://db:5432 and db is just the other container's name.
THE ONE THING THAT TRIPS EVERYBODY UP
The default network has no phone book. Docker gives you a network called bridge out of the box. Container names do not resolve on it. You have to create your own network for name lookup to work.
$ docker network create app-net # creates a network WITH the phone book
This single fact explains most "my containers can't talk to each other" tickets.
THE NETWORK TYPES
TypeWhat it isWhen to use
default bridgeThe one you get for free. No name lookup.Try not to
user-defined bridgeThe one you make. Name lookup works.Normal apps. Use this.
hostContainer shares the computer's network directlyMax speed, no isolation
noneNo network at allIsolated batch jobs
overlaySpans several machinesClusters (Swarm/Kubernetes)
THE OTHER THING PEOPLE GET WRONG
-p 8080:80 is for reaching a container from outside Docker (your browser). Container-to-container traffic doesn't need -p at all. They just need to be on the same network and use the container's internal port.
COMMANDS
$ docker network create app-net # Make your own network. This is the important step. $ docker run -d --name api --network app-net myapi $ docker run -d --name db --network app-net postgres:16 # Now "api" can connect to postgres://db:5432 # "db" works as a hostname because it's the container's --name. $ docker network connect app-net some-container # Add an already-running container to a network. $ docker network inspect app-net # See the network's address range and which containers are on it. # --- Testing --- $ docker exec -it api ping -c 3 db $ docker exec -it api getent hosts db # getent hosts = "can I look up this name?" Proves the phone book works. $ docker exec -it api nc -zv db 5432 # nc -z = "is this port open?" -v = show me. Proves the connection works. # Testing these two separately tells you exactly which part is broken.
DOCKER-COMPOSE DOES THIS FOR YOU
services: api: build: . environment: DATABASE_URL: postgres://user:pass@db:5432/app # "db" is the service name db: image: postgres:16
Compose automatically creates a network and registers every service name as a hostname. Nothing extra to do.
SAY THIS

"Same user-defined network, then use the container name. Docker's built-in DNS handles the rest."

"The default bridge network has no DNS, which is why container names don't resolve there. I always create a user-defined network."

"Published ports are for the outside world. Containers talking to each other use the internal port and don't need -p."
same network + namedefault bridge has no DNS-p is for outside traffic only
D7CMD vs ENTRYPOINT — what's the difference, and can they work together?▼
ANSWER
SHORT ANSWER
ENTRYPOINT is the program. CMD is its default arguments. Yes, they work together, and that's the recommended way.
EXPLAIN IT SIMPLY
Think of a coffee machine. ENTRYPOINT = the machine itself. It makes coffee. That's fixed. CMD = the default setting, say "medium, one sugar."
Press the button with no input → medium, one sugar. Press it and say "strong, no sugar" → you get strong with no sugar. Still coffee. The machine didn't change.
If you'd only set a CMD with no ENTRYPOINT, saying "make me toast" would actually replace the whole machine with a toaster.
CMD ON ITS OWN
CMD ["nginx", "-g", "daemon off;"]
$ docker run myimage # runs nginx $ docker run myimage bash # runs bash — CMD is COMPLETELY REPLACED
CMD is easy to override. That's the point of it.
ENTRYPOINT ON ITS OWN
ENTRYPOINT ["ping"]
$ docker run myimage google.com # runs: ping google.com
The argument gets added on the end, not swapped in. To replace ENTRYPOINT you have to be explicit:
# This is your most useful debugging flag. Remember it. $ docker run --entrypoint sh -it myimage
BOTH TOGETHER (the recommended pattern)
ENTRYPOINT ["ping", "-c", "3"] CMD ["localhost"]
You typeWhat actually runs
docker run imgping -c 3 localhost
docker run img google.comping -c 3 google.com
docker run --entrypoint sh -it imgsh
Real example:
ENTRYPOINT ["java", "-jar", "/app/app.jar"] CMD ["--spring.profiles.active=prod"] # Runs prod by default. Pass a different profile to override.
SQUARE BRACKETS VS PLAIN TEXT — THE IMPORTANT BIT
CMD ["node", "server.js"] # bracket form — USE THIS CMD node server.js # plain form — becomes /bin/sh -c "node server.js"
Why it matters: when you run docker stop, Docker sends a polite "please shut down" signal to the main program, waits 10 seconds, then force-kills it.
• Bracket form: your app is the main program. It gets the signal. It closes database connections, finishes the current request, exits cleanly.
• Plain form: /bin/sh is the main program. sh does not pass the signal on. Your app never hears it. After 10 seconds Docker force-kills everything. Dropped requests, half-written files, unclosed connections.
Bracket form gives you graceful shutdown. Plain form doesn't. (Plain form does let you use $VARIABLES and pipes, which is why RUN normally uses it. But for CMD and ENTRYPOINT, use brackets.)
One gotcha: if ENTRYPOINT is written in plain form, CMD is ignored entirely.
THE ENTRYPOINT-SCRIPT PATTERN (common in real images)
COPY entrypoint.sh /usr/local/bin/ RUN chmod +x /usr/local/bin/entrypoint.sh ENTRYPOINT ["/usr/local/bin/entrypoint.sh"] CMD ["node", "server.js"]
#!/bin/sh set -e # Stop immediately if anything fails. # Do setup first: wait for the database, run migrations until nc -z "$DB_HOST" 5432; do echo "waiting for db"; sleep 1; done npm run migrate exec "$@" # exec = replace this script with the real command, so your app becomes the # main program and receives shutdown signals properly. # "$@" = whatever CMD said (or whatever you typed after docker run).
That exec "$@" line is a detail interviewers notice.
SAY THIS

"CMD sets easily-overridden defaults. ENTRYPOINT sets what always runs. Together: ENTRYPOINT is the program, CMD is its arguments."

"I always use the bracket form, because with the plain form /bin/sh becomes the main process and never passes the shutdown signal to the app. docker stop turns into a force-kill."

"--entrypoint sh is my go-to flag when an image won't start and I need to look inside."
ENTRYPOINT = programCMD = default argsbracket form for graceful shutdown--entrypoint sh to debug
D8How do you pass secrets to a container securely?▼
ANSWER
SHORT ANSWER
Inject them when the container runs. Never build them into the image.
EXPLAIN IT SIMPLY
An image is like a photocopy that gets handed around. Everyone who has the image has everything inside it, forever, including deleted files (remember the layers). So a password written into the image is a password you've published.
WHAT NOT TO DO
ENV DB_PASSWORD=supersecret # visible via docker inspect ARG API_KEY # visible via docker history COPY .env /app/.env # baked into a layer permanently RUN echo $TOKEN > /root/.netrc # still in the layer even if you delete it later
You can prove it in one line:
$ docker history --no-trunc myimage | grep -i secret
WHAT TO DO — AT BUILD TIME
If you need a private token while building (private npm registry, private git repo), use a BuildKit secret. It exists only during that one command and is never saved into any layer.
# syntax=docker/dockerfile:1 RUN --mount=type=secret,id=npmtoken \ NPM_TOKEN=$(cat /run/secrets/npmtoken) npm ci
$ docker build --secret id=npmtoken,src=$HOME/.npmtoken -t app .
WHAT TO DO — AT RUN TIME (better to best)
1. --env-file — better than typing -e PASSWORD=x, because that ends up in your shell history and in ps output.
$ docker run --env-file ./prod.env myapp
2. Mount it as a file, read-only — better than an environment variable.
$ docker run -v /host/secrets/db_pass:/run/secrets/db_pass:ro myapp
Why files beat environment variables: environment variables are inherited by every child process, and they get scooped up by crash reporters and logging tools. Files don't.
3. Docker/Kubernetes secrets — encrypted at rest, delivered over TLS, appear as files at /run/secrets/.
$ echo "s3cr3t" | docker secret create db_password - $ docker service create --secret db_password myapp
4. A secrets manager — the real production answer. HashiCorp Vault, AWS Secrets Manager, Azure Key Vault. The app fetches its password at startup using a short-lived identity. Central rotation, audit logs, instant revocation.
THE _FILE CONVENTION
The official Postgres, MySQL and Redis images accept a path instead of a value:
environment: POSTGRES_PASSWORD_FILE: /run/secrets/db_password
Naming this pattern scores points.

"Secrets are injected at runtime, never baked into the image. Anything in ENV or ARG shows up in docker history or docker inspect."

"For build-time secrets I use BuildKit's --mount=type=secret, which exists only for that one command and never persists to a layer."

"I prefer mounting secrets as files rather than environment variables, because env vars get inherited by child processes and picked up by crash reporters."

"In production the real answer is a secrets manager with rotation, not files in a repo."

D10How do you troubleshoot a container that keeps restarting?▼
ANSWER
SHORT ANSWER
Two things are happening: the app keeps crashing, and a restart policy keeps bringing it back. Fix the crash. The restart is just the symptom.
EXPLAIN IT SIMPLY
Imagine a car that stalls, and you've set it to auto-restart. It stalls, restarts, stalls, restarts. Turning off the auto-restart doesn't fix the car. It just lets you look under the bonnet in peace.
HOW TO WORK THROUGH IT
1. Confirm it's actually looping. docker ps shows "Restarting (1) 3 seconds ago". Check if the restart count is climbing.

2. Read the logs. They survive across restarts, so you can see what it said before it died.

3. Check the exit code and the out-of-memory flag. Exit 137 plus OOMKilled: true means it hit a memory limit. That's a different problem from a crash.

4. Check the health check. A health check that points at the wrong port will restart a perfectly healthy app forever.

5. Check its dependencies. Very common: the app starts before the database is ready, can't connect, exits. Then restarts, and the database still isn't ready.

6. Stop the loop so you can work. Turn off the restart policy and start the app manually.
COMMANDS
$ docker ps # STATUS says "Restarting (1) 5 seconds ago" — that's your confirmation. $ docker inspect mycontainer --format \ 'restarts={{.RestartCount}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' # One line with the three facts you need. $ docker logs --tail 200 mycontainer $ docker logs -f mycontainer # -f = keep watching, so you catch the next crash live. $ docker inspect mycontainer --format '{{json .State.Health}}' # Shows the last few health check results and their output. # Often reveals a check hitting the wrong port. $ docker update --restart=no mycontainer # Turn off auto-restart on a RUNNING container without recreating it. # Now it stays dead and you can investigate. $ docker events --filter container=mycontainer # Live feed of what the container is doing: die, restart, oom. $ docker stats --no-stream mycontainer # Is memory pinned at the limit right before each death?
RESTART POLICIES
--restart=no # never restart (default) --restart=on-failure:5 # restart only on a crash, max 5 tries --restart=always # always restart --restart=unless-stopped # always, but respect a manual docker stop
SAY THIS

"Restarting is the symptom. The crash is the disease. I check the restart count, exit code, and out-of-memory flag first."

"137 with OOMKilled means a memory limit — either raise it or fix the leak. A clean app error usually means bad config or a dependency that isn't ready."

"docker update --restart=no stops the loop so I can inspect it properly."

"In compose, depends_on alone only waits for the container to start, not to be ready. I use a health check with condition: service_healthy."

D11The app runs inside the container but I can't reach it in the browser.▼
ANSWER
SHORT ANSWER
Check three things in order: is the app listening on 0.0.0.0, is the port published with -p, and is anything blocking it on the host.
EXPLAIN IT SIMPLY
There are three doors between your browser and the app. Test them one at a time instead of guessing.
Browser → [door 3: host firewall] → [door 2: -p port mapping] → [door 1: app listening] → App
Work from the app outwards.
DOOR 1 — IS THE APP LISTENING ON THE RIGHT ADDRESS? (the #1 cause)
This is the single most common cause. The app is bound to 127.0.0.1. Inside a container, 127.0.0.1 means "only this container." Nothing outside can ever reach it, no matter how many ports you publish. It must bind to 0.0.0.0, which means "accept from anywhere."
$ docker exec -it mycontainer sh -c "ss -lntp" # Look for 0.0.0.0:3000 ← good # vs 127.0.0.1:3000 ← this is your bug
Fixes by language:
• Node/Express: app.listen(3000, '0.0.0.0')
• Flask: flask run --host=0.0.0.0
• Django: runserver 0.0.0.0:8000
• Spring: server.address=0.0.0.0
Then check it responds from inside:
$ docker exec -it mycontainer curl http://localhost:3000/ # If this fails, the problem is your app, not Docker. Stop and fix the app.
DOOR 2 — IS THE PORT PUBLISHED, IN THE RIGHT DIRECTION?
$ docker port mycontainer # Shows the actual mapping, e.g. 3000/tcp -> 0.0.0.0:8080
Things to check:
• -p HOST:CONTAINER — the order confuses everyone. -p 8080:3000 means browser uses 8080, container receives 3000.
• Empty PORTS column? You forgot -p entirely.
• EXPOSE doesn't publish anything. It's a note. You still need -p.
• --network host means -p is ignored completely.
DOOR 3 — IS THE HOST BLOCKING IT?
$ curl -v http://localhost:8080/ # Works here but not in the browser? → browser cache, or http vs https, or wrong URL. # Doesn't work here? → firewall, security group, or nothing is listening.
Check: ufw/firewalld on the machine, AWS Security Groups, Azure NSG. Also: on a remote server, localhost means your laptop, not the server. Use the server's IP.
FULL DEBUG SEQUENCE
$ docker ps # is it running? what's in PORTS? $ docker port mycontainer # exact mapping $ docker logs mycontainer # what address did it say it's listening on? $ docker exec -it mycontainer ss -lntp # 0.0.0.0 or 127.0.0.1? $ docker exec -it mycontainer curl localhost:3000 # healthy from inside? $ curl -v http://localhost:8080 # reachable from the host? $ sudo ss -lntp | grep 8080 # is the host actually listening?
SAY THIS

"First I check whether the app is bound to 0.0.0.0 instead of 127.0.0.1. That's the most common cause by far, because localhost inside a container means only that container."

"Then the port mapping direction: -p host:container. And EXPOSE doesn't publish anything, it's documentation."

"I test one hop at a time — inside the container, then from the host, then from outside — so I know exactly which layer is broken."

D13A container can't reach another container. What do you check?▼
ANSWER
SHORT ANSWER
Same network first, then whether the name resolves, then whether the port is open.
EXPLAIN IT SIMPLY
Three separate questions, and you must test them separately or you'll be guessing:
1. Are they plugged into the same switch? (same network)
2. Can one find the other's address? (DNS)
3. Is the door open when it gets there? (port)
Test them individually and the answer falls out.
THE CHECKLIST
1. Same network? (right about 70% of the time)
$ docker inspect container1 --format '{{json .NetworkSettings.Networks}}' $ docker inspect container2 --format '{{json .NetworkSettings.Networks}}'
2. Is it the default bridge? The default bridge network has no DNS. Container names simply don't work there. Make your own network.
$ docker network create app-net $ docker network connect app-net container1 $ docker network connect app-net container2
3. Right hostname? It's the container's --name, or in compose, the service name.
4. Does the name resolve?
$ docker exec -it container1 getent hosts container2 # Works → DNS is fine, move to the port. # Fails → go back to steps 1 and 2.
5. Is the port open, and is the target bound to 0.0.0.0?
$ docker exec -it container1 nc -zv container2 5432 $ docker exec -it container2 ss -lntp
Same trap as door 1 above. A database bound to 127.0.0.1 inside its own container can't be reached by anyone else.
6. Right port number? Between containers you use the internal port (5432), not the published one. -p 5433:5432 doesn't change the internal port.
7. Using localhost by mistake? DATABASE_URL=postgres://localhost:5432 means "the app container itself." Extremely common when moving code from a laptop into Docker. It has to be the other container's name.
8. Is the target even up? docker ps. It might be restarting, or just not ready yet.
THE BEST DEBUGGING TRICK
If your image is minimal and has no tools inside:
$ docker run --rm -it --network container:myapp nicolaka/netshoot # This borrows myapp's exact network, but gives you a container full of # network tools: dig, curl, tcpdump, ss, nmap. # You're now debugging from inside your app's network with real tools.
SAY THIS

"Then I separate name resolution from connectivity — getent hosts proves DNS, nc -zv proves the port. Knowing which one failed tells me exactly where to look."

"And I check the app isn't pointed at localhost, because inside a container localhost is that container, not its neighbour."

D15"No space left on device". How do you fix it?▼
ANSWER
SHORT ANSWER
Check disk and inodes, see what Docker is holding with docker system df, then clean up from safest to most destructive.
EXPLAIN IT SIMPLY
Docker never throws anything away on its own. Every image you ever built, every stopped container, every volume, every log file — it all just accumulates until the disk is full.
STEP 1 — CHECK WHAT'S ACTUALLY FULL
$ df -h # disk space $ df -i # INODES
Don't skip df -i. An inode is a slot for a file. You can have plenty of free GB but zero free inodes, and you get the exact same error message. Docker creates millions of tiny files, so this happens. Mentioning it in an interview is a nice touch.
STEP 2 — SEE WHAT DOCKER IS HOLDING
$ docker system df
TYPE TOTAL ACTIVE SIZE RECLAIMABLE Images 42 5 18.2GB 15.1GB (82%) Containers 18 3 2.1GB 1.9GB Local Volumes 23 4 31.4GB 28.0GB Build Cache - - 12.7GB 12.7GB
$ docker system df -v # -v = itemised. Every single image, container and volume with its own size. # This is how you find the one 40GB volume nobody knew about.
STEP 3 — THE FOUR USUAL CULPRITS
1. Old images — every rebuild orphans the previous one
2. Unused volumes — docker rm does not delete volumes. They pile up silently and are often the biggest item.
3. Build cache — grows without limit
4. Container logs — the one everyone forgets
About the logs: Docker's default log setup has no rotation. A chatty app writes to one file forever. 100GB log files are a real thing.
$ sudo du -sh /var/lib/docker/containers/* | sort -rh | head # Ranks containers by log size. Often the smoking gun.
STEP 4 — CLEAN UP, SAFEST FIRST
$ docker container prune # Removes stopped containers. Safe. $ docker image prune # Removes untagged leftover images. Safe. $ docker image prune -a # Removes every image not currently in use. You'll have to re-download them. $ docker builder prune # Clears build cache. Safe. $ docker volume prune # ⚠️ THIS DELETES DATA. Check docker volume ls first. $ docker system prune # Containers + networks + unused images + build cache. $ docker system prune -a --volumes # ⚠️ THE NUCLEAR OPTION. Everything not in use, including your databases. # Never run this in production without checking docker system df -v first.
STEP 5 — STOP THE LOGS COMING BACK
Edit /etc/docker/daemon.json:
{ "log-driver": "json-file", "log-opts": { "max-size": "10m", "max-file": "3" } }
$ sudo systemctl restart docker # Now each container is capped at 3 files × 10MB = 30MB.
Note: this only affects newly created containers. To empty a huge log right now:
$ sudo truncate -s 0 /var/lib/docker/containers/<id>/<id>-json.log # Empties the file in place. # Do NOT use rm — Docker keeps writing to the deleted file and you get no space back.
STEP 6 — PREVENT IT
• Weekly cron: docker system prune -af --filter "until=168h" (only things older than 7 days)
• Set up log rotation as part of every new server's setup
• Send logs somewhere central instead of leaving them on disk
• Alert at 80% disk, before it becomes an outage
SAY THIS

"I check df -h and df -i — inode exhaustion gives the identical error and catches people out."

"Then docker system df -v to see where it went. The four usual suspects are old images, unused volumes, build cache, and unrotated logs."

"Logs are the one people forget. The default driver never rotates, so I set max-size and max-file in daemon.json as standard server setup."

"I prune from safest to most destructive, and I never run system prune -a --volumes in production without checking what's in those volumes first."

D16Why is my data gone after restarting the container?▼
ANSWER
SHORT ANSWER
Because it was never saved anywhere permanent. And usually you didn't restart the container, you replaced it with a new one.
EXPLAIN IT SIMPLY
Remember the stack of sheets from D1? The container's blank top sheet is where all its writing goes. Delete the container, the sheet goes in the bin.
FIRST, WORK OUT WHAT ACTUALLY HAPPENED
This distinction is the mark of someone who has actually done this:
What you didData
docker stop then docker startSurvives. Same container, same sheet.
docker rm then docker runGone. New container = brand new blank sheet.
docker run againGone. You made a new container, you didn't restart the old one.
docker compose downContainers deleted. Named volumes survive.
docker compose down -v-v deletes the volumes too. Real data loss.
So most of the time the answer is: you didn't restart it, you recreated it, and the data only ever lived on the disposable sheet.
IF YOU DO HAVE A VOLUME AND IT'S STILL NOT WORKING
1. Wrong path. The volume is fine, but the app writes somewhere else. Each database has a specific folder:
• Postgres → /var/lib/postgresql/data
• MySQL → /var/lib/mysql
• MongoDB → /data/db
• Redis → /data (and Redis needs appendonly yes, otherwise it's memory-only by design)
2. Anonymous volume. -v /var/lib/postgresql/data with no name creates a brand new unnamed volume every single run. You need -v pgdata:/var/lib/postgresql/data.
3. The --rm flag. docker run --rm deletes the container and its anonymous volumes on exit. Easy to leave in from testing.
4. Permissions. The container's user can't write to the folder, so the app fails silently or writes somewhere temporary. Check ls -la inside.
5. Compose renamed the volume. Compose names volumes after the project folder. Rename the folder, and you're now pointing at a different, empty volume.
HOW TO CHECK
$ docker inspect mycontainer --format '{{json .Mounts}}' # The definitive answer. # If it prints [] → you have no volume at all. That's your bug. # Otherwise check that "Destination" matches where the app actually writes. $ docker volume ls # Seeing lots of long unnamed hashes? Those are anonymous volumes piling up. # Prove the volume works with a test file: $ docker exec mycontainer sh -c 'echo test > /var/lib/postgresql/data/canary.txt' $ docker restart mycontainer $ docker exec mycontainer cat /var/lib/postgresql/data/canary.txt # Survives → the volume works, so the app is writing somewhere else.
THE FIX
$ docker volume create pgdata $ docker run -d --name db \ -v pgdata:/var/lib/postgresql/data \ -e POSTGRES_PASSWORD=secret \ postgres:16
services: db: image: postgres:16 volumes: - pgdata:/var/lib/postgresql/data volumes: pgdata: # declaring it here makes it a NAMED volume that persists
BONUS: HOW TO BACK UP A VOLUME
$ docker run --rm -v pgdata:/data -v $(pwd):/backup alpine \ tar czf /backup/backup.tar.gz -C /data . # Starts a throwaway container with both the volume and your current folder # attached, then zips the volume contents into your folder.
SAY THIS

"Containers are disposable by design. The writable layer dies with the container, so anything you want to keep has to be in a volume."

"First I check whether they restarted it or recreated it. stop/start keeps the data; rm + run doesn't."

"Then docker inspect --format '{{json .Mounts}}'. If Mounts is empty there's no volume. If it's there, I check the path matches where the app actually writes."

"Watch out for anonymous volumes and --rm — both give you a fresh empty volume on every run."

D17A container is using too much CPU or memory. How do you troubleshoot?▼
ANSWER
SHORT ANSWER
docker stats to see it, docker top to find the process, then check whether it was killed for memory and whether limits are set.
STEP 1 — SEE IT
$ docker stats # Live view: CPU%, memory used / limit, network, disk, number of processes. $ docker stats --no-stream # One snapshot instead of a live view. Better for copying into a ticket.
Read CPU% correctly. It's per core. On an 8-core machine, 400% means four cores are fully busy, and 800% is the maximum. People see 200% and think the tool is broken.
Watch the PIDS column. If the process count keeps climbing, you have a thread or process leak, and that's usually the actual bug.
STEP 2 — FIND THE CULPRIT PROCESS
$ docker top mycontainer # Lists the processes inside. Works even on minimal images with no shell. $ docker exec -it mycontainer ps aux --sort=-%mem | head # Heaviest memory users first.
STEP 3 — WAS IT KILLED FOR MEMORY?
$ docker inspect mycontainer --format '{{.State.OOMKilled}} {{.State.ExitCode}}' # true and 137 = the system killed it for exceeding its memory limit. $ dmesg -T | grep -i "killed process" # The system log confirming it, with the exact memory usage at the moment it died.
STEP 4 — ARE LIMITS EVEN SET?
$ docker inspect mycontainer --format 'mem={{.HostConfig.Memory}} cpus={{.HostConfig.NanoCpus}}' # 0 means unlimited. # An unlimited container can eat the whole machine and take down its neighbours.
STEP 5 — IS IT A LEAK OR JUST UNDER-PROVISIONED?
The shape of the graph tells you:
• Memory climbs steadily and never comes down → a leak. You need a heap dump or profiler.
• Memory is high but flat → the app just needs more memory. Raise the limit.
• CPU pinned at 100% → an infinite loop, a slow database query being retried, or garbage collection struggling.
Profilers: Java jcmd GC.heap_dump, Node --inspect, Python tracemalloc, Go pprof.
THE CLASSIC CONTAINER GOTCHA WORTH MENTIONING
Older Java versions ignored the container's memory limit and sized the heap based on the whole machine's RAM. Give a 512MB container to a JVM on a 32GB server and it tries to use an 8GB heap, then gets killed instantly.
Fix: -XX:MaxRAMPercentage=75. (-XX:+UseContainerSupport is on by default from Java 10.) Same problem exists elsewhere: libraries that count CPUs and size their thread pool from the host's core count, not the container's share.
STEP 6 — SET LIMITS
$ docker run -d --memory 512m --memory-swap 512m --cpus 1.5 myapp # --memory = hard limit; going over gets it killed # --memory-swap = memory + swap combined. Setting it EQUAL to --memory turns swap off, # which you want — swap hides leaks and destroys performance. # --cpus 1.5 = at most one and a half cores $ docker update --memory 1g --memory-swap 1g mycontainer # Change the limit on a running container without recreating it.

D18What are the first commands you run in a production incident?▼
ANSWER
SHORT ANSWER
docker ps -a → docker logs → docker stats → docker inspect. Broad to narrow: what's running, what did it say, is it starved, why did it die.
EXPLAIN IT SIMPLY
Think of it like a doctor. Look at the patient, ask what happened, check the vital signs, then run the specific test. You don't start with the specific test.
THE SEQUENCE
# 1 — What's running, what isn't, what's flapping $ docker ps -a # The STATUS column tells you immediately: "Up 3 days", "Exited (137)", # or "Restarting (1)". That one column often solves it. # 2 — What did it say before it broke $ docker logs --tail 200 --timestamps mycontainer $ docker logs -f --since 10m mycontainer # --since 10m narrows a noisy log down to the incident window. # 3 — Is anything starved $ docker stats --no-stream # Instant read on CPU and memory across everything. # 4 — Why exactly did it stop $ docker inspect mycontainer --format \ 'status={{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}} restarts={{.RestartCount}}' # Four facts on one line. These classify almost any container failure. # 5 — Get inside and look $ docker exec -it mycontainer sh $ docker exec -it mycontainer sh -c 'ps aux; df -h' # 6 — Is the disk full (the silent killer) $ df -h && df -i $ docker system df # 7 — Timeline of what happened $ docker events --since 30m # Everything the daemon did: starts, deaths, out-of-memory kills, health changes. # Great for lining up with when the alert fired. # 8 — Did someone deploy? $ docker inspect mycontainer --format '{{.Config.Image}}' # "Was anything changed" is the answer more often than you'd think.
BEFORE YOU FIX ANYTHING, SAVE THE EVIDENCE
$ docker logs mycontainer > /tmp/incident.log $ docker inspect mycontainer > /tmp/incident.json $ docker commit mycontainer incident-snapshot # docker commit saves the container's exact filesystem as an image, so you # can investigate later, after you've restarted the service and fixed the customer.
Restarting destroys everything you need for the postmortem. Capture first.
SAY THIS

"docker ps -a → docker logs → docker stats → docker inspect. Broad to narrow: what's running, what did it say, is it starved, why did it die."

"I capture evidence before I fix — logs, inspect output, and a docker commit snapshot — because restarting destroys the state I need for the postmortem."

"I don't run any prune commands during an incident. Fix first, clean up later once I know the cause."

"In real life I'd be looking at central logging and dashboards first. These are the commands for when I actually need to be on the machine."
