📦 The Daily Git Workflow
A change you make never jumps straight into permanent history. It always passes through three boxes, in this exact order:
Working Directory → Staging Area → Repository (you edit a file) (git add) (git commit)
Important: "committed" means it's in the Repository box. "Staged" means it's only in the middle box, waiting. These are two different boxes with two different contents — that single fact is the whole workflow below.
git statusinspect
Shows the difference between all three boxes right now. Run it before every single command below — it tells you exactly what state you're in.
M = modified, A = staged, ?? = untracked (git doesn't know this file yet).
$ git status -s M src/auth.js ?? notes.txt
git addstage
Copies a change from the Working Directory into the Staging Area. Nothing is saved permanently yet — you can still change your mind.
Before: Working Dir = new edit, Staging = old, Repo = old After: Working Dir = new edit, Staging = new edit, Repo = old
$ git add .  # stage everything $ git add -p  # review each chunk first
git commitsnapshot
Takes everything sitting in the Staging Area and turns it into a permanent commit. Git does this in order: look at HEAD → find the current branch → create the new commit → move that branch to point at it.
Before: main → C1 After: main → C2 (C2 is the new commit; C1 still exists behind it)
$ git commit -m "feat: add JWT auth"
git pushupload
Copies your local commits to a second copy of the repository living somewhere else — almost always GitHub, under the name origin.
Always name the branch, so you know exactly what you're sending.
$ git push origin feature/auth
git loghistory
Lists every commit in the Repository box, newest first — the full chain: C0 ← C1 ← C2 ← ... --oneline shows one short line per commit instead of the full message.
$ git log --oneline a3f9d2c feat: add JWT auth b1e8c4a fix: null check on login
git checkout <hash>time travel
Moves HEAD to point directly at an old commit instead of a branch.
Before: HEAD → main After: HEAD → a3f9d2c (a specific commit, not a branch)
Important: this is "detached HEAD." Committing here creates commits that nothing points to. git checkout main gets you back.
$ git checkout a3f9d2c  # go back $ git checkout main    # come back
🔄 fetch vs pull vs merge vs rebase
git fetch
Downloads new commits from the remote. Updates a label called origin/main to point at them.
Before: origin/main → C2 (old) After: origin/main → C4 (updated)
Your own files never move. Your own main branch never moves. Only that one remote-tracking label changes.
git pull
Exactly git fetch, immediately followed by git merge (or rebase, if you've configured that). This time your own branch DOES move — it's fetch, then one more step.
git merge
Combines two branches back into one.
If main didn't move (fast-forward): main → C4 (just slides forward, nothing new) If main ALSO has new commits: git creates a new commit C6 with TWO parent arrows — one to each side
git rebase
Takes your branch's commits OFF, and replays them as brand new commits on top of another branch.
Before: feature: C0→C1→C2→C3→C4 main: C0→C1→C2→C5 After: C0→C1→C2→C5→C3'→C4'
C3 and C4 aren't moved — C3' and C4' are new commits with new IDs. ⚠️ Never rebase a branch someone else already has a copy of.
🛠️ Fixing & Undoing Things
To actually understand reset, you need to know exactly what's sitting in each of the three boxes. Walk through this slowly:
Step 1 — commit "Hello"
git add app.js git commit -m "C1"
State: Working Directory = Hello · Staging Area = Hello · Repository = Hello
Step 2 — edit the file, add "Git" (no add, no commit yet)
State: Working Directory = Hello + Git · Staging Area = Hello · Repository = Hello
Step 3 — git add app.js
State: Working Directory = Hello + Git · Staging Area = Hello + Git · Repository = Hello
Step 4 — git commit -m "C2"
State: Working Directory = Hello + Git · Staging Area = Hello + Git · Repository = Hello + Git
Now reset actually makes sense — each flavor undoes the commit, but stops touching the boxes at a different point:

--soft → moves the branch pointer back. Staging Area untouched. Working Directory untouched.
--mixed → moves the branch pointer back, AND clears the Staging Area. Working Directory untouched.
--hard → moves the branch pointer back, clears the Staging Area, AND resets the Working Directory to match.

None of them delete the commit. C2 still exists in the Repository — reset only changes which commit your branch points to. git reflog finds it again if you need it.
git stashshelve work
Takes whatever's in the Working Directory and Staging Area right now, sets it aside, and resets both boxes to match the last commit — without creating a commit. git stash pop puts it all back exactly as it was.
$ git stash    # save WIP $ git stash pop  # restore it
git reset --soft HEAD~1undo commit
Moves your branch back one commit. Staging Area and Working Directory stay exactly as they were — nothing is lost, the commit just isn't "official" anymore.
$ git reset --soft HEAD~1  # safe undo
git revert <hash>safe undo
Creates a brand NEW commit that does the exact opposite of an old one. The old commit is still right there in history — nothing is removed or rewritten.
Before: C0→C1→C2 After: C0→C1→C2→C3 (C3 undoes C2)
Safe on shared branches, because history only grows — it never gets rewritten.
$ git revert a3f9d2c  # adds undo commit
git restore <file>discard changes
Resets ONE file in the Working Directory back to match the last commit. Cannot be undone — whatever wasn't committed is simply gone.
$ git restore src/auth.js  ⚠️
git remoteremotes
Lists the other copies of this repository git knows about. origin is just a name — the default name for whichever remote you cloned from.
$ git remote -v origin https://github.com/you/repo.git
⚔️ Merge Conflicts
A merge tries to combine two branches automatically, line by line. A conflict happens on exactly one condition: the same line was changed to two different things on each side. Git genuinely cannot guess which one you want — so it stops and shows you both.

What to do, in order:
1. Open the file. Git has marked exactly where the conflict is:
<<<<<<< HEAD
your version
=======
their version
>>>>>>> feature/their-branch
2. Delete the <<<<<<< / ======= / >>>>>>> lines, and keep only whichever version (or combination) is actually correct.
3. git add the file — this tells git "the conflict here is resolved."
4. git commit (or git merge --continue) — this finishes the merge you were already doing.

💬 Talk to whoever wrote the other side — a conflict usually means two people had genuinely different ideas about the same piece of code, which is worth a real conversation.
🔀 Pull Requests (PRs)
A Pull Request is not a git command at all — git doesn't even know what one is. It's a GitHub (or GitLab) feature layered on top: a request that says "please merge my branch into main."

Opening one gives your teammates a chance to read the change before it becomes permanent. They can comment, ask for changes, or approve. Automated checks (tests, CI) run on it too — if those fail, the PR usually can't merge.

The full path: new branch → commits → push → open PR → review + checks pass → merge into main → pipeline deploys it
🌿
The Git DevOps Workflow
git status → git add . → git commit -m "feat: ..." → git push origin feature/x → open PR → CI runs → review → merge → deploy
🔍 Advanced Git
git reflogHEAD history
git log only shows the commits your current branch can currently reach. git reflog shows something different: every place HEAD has ever pointed — including commits a reset or rebase left behind. Nothing you "lost" is actually gone. Find the hash here, then git checkout -b recovery <hash> to get it back.
$ git reflog a3f9d2c HEAD@{0}: commit: feat: auth b1e8c4a HEAD@{1}: reset: moving to HEAD~1 c9d7f3a HEAD@{2}: checkout: moved to main
clone vs forkcopy a repo
git clone — makes a local copy on your own machine. Your origin points at the SAME remote everyone else on the team uses. For repos you already have write access to.

Fork (a GitHub feature, not a git command) — makes your own separate copy of the whole repo, under your account. You commit there freely, then open a PR from your fork back to the original. For contributing to a project you don't have write access to.
clone = local copy, same origin fork = your own GitHub copy → PR back
🪝 Git Hooks
A hook is just a script sitting in .git/hooks/ that git runs automatically at one specific moment. Nothing magic — it's your own shell script, triggered for you. Share them across a team with a tool like Husky, so everyone's hooks match.
CLIENT-SIDElocal machine
pre-commit — runs right before a commit is created. If the script exits with an error, the commit is blocked. Used for linters and fast checks.

commit-msg — checks the commit message itself. Used to require a format like feat: or fix:.

pre-push — runs right before git push. The last local checkpoint before code leaves your machine.
#!/bin/sh npm run lint && npm test
SERVER-SIDEremote / GitHub
pre-receive — runs on the SERVER, before it accepts an incoming push. Can reject a push outright — e.g. blocking anyone from pushing directly to main.

post-receive — runs after the push is already accepted. Used to kick off a CI/CD pipeline or send a notification.

On GitHub/GitLab these are called webhooks instead — same idea, delivered as an HTTP request.
🍒 More Essential Git Commands
git cherry-pickcopy a commit
Takes ONE specific commit from another branch and replays it onto your current branch — nothing else from that branch comes with it. Used to apply a hotfix to two places at once without merging everything.
$ git cherry-pick a3f9d2c  # apply that one commit here
git rebase -i HEAD~3squash commits
Opens your last 3 commits in an editable list. Change pick to squash on the ones you want folded into the commit above them. Rewrites those commits — never do this on a branch someone else already has.
$ git rebase -i HEAD~3  # opens an editor
git tagreleases
Marks one exact commit as important — usually a release. Unlike a branch, a tag never moves once created. A pipeline can trigger differently when a tag is pushed vs. a normal commit.
$ git tag -a v2.0 -m "Release v2.0" $ git push origin v2.0
git commit --amendfix last commit
Replaces your last commit with a new one — a fixed message, or forgotten files folded in. Only safe before you've pushed it. Already pushed? Use git revert instead, so you're not rewriting history someone else already has.
$ git commit --amend -m "fixed: better message"
git clean -fdremove untracked
Deletes every file git isn't tracking yet — permanently, no undo. -n first shows you exactly what WOULD be deleted, without deleting anything. Always run -n before the real thing.
$ git clean -n   # dry run first $ git clean -fd  # actually delete
.gitignoreexclude files
A plain list of file patterns git should never track — node_modules/, .env, *.log and similar. It's committed to the repo itself, so the whole team ignores exactly the same files, automatically.
# .gitignore node_modules/ .env *.log .terraform/
⚠️ Dangerous Git Situations — What To Do
SITUATIONHOW TO RECOVER
Accidentally committed a secretThe secret is compromised the moment it's pushed — rotate it first. Then remove it from history with BFG Repo Cleaner or git filter-branch, and force-push the clean version.
Force-pushed and lost commitsThe commits are still there — you just don't have a label pointing at them. git reflog finds the hash, then git checkout -b recovery <hash> brings it back.
git reset --hard (wrong branch)Same idea — reset only moved a pointer, nothing was deleted. git reflog to find where you were before the reset, then git reset --hard <that-hash>.
Monorepo vs PolyrepoMonorepo — every service lives in one repository. One commit can change several services at once. Polyrepo — each service gets its own repository. More independent, but a change spanning two services now needs two separate commits, in two separate repos.
🍒 git cherry-pick — Steal a Single Commit
Copies exactly one commit from one branch onto another — the rest of that branch is never touched. The real use case: a bug fix landed on main, and a release branch needs that exact fix and nothing else new from main.
git cherry-pick a3f9d2c          # copy exactly this one commit here
git cherry-pick a3f9d2c..b1e8c4a   # copy a whole range of commits
git cherry-pick --no-commit a3f9d2c # apply the changes, don't commit yet
🏷️ Git Tags — Semantic Versioning
A tag marks one exact commit as meaningful — usually a release. The one rule that matters: a branch keeps moving forward as you commit; a tag, once created, never moves again. Semantic Versioning: MAJOR.MINOR.PATCH, e.g. v2.1.3. MAJOR = something breaks. MINOR = a new feature, nothing breaks. PATCH = a bug fix, nothing new.
git tag v2.1.0                     # lightweight tag
git tag -a v2.1.0 -m "Release 2.1.0" # annotated tag (recommended)
git push origin v2.1.0                # tags don't push automatically
git tag                              # list every tag

🔀 Squash Commits — Clean History Before Merge
While you're building a feature, your commits are often messy — "wip", "fix typo", "actually fix it". Squashing takes several of those and folds them into one clean commit before the branch merges, so main's history stays readable.

git rebase -i HEAD~5 — opens the last 5 commits as an editable list. Change pick to squash on every commit except the first, and git folds them all into one, letting you write a single clean message.
🧾 Cheatsheet — The Whole Mental Model, Compressed
Everything above, distilled to 11 diagrams. If you understand every one of these, your foundation is solid.
1. A commit is a snapshot
C0 → C1 → C2
Each C is a snapshot of your project at a specific moment. git commit creates a new snapshot.
2. A branch is just a label
C0 → C1 → C2 main → C2
main doesn't contain code. main doesn't contain files. main is just a label that points to a commit.
3. main is a branch too
main → C2
main isn't special. It's just the default branch. You can create as many branches as you want:
main → C2 feature → C2 bugfix → C2
4. Creating a branch doesn't copy anything
git branch feature
Before:
C0 → C1 → C2 main → C2
After:
C0 → C1 → C2 main → C2 feature → C2
No commits were copied. Git only created another label.
5. HEAD tells you which branch you're currently using
HEAD → main or HEAD → feature
HEAD points to a branch. The branch points to a commit.
HEAD → branch → commit
This is probably the most important diagram in Git.
6. git checkout moves HEAD
Before:
HEAD → main main → C2 feature → C2
Command:
git checkout feature
After:
HEAD → feature main → C2 feature → C2
Only HEAD moved. The branches didn't move.
7. git commit creates a new commit and moves the current branch
Before:
C0 → C1 → C2 main → C2 HEAD → main
Command:
git commit
After:
C0 → C1 → C2 → C3 main → C3 HEAD → main
The current branch moved.
8. git merge X
Rule:
git merge X = merge X into the current branch.
Before:
C3 → C4 / C0 → C1 → C2 \ C5 feature → C4 main → C5 HEAD → main
Command:
git merge feature
After:
C3 → C4 / \ C0 → C1 → C2 C6 \ / C5
main moved. feature didn't move.
9. git rebase X
Rule:
git rebase X = take the commits that belong only to the current branch, copy them, rebuild them after X.
Before:
main: C0 → C1 → C2 → C5 feature: C0 → C1 → C2 → C3 → C4 HEAD → feature
Command:
git rebase main
Git copies C3 and C4, then rebuilds them as C3' and C4'. Result:
C0 → C1 → C2 → C5 → C3' → C4'
10. Git has three boxes
Working Directory ↓ Staging Area ↓ Repository
Working Directory — your actual files.
app.js index.html login.js
You edit a file. The change appears here first.
Staging Area
git add app.js
git add copies changes into the staging area. It doesn't move them.
Repository
git commit
Git creates a snapshot. The snapshot becomes a commit.
The complete flow:
Edit file ↓ Working Directory ↓ git add ↓ Staging Area ↓ git commit ↓ Repository
11. git reset
git reset moves the current branch. The current branch is the branch HEAD points to.
git reset --soft
Working Directory = unchanged Staging Area = unchanged Repository = unchanged Branch pointer = moved
git reset --mixed
Working Directory = unchanged Staging Area = cleared Repository = unchanged Branch pointer = moved
git reset --hard
Working Directory = reset Staging Area = cleared Repository = unchanged Branch pointer = moved
