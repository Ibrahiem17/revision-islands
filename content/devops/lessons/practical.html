🐳 Docker — Practical Use Cases
01
Build a Docker Image from a Node.js App
Package your app into a portable image that runs anywhere
Dockerfile
FILE
./Dockerfile
# Use official Node.js 20 base image FROM node:20-alpine # Set working directory inside container WORKDIR /app # Copy package files and install dependencies FIRST (caching!) COPY package*.json ./ RUN npm install # Copy the rest of the source code COPY . . # Expose the port your app listens on EXPOSE 3000 # Command to start the app CMD ["node", "index.js"]
FILE
./.dockerignore
node_modules .git .env *.log
CMD
# Build the image — tag it as myapp:1.0 docker build -t myapp:1.0 . # List images to confirm it was created docker images
OUTPUT
[1/4] FROM docker.io/library/node:20-alpine [2/4] WORKDIR /app [3/4] RUN npm install [4/4] COPY . . => exporting to image => naming to docker.io/library/myapp:1.0 REPOSITORY TAG IMAGE ID SIZE myapp 1.0 a3f8c91b7e2d 185MB
WHY
COPY package*.json + RUN npm install before COPY . . — Docker caches each layer. If you change only app code, npm install layer is reused → much faster rebuilds.
02
Run a Container with Port Mapping & Env Vars
Start your image as a running container, map ports, inject config
docker run
CMD
# Run container: # -d = detached (background) # --name = give it a name # -p 8080:3000 = host:container port map # -e = inject environment variable docker run -d --name my-api -p 8080:3000 -e NODE_ENV=production -e PORT=3000 myapp:1.0 # Check it is running docker ps # View live logs docker logs -f my-api # Stop the container docker stop my-api
OUTPUT
CONTAINER ID NAME STATUS PORTS d7a3b891f2c1 my-api Up 3 seconds 0.0.0.0:8080->3000/tcp Server listening on port 3000 Connected to DB
WHY
-p 8080:3000 means "on my laptop, go to localhost:8080 — it forwards to port 3000 inside the container". The container stays isolated; you only open the ports you need.

04
Push Image to Docker Hub (Registry)
Publish your image so any server or CI pipeline can pull it
push / pull
CMD
# 1. Login to Docker Hub docker login # → prompts for username + password/token # 2. Tag the image with your Docker Hub username # format: username/repo:tag docker tag myapp:1.0 ibrahiem17/myapp:1.0 docker tag myapp:1.0 ibrahiem17/myapp:latest # 3. Push both tags docker push ibrahiem17/myapp:1.0 docker push ibrahiem17/myapp:latest # 4. On any other machine — pull and run it docker pull ibrahiem17/myapp:1.0 docker run -p 8080:3000 ibrahiem17/myapp:1.0
OUTPUT
The push refers to repository [docker.io/ibrahiem17/myapp] 1.0: digest: sha256:a3f8...7e2d size: 1234 latest: digest: sha256:a3f8...7e2d size: 1234
WHY
Always push both a version tag (1.0) and latest. Kubernetes manifests can pin to 1.0 for stability. CI pipelines use latest for dev builds. Never use only latest in production — you can't roll back a tag that moves.
05
Multi-Stage Build — Shrink Production Image
Use a builder stage; copy only the compiled output into a tiny final image
multi-stage
FILE
./Dockerfile
# ── STAGE 1: Builder (has all dev tools + source) ────────── FROM node:20-alpine AS builder WORKDIR /app COPY package*.json ./ RUN npm ci # clean install (faster than npm install in CI) COPY . . RUN npm run build # e.g. compiles TypeScript → dist/ # ── STAGE 2: Production (only the dist/ output) ──────────── FROM node:20-alpine AS production WORKDIR /app COPY package*.json ./ RUN npm ci --omit=dev # no devDependencies in prod COPY --from=builder /app/dist ./dist EXPOSE 3000 CMD ["node", "dist/index.js"]
CMD
docker build -t myapp:prod . docker images | grep myapp
OUTPUT
REPOSITORY TAG IMAGE ID SIZE myapp prod b2d9e44c8f1a 72MB ← production (tiny!) myapp 1.0 a3f8c91b7e2d 185MB ← dev (had all tools)
WHY
Builder stage has compilers, test runners, source code — none of which belongs in production. Multi-stage build keeps the final image lean (smaller attack surface, faster pulls, cheaper ECR storage).
06
Volumes — Persist Data Between Container Restarts
Without a volume, all data inside a container dies when it stops
volumes
CMD
# Create a named volume docker volume create pgdata # Run PostgreSQL mounting the volume to its data dir docker run -d --name mydb -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:16-alpine # Stop and delete the container — data SURVIVES in the volume docker stop mydb && docker rm mydb # Start a NEW container, re-mount same volume — data is back! docker run -d --name mydb-v2 -v pgdata:/var/lib/postgresql/data postgres:16 # Inspect where the volume lives on disk docker volume inspect pgdata
OUTPUT
[ { "Name": "pgdata", "Mountpoint": "/var/lib/docker/volumes/pgdata/_data", "Driver": "local" } ]
WHY
Containers are ephemeral by design — their filesystem is wiped on removal. Named volumes are managed by Docker and live outside the container lifecycle. Always use volumes for databases, uploads, and anything that must survive a restart.

03
Rolling Update — Deploy New Version with Zero Downtime
K8s replaces pods one-by-one; users never see downtime
rolling update
CMD
# Update image to v2.0 — triggers rolling update kubectl set image deployment/myapp myapp=ibrahiem17/myapp:2.0 # Watch the rollout progress kubectl rollout status deployment/myapp # View rollout history kubectl rollout history deployment/myapp # Something wrong? Roll back to previous version instantly kubectl rollout undo deployment/myapp
OUTPUT
Waiting for deployment "myapp" rollout to finish... 1 out of 3 new replicas have been updated... 2 out of 3 new replicas have been updated... deployment "myapp" successfully rolled out # After undo: deployment.apps/myapp rolled back
WHY
K8s won't terminate old pods until new ones are Ready. If the new pod fails health checks, the rollout pauses automatically — your old pods keep serving traffic. This is why you always define readinessProbe in production.

05
Exec into a Running Pod — Debug Live Issues
SSH-equivalent for Kubernetes — get a shell inside any running container
debug
CMD
# Get pod name kubectl get pods # Open a shell INSIDE the pod (like SSH) kubectl exec -it myapp-79f8b9d5c-4pqx7 -- sh # Inside the container now — debug freely: # ls /app check files # cat /app/.env check injected env file # curl localhost:3000/health test the API locally # env | grep NODE check env vars # exit leave the shell # Stream live logs from a specific pod kubectl logs -f myapp-79f8b9d5c-4pqx7 # Describe pod — see events, errors, resource usage kubectl describe pod myapp-79f8b9d5c-4pqx7
OUTPUT
/app # ← you are INSIDE the container now $ curl localhost:3000/health {"status":"ok","db":"connected"} $ env | grep NODE NODE_ENV=production
WHY
CrashLoopBackOff? exec won't work (container keeps dying). Use: kubectl logs myapp-xxx --previous to see logs from the previous crashed instance. Or override the command: kubectl debug pod/myapp-xxx -it --image=busybox

Set Up a Cron Job — Automate Recurring Tasks
Run scripts on a schedule: backups, cleanup, health checks
cron
FILE
./backup.sh
#!/bin/bash # Daily DB backup script DATE=$(date +%Y-%m-%d) BACKUP_DIR=/opt/backups mkdir -p $BACKUP_DIR # Dump PostgreSQL database pg_dump -U postgres mydb > $BACKUP_DIR/mydb-$DATE.sql # Compress it gzip $BACKUP_DIR/mydb-$DATE.sql # Delete backups older than 7 days find $BACKUP_DIR -name "*.gz" -mtime +7 -delete echo "Backup complete: $BACKUP_DIR/mydb-$DATE.sql.gz"

OUTPUT
0 2 * * * /opt/backup.sh >> /var/log/backup.log 2>&1 # In /var/log/backup.log the next morning: Backup complete: /opt/backups/mydb-2024-01-15.sql.gz
04
File Permissions — chmod & chown Explained
Fix "Permission denied" errors and understand rwx in 3 minutes
permissions
CMD
# See current permissions ls -la myapp/ # -rw-r--r-- means: owner=rw, group=r, others=r # Make a script executable chmod +x deploy.sh # add execute for everyone chmod 755 deploy.sh # rwxr-xr-x (owner full, others read+exec) chmod 600 .env # rw------- (only owner can read — good for secrets!) chmod 700 ~/.ssh # rwx------ (your SSH dir — others cannot see it) # Change owner (run as root) chown ubuntu:ubuntu /opt/myapp # user:group chown -R ubuntu:ubuntu /opt/myapp # -R = recursive (all files inside)
OUTPUT
-rw------- 1 ubuntu ubuntu 512 Jan 15 .env -rwxr-xr-x 1 ubuntu ubuntu 1024 Jan 15 deploy.sh drwx------ 2 ubuntu ubuntu 4096 Jan 15 .ssh/
CHEATSHEET
400 = read-only (SSH key files) | 600 = rw owner only (.env, secrets) | 644 = web files (owner rw, others r) | 755 = scripts and dirs | 777 = everyone full access (⚠️ never use in prod)

Resolve a Merge Conflict
Two people edited the same file — here's how to resolve it without panic
conflict
CMD

03
git stash — Save Work Without Committing
Mid-task and need to switch branches urgently? Stash it.
stash
CMD
# You are halfway through a feature when a hotfix comes in # Stash your current work (like a clipboard) git stash push -m "WIP: halfway through auth feature" # Now your working directory is clean — switch branches safely git checkout main git checkout -b hotfix/login-crash # ... fix the bug, commit, push, merge ... # Come back to your feature branch git checkout feature/add-auth # See what is stashed git stash list # Restore your stashed work git stash pop # applies latest stash AND removes it from stash list
OUTPUT
stash@{0}: On feature/add-auth: WIP: halfway through auth feature On branch feature/add-auth Changes not staged for commit: modified: src/auth/middleware.js Dropped stash@{0}
04
git rebase — Clean Up History Before a PR
Squash messy WIP commits into one clean commit before requesting review
rebase
CMD
# You have 4 messy commits on your feature branch: # abc123 WIP # def456 fix typo # ghi789 almost done # jkl012 finally works # Squash last 4 commits interactively git rebase -i HEAD~4 # Editor opens — change to: # pick abc123 WIP # squash def456 fix typo # squash ghi789 almost done # squash jkl012 finally works # → save → another editor opens for the combined commit message # Write: "feat: add JWT authentication" # Force push (you rewrote history) git push --force-with-lease origin feature/add-auth
OUTPUT
Successfully rebased and updated refs/heads/feature/add-auth. git log --oneline f9c3a2b feat: add JWT authentication ← 4 commits became 1, clean! a81b3d1 feat: previous work
05
Undo Mistakes — reset, revert & restore
The right tool for every "oh no" moment — without losing work
undo
CMD
─── Scenario 1: Unstage a file (not yet committed) ─── git restore --staged src/secrets.js # remove from staging, keep changes ─── Scenario 2: Discard ALL local changes (dangerous!) ─── git restore . # reverts working directory to last commit ─── Scenario 3: Undo last commit but KEEP the changes ─── git reset HEAD~1 # unpacks last commit back to working dir ─── Scenario 4: Undo a commit that was ALREADY PUSHED ─── # NEVER force-push to shared branches! # Use revert — creates a new "undo" commit git revert abc123 # creates commit that reverses abc123 git push origin main # safe to push ─── Scenario 5: I committed to wrong branch! ─── git log --oneline -1 # copy the commit hash git reset HEAD~1 # undo the commit on wrong branch git checkout correct-branch git cherry-pick abc123 # apply that commit here
RULE
revert = safe for shared branches (adds new commit). reset = rewrites history, only use on your own local branches. --force-with-lease > --force (checks nobody else pushed first).
