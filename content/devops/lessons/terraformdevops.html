🧱 Foundation for Terraform
Before providers and state files fly past you — let's build this from true zero: what "Infrastructure as Code" even means, the complete journey from a text file to a real running server, the real commands you'll type, and what a DevOps engineer actually spends their day doing with all of this.
Terraform — Complete Foundation for DevOps
1. First: what even is "Infrastructure as Code"?
Before Terraform existed, creating a server meant clicking through a cloud provider's website — pick a region, pick a size, click "Launch," then do it all again by hand for the next server, and hope you remembered every setting the same way each time.
Old way: click buttons in a web console, by hand, every time 🖱️ New way: write a text file describing what you want, run one command 📄
"Infrastructure as Code" (IaC) just means: instead of clicking, you write down what infrastructure you want, in a file, and a tool builds it for you. That file can be reviewed, versioned, and re-run identically forever.
2. Why does DevOps even need this?
Because clicking through a console doesn't scale, isn't repeatable, and leaves no record of what changed or why.
If a server was set up by hand and then dies, is anyone 100% sure they can recreate it exactly? With Terraform, the answer is always yes — the file is the setup instructions, and running it again produces the exact same result.
🔑 The uncomfortable truth: "someone clicked around in the AWS console until it worked" is one of the scariest sentences in DevOps — because nobody, including that person six months later, can fully explain what state the infrastructure is actually in. Terraform's whole reason for existing is to make infrastructure as reviewable and reproducible as application code.
3. The complete flow — what actually happens when you run Terraform
This is the single most important mental model in this whole section. Walk through it slowly:
You write a .tf file "I want one server, this size, in this region" │ ↓ terraform init 📥 Downloads the plugin (provider) that knows how to talk to AWS/Azure/GCP │ ↓ terraform plan 📋 "Here's exactly what I would create, change, or destroy — nothing happens yet" │ ↓ You review the plan │ ↓ terraform apply ✅ Terraform calls the cloud provider's API and actually creates it │ ↓ terraform.tfstate 🧠 Terraform writes down exactly what it just created, so it remembers next time
Every arrow in that diagram is something a DevOps engineer configures, reviews, and eventually has to debug. That's the whole job, condensed into one picture.
4. Declarative vs. imperative — the idea underneath everything
This is the single biggest mental shift for anyone new to Terraform:
Imperative (a script) Declarative (Terraform) "Do these steps, in order:" "I want this end result:" 1. Create a server resource "aws_instance" "web" { 2. Attach a disk instance_type = "t3.micro" 3. Open port 443 ... }
You never tell Terraform how to create a server step by step — you just describe the end state you want, and Terraform figures out the "how" by comparing that description against what actually exists right now.
5. Providers — how Terraform actually talks to the cloud
Terraform itself doesn't know anything about AWS, Azure, or GCP out of the box. A provider is a plugin that teaches it how to talk to one specific platform's API.
provider "aws" { region = "us-east-1" }
This is why terraform init is always the very first command — it reads your config, sees you're using the AWS provider, and downloads that specific plugin before anything else can happen.
6. Resources — the actual "things" being created
A resource block is one real object Terraform will manage — a server, a network, a bucket, a database.
resource "aws_instance" "web" { ami = "ami-0c55b159cbfafe1f0" instance_type = "t3.micro" }
Read it as: "create a resource of type aws_instance, and locally call it web so other parts of this config can refer back to it." Every real Terraform project is fundamentally a pile of these blocks.
7. The state file — Terraform's memory
The very first time you run terraform apply, Terraform doesn't just create your resources — it also writes a file called terraform.tfstate that records exactly what it created and every setting it used.
Your .tf files Real AWS resources terraform.tfstate "what I want" ⟷ "what actually exists" ⟷ "what Terraform thinks exists"
Every future plan or apply compares all three of these. This is exactly why the state file matters so much — without it, Terraform would have no way to know the difference between "this server doesn't exist yet" and "this server already exists, leave it alone."
🔑 In a real team, the state file is stored remotely (like an S3 bucket), never on one person's laptop and never committed to Git — it often contains sensitive values, and two people applying from two different local state files at the same time is exactly how infrastructure gets silently corrupted.
8. Variables & outputs — making configs reusable
Hardcoding values everywhere makes a config brittle. Variables let you define a value once and reuse it; outputs let you print a value back out after apply.
variable "instance_type" { default = "t3.micro" } resource "aws_instance" "web" { instance_type = var.instance_type } output "public_ip" { value = aws_instance.web.public_ip }
Now the exact same config can spin up a bigger instance just by overriding one variable — and after apply, the new server's IP prints right in the terminal instead of you having to go look it up manually.
9. HCL syntax — reading a .tf file top to bottom
HCL (HashiCorp Configuration Language) has a small, consistent shape you'll see in every file:
BLOCK_TYPE "label1" "label2" { argument = value nested_block { argument = value } }
That's genuinely the whole grammar. A provider block, a resource block, a variable block — they're all this exact same shape, just with different keywords and different numbers of labels.
10. Commands you actually type
Theory is nothing without the terminal. These are the commands you will genuinely reach for, in the order you'd actually reach for them building something for real.
terraform init — "set this project up, download what it needs"
terraform init
Initializing the backend... Initializing provider plugins... - Installing hashicorp/aws v5.31.0... Terraform has been successfully initialized!
Run this once per project, and again any time you add a new provider or module — safe to run repeatedly, it won't touch your infrastructure.
terraform plan — "show me what would happen, but don't do it"
terraform plan
# aws_instance.web will be created + resource "aws_instance" "web" { + instance_type = "t3.micro" + ami = "ami-0c55b159cbfafe1f0" } Plan: 1 to add, 0 to change, 0 to destroy.
The single most important safety feature in all of Terraform — a full preview of every change, with zero risk, before anything real happens.
terraform apply — "okay, actually do it"
terraform apply
aws_instance.web: Creating... aws_instance.web: Creation complete after 24s [id=i-0abc123def456789] Apply complete! Resources: 1 added, 0 changed, 0 destroyed.
Asks for confirmation (type yes) unless you pass -auto-approve — the actual moment real cloud resources get created.
terraform destroy — "tear it all back down"
terraform destroy
aws_instance.web: Destroying... [id=i-0abc123def456789] aws_instance.web: Destruction complete after 5s Destroy complete! Resources: 1 destroyed.
Removes everything Terraform is tracking in the state file — genuinely destructive, always double-check the plan output first.
11. What does a DevOps engineer actually DO with Terraform, day to day?
This is the part most tutorials skip. Here's what it actually looks like in a real job:
Writing and reviewing .tf files in pull requests — infrastructure changes go through code review exactly like application code, with terraform plan output often posted right on the PR.
Reading a plan carefully before approving it — spotting when a seemingly small change would actually destroy and recreate a resource (shown as -/+), which might mean real downtime.
Managing remote state and locking — making sure the whole team applies against the same shared state, and that two people can't apply at the exact same time and corrupt it.
Debugging drift — someone manually changed a setting in the cloud console, and now Terraform's plan shows an unexpected change because reality no longer matches the state file.
Building reusable modules — packaging up a "standard web server setup" once, so five different teams can reuse it instead of five different copy-pasted configs.
Running Terraform inside CI/CD — a merged PR automatically triggers terraform plan, and often a manual approval step before terraform apply runs for real.
12. The full picture, one more time
main.tf 📄 │ terraform init │ ↓ ┌─────────────────────┐ │ Provider plugin │ ← knows how to talk to AWS/Azure/GCP └──────────┬────────────┘ │ terraform plan │ ↓ ┌─────────────────────┐ │ Execution plan │ ← preview, nothing happens yet └──────────┬────────────┘ │ terraform apply │ ↓ ┌─────────────────────┐ │ Real cloud resources │ └──────────┬────────────┘ │ ↓ terraform.tfstate 🧠 (remembers what exists)
Every box is something you'll configure. Every arrow is a command you'll eventually reach for without even thinking about it.

🧠 Kid-friendly memory trick
Think of Terraform like building with architectural blueprints:
.tf file ↓ The BLUEPRINT — what you want built terraform plan ↓ The contractor reading the blueprint back to you: "here's exactly what I'm going to build" — before touching anything terraform apply ↓ The contractor actually BUILDING it terraform.tfstate ↓ The contractor's own notes on what's already been built, so they don't accidentally build the same house twice
🔑 Key takeaway

Everything in Terraform traces back to one idea: describe the end state you want, in a file, and let the tool figure out how to get there — safely, predictably, and the exact same way every single time. A provider is how it talks to the cloud. A resource is one thing it manages. The state file is how it remembers. Plan, then apply, is how it stays safe.
