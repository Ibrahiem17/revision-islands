EC2 — Elastic Compute Cloud
Virtual server in AWS. The foundation of everything.
Compute
Real-World Scenario: Your team needs to host a Node.js API. You need a server that's publicly reachable, automatically starts your app on boot, and you can redeploy without touching it manually.
Step-by-Step: Launch & Deploy to EC2
1
Launch the instance (AWS Console)
EC2 → Launch Instance → Ubuntu 22.04 LTS → t2.micro (free tier) → Key pair: create new → download .pem. Security group: allow SSH (22), HTTP (80), HTTPS (443).
2
SSH in and set up the server
# Fix key permissions (required or SSH refuses it) chmod 400 my-key.pem # Connect to the server ssh -i my-key.pem ubuntu@<EC2_PUBLIC_IP> # On the server: update + install Docker sudo apt update && sudo apt install docker.io -y sudo systemctl enable docker && sudo systemctl start docker sudo usermod -aG docker $USER && newgrp docker
3
Deploy your app with --restart=always
# Pull your image and run it docker pull ibrahiem/my-node-api:latest docker run -d \ -p 80:3000 \ --name api \ --restart=always \ -e NODE_ENV=production \ ibrahiem/my-node-api:latest # Verify it's running docker ps curl http://localhost:80/health # Test from outside curl http://<EC2_PUBLIC_IP>/health # → {"status":"ok"}
4
The DevOps way: User Data (zero manual setup)
Paste this in User Data when launching the EC2. Server auto-configures itself on first boot. You never SSH in.
#!/bin/bash # This runs as root on first boot — before you can even log in apt update -y apt install docker.io -y systemctl start docker systemctl enable docker docker run -d -p 80:3000 --name api --restart=always \ ibrahiem/my-node-api:latest
5
Redeploy new version (zero-downtime approach)
# SSH in and update the container docker pull ibrahiem/my-node-api:v2 docker stop api && docker rm api docker run -d -p 80:3000 --name api --restart=always \ ibrahiem/my-node-api:v2 # Or do it in one line from CI/CD (e.g. GitHub Actions / Jenkins) ssh ubuntu@EC2_IP 'docker pull ibrahiem/api:latest && \ docker stop api || true && docker rm api || true && \ docker run -d -p 80:3000 --name api --restart=always ibrahiem/api:latest'
Pro tip: Add --restart=always so the container auto-restarts if it crashes or the EC2 reboots. Without it, a server restart = dead app until you manually start it again.
Instance Typest2.micro = free tier dev. t3.small = light prod. c5.large = CPU heavy. r5.large = memory heavy. Always check cost.
Elastic IPEC2 public IP changes on stop/start. Attach an Elastic IP for a permanent IP. First one free per account.
EBS VolumeEC2's hard drive. Persists after stop. Snapshots = backups. Can detach and attach to another instance.
AMIA snapshot of an EC2 state. Create AMI from your configured server → launch identical copies instantly. Faster than User Data for complex setups.

S3 — Simple Storage Service
Infinitely scalable object storage. Files, backups, static sites, Terraform state.
Storage
Real-World Scenario 1: Host your React app's built files as a static website. No server needed.
Real-World Scenario 2: Store Terraform state file so your whole team shares the same infrastructure state.
Use Case A: Host a Static Website on S3
# 1. Build your React/Next.js app npm run build # 2. Create an S3 bucket (name must be globally unique) aws s3 mb s3://ibrahiem-portfolio-app # 3. Enable static website hosting aws s3 website s3://ibrahiem-portfolio-app \ --index-document index.html \ --error-document index.html # 4. Upload your build folder aws s3 sync ./dist s3://ibrahiem-portfolio-app/ --delete # 5. Make bucket publicly readable (bucket policy) aws s3api put-bucket-policy --bucket ibrahiem-portfolio-app \ --policy '{ "Version":"2012-10-17", "Statement":[{ "Effect":"Allow", "Principal":"*", "Action":"s3:GetObject", "Resource":"arn:aws:s3:::ibrahiem-portfolio-app/*" }] }' # Your site is now live at: # http://ibrahiem-portfolio-app.s3-website-us-east-1.amazonaws.com
Use Case B: Terraform Remote State in S3
# 1. Create the state bucket + DynamoDB lock table aws s3 mb s3://ibrahiem-terraform-state --region us-east-1 aws s3api put-bucket-versioning --bucket ibrahiem-terraform-state \ --versioning-configuration Status=Enabled aws dynamodb create-table \ --table-name terraform-locks \ --attribute-definitions AttributeName=LockID,AttributeType=S \ --key-schema AttributeName=LockID,KeyType=HASH \ --billing-mode PAY_PER_REQUEST # 2. In your main.tf — add this backend block terraform { backend "s3" { bucket = "ibrahiem-terraform-state" key = "prod/terraform.tfstate" region = "us-east-1" dynamodb_table = "terraform-locks" # prevents simultaneous applies encrypt = true } } # 3. Init — Terraform now stores state in S3, not locally terraform init
Use Case C: Store Build Artifacts from CI/CD
# In your GitHub Actions / Jenkins pipeline: # After a successful build, upload the artifact to S3 aws s3 cp ./dist/app.tar.gz \ s3://ibrahiem-artifacts/builds/${BUILD_NUMBER}/app.tar.gz # Later, on the EC2 during deploy: aws s3 cp s3://ibrahiem-artifacts/builds/47/app.tar.gz . tar -xzf app.tar.gz && pm2 restart all
Common gotcha: Forgetting --delete in s3 sync. Without it, old files from previous builds stay in the bucket — users may get stale cached assets. Always use --delete when syncing a fresh build.

IAM — Identity and Access Management
Who can do what in your AWS account. The most important security layer.
Security
Real-World Scenario: Your EC2 needs to read from S3 and push to ECR. Your GitHub Actions needs to deploy to ECS. A new junior dev needs read-only access to view resources. None of these should have access keys hardcoded anywhere.
Pattern 1: EC2 Instance Role (no access keys on server)
# 1. Create an IAM Role that EC2 can assume aws iam create-role \ --role-name EC2-App-Role \ --assume-role-policy-document '{ "Version":"2012-10-17", "Statement":[{ "Effect":"Allow", "Principal":{"Service":"ec2.amazonaws.com"}, "Action":"sts:AssumeRole" }] }' # 2. Attach policy — allow reading from a specific S3 bucket only aws iam put-role-policy \ --role-name EC2-App-Role \ --policy-name S3ReadPolicy \ --policy-document '{ "Version":"2012-10-17", "Statement":[{ "Effect":"Allow", "Action":["s3:GetObject","s3:ListBucket"], "Resource":[ "arn:aws:s3:::ibrahiem-app-assets", "arn:aws:s3:::ibrahiem-app-assets/*" ] }] }' # 3. Create instance profile and attach role aws iam create-instance-profile --instance-profile-name EC2-App-Profile aws iam add-role-to-instance-profile \ --instance-profile-name EC2-App-Profile --role-name EC2-App-Role # 4. Attach to EC2 at launch time (or associate to running instance) aws ec2 associate-iam-instance-profile \ --instance-id i-1234567890 \ --iam-instance-profile Name=EC2-App-Profile # Now on the EC2, run AWS CLI commands WITHOUT any access keys aws s3 ls s3://ibrahiem-app-assets # ← works because of the role
Pattern 2: GitHub Actions Deploy Role (OIDC — no long-lived keys)
# In your GitHub Actions workflow.yml: permissions: id-token: write # required for OIDC contents: read steps: - name: Configure AWS credentials (OIDC - no secret keys!) uses: aws-actions/configure-aws-credentials@v4 with: role-to-assume: arn:aws:iam::123456789:role/GitHub-Deploy-Role aws-region: us-east-1 # GitHub gets a temp token, assumes the role, no secrets needed - run: aws s3 sync ./dist s3://my-bucket/
Pattern 3: Create a Read-Only Dev User
# Create user aws iam create-user --user-name ahmed-dev # Attach AWS-managed ReadOnly policy aws iam attach-user-policy \ --user-name ahmed-dev \ --policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess # Create access keys for CLI use aws iam create-access-key --user-name ahmed-dev # → Save the SecretAccessKey NOW — it's never shown again # NEVER give users AdministratorAccess unless absolutely necessary # Least privilege = only the permissions the role actually needs
Interview gold — say this: "I never put AWS access keys in code or .env files committed to Git. For EC2 I use instance roles. For CI/CD I use OIDC or service-specific IAM roles. Least privilege — every role only gets the specific actions on the specific resources it needs, nothing more."

VPC — Virtual Private Cloud
Your private, isolated network inside AWS. Everything runs inside one.
Networking
Real-World Scenario: You need a VPC with public subnets (for the load balancer) and private subnets (for EC2 app servers and RDS database). App servers must reach the internet for package updates but must NOT be directly reachable from the internet.
Build a Production VPC with Terraform
# vpc.tf — production-ready VPC ### VPC ### resource "aws_vpc" "main" { cidr_block = "10.0.0.0/16" enable_dns_hostnames = true tags = { Name = "prod-vpc" } } ### PUBLIC SUBNETS (for ALB, NAT Gateway) ### resource "aws_subnet" "public_a" { vpc_id = aws_vpc.main.id cidr_block = "10.0.1.0/24" availability_zone = "us-east-1a" map_public_ip_on_launch = true } resource "aws_subnet" "public_b" { vpc_id = aws_vpc.main.id cidr_block = "10.0.2.0/24" availability_zone = "us-east-1b" map_public_ip_on_launch = true } ### PRIVATE SUBNETS (for EC2 app servers) ### resource "aws_subnet" "private_a" { vpc_id = aws_vpc.main.id cidr_block = "10.0.10.0/24" availability_zone = "us-east-1a" } ### INTERNET GATEWAY (front door for public subnets) ### resource "aws_internet_gateway" "igw" { vpc_id = aws_vpc.main.id } ### NAT GATEWAY (lets private EC2s reach internet for updates) ### resource "aws_eip" "nat" { domain = "vpc" } resource "aws_nat_gateway" "nat" { allocation_id = aws_eip.nat.id subnet_id = aws_subnet.public_a.id # NAT lives in public subnet } ### ROUTE TABLES ### # Public: route internet traffic to IGW resource "aws_route_table" "public" { vpc_id = aws_vpc.main.id route { cidr_block = "0.0.0.0/0"; gateway_id = aws_internet_gateway.igw.id } } # Private: route internet traffic to NAT (not IGW) resource "aws_route_table" "private" { vpc_id = aws_vpc.main.id route { cidr_block = "0.0.0.0/0"; nat_gateway_id = aws_nat_gateway.nat.id } } ### SECURITY GROUPS ### # ALB: allow all HTTP/HTTPS from internet resource "aws_security_group" "alb" { vpc_id = aws_vpc.main.id ingress { from_port=80; to_port=80; protocol="tcp"; cidr_blocks=["0.0.0.0/0"] } ingress { from_port=443; to_port=443; protocol="tcp"; cidr_blocks=["0.0.0.0/0"] } egress { from_port=0; to_port=0; protocol="-1"; cidr_blocks=["0.0.0.0/0"] } } # App EC2: ONLY allow traffic from ALB security group resource "aws_security_group" "app" { vpc_id = aws_vpc.main.id ingress { from_port = 3000 to_port = 3000 protocol = "tcp" security_groups = [aws_security_group.alb.id] # ← key pattern } }
Interview gold — SG referencing SGs: Instead of cidr_blocks = ["0.0.0.0/0"] for the app servers, reference the ALB's security group ID. This means ONLY traffic that came through the load balancer can reach the app — even if someone discovers the private IP, they can't hit it directly.

RDS — Relational Database Service
Managed Postgres / MySQL. AWS handles backups, patching, failover.
Database
Real-World Scenario: Provision a PostgreSQL database that your Node.js app connects to. Database must be in a private subnet (not internet-accessible). App servers connect to it via its internal DNS endpoint.
Provision RDS with Terraform + Connect from App
# rds.tf — Postgres in private subnet # DB subnet group — RDS needs at least 2 AZs resource "aws_db_subnet_group" "main" { name = "prod-db-subnets" subnet_ids = [aws_subnet.private_a.id, aws_subnet.private_b.id] } # Security group — only allow from app servers resource "aws_security_group" "rds" { vpc_id = aws_vpc.main.id ingress { from_port = 5432 to_port = 5432 protocol = "tcp" security_groups = [aws_security_group.app.id] # only app EC2s } } # The RDS instance resource "aws_db_instance" "postgres" { identifier = "prod-postgres" engine = "postgres" engine_version = "15.4" instance_class = "db.t3.micro" # free tier eligible allocated_storage = 20 db_name = "appdb" username = "appuser" password = var.db_password # from tfvars / Secrets Manager db_subnet_group_name = aws_db_subnet_group.main.name vpc_security_group_ids = [aws_security_group.rds.id] publicly_accessible = false # NEVER true in prod multi_az = true # automatic failover to standby backup_retention_period = 7 # keep 7 days of backups skip_final_snapshot = false # snapshot on destroy } # Output the endpoint so app servers can connect output "db_endpoint" { value = aws_db_instance.postgres.endpoint # → prod-postgres.xxxxx.us-east-1.rds.amazonaws.com:5432 } # In your Node.js app — connect using the endpoint # DATABASE_URL=postgresql://appuser:pass@prod-postgres.xxx.rds.amazonaws.com:5432/appdb

ECR — Elastic Container Registry
Private Docker image registry. Like Docker Hub but inside AWS, with IAM auth.
Containers
Real-World Scenario: Your CI/CD pipeline builds a Docker image and pushes it to ECR. Your ECS service pulls from ECR to deploy. No Docker Hub credentials needed — IAM handles auth.
Full ECR Workflow: Build → Push → Pull
# 1. Create the ECR repository aws ecr create-repository \ --repository-name my-node-api \ --region us-east-1 # Returns: repositoryUri = 123456789.dkr.ecr.us-east-1.amazonaws.com/my-node-api # 2. Log Docker into ECR (token valid 12 hours) aws ecr get-login-password --region us-east-1 | \ docker login --username AWS --password-stdin \ 123456789.dkr.ecr.us-east-1.amazonaws.com # 3. Build and tag with ECR URI docker build -t my-node-api:latest . docker tag my-node-api:latest \ 123456789.dkr.ecr.us-east-1.amazonaws.com/my-node-api:latest docker tag my-node-api:latest \ 123456789.dkr.ecr.us-east-1.amazonaws.com/my-node-api:${BUILD_NUMBER} # 4. Push both tags docker push 123456789.dkr.ecr.us-east-1.amazonaws.com/my-node-api:latest docker push 123456789.dkr.ecr.us-east-1.amazonaws.com/my-node-api:${BUILD_NUMBER} # 5. Enable lifecycle policy — keep only 10 latest images (saves cost) aws ecr put-lifecycle-policy \ --repository-name my-node-api \ --lifecycle-policy-text '{ "rules":[{ "rulePriority":1, "selection":{"tagStatus":"any","countType":"imageCountMoreThan","countNumber":10}, "action":{"type":"expire"} }] }' # 6. In GitHub Actions — full push step - name: Push to ECR env: ECR_REGISTRY: ${{ steps.login-ecr.outputs.registry }} run: | docker build -t $ECR_REGISTRY/my-node-api:${{ github.sha }} . docker push $ECR_REGISTRY/my-node-api:${{ github.sha }}

ECS — Elastic Container Service
Run Docker containers on AWS without managing Kubernetes. Simpler than EKS.
Containers
Real-World Scenario: Deploy your Dockerized app to ECS Fargate. AWS manages the underlying servers entirely — you just say "run 3 copies of this container with 512MB RAM" and AWS handles the rest.
ECS Fargate Deployment with Terraform
# ecs.tf — deploy container to Fargate (serverless containers) ### CLUSTER ### resource "aws_ecs_cluster" "main" { name = "prod-cluster" } ### TASK DEFINITION — what container to run and how ### resource "aws_ecs_task_definition" "app" { family = "my-node-api" requires_compatibilities = ["FARGATE"] network_mode = "awsvpc" cpu = "256" # 0.25 vCPU memory = "512" # 512 MB execution_role_arn = aws_iam_role.ecs_execution.arn container_definitions = jsonencode([{ name = "api" image = "123456789.dkr.ecr.us-east-1.amazonaws.com/my-node-api:latest" portMappings = [{ containerPort = 3000 }] environment = [ { name = "NODE_ENV", value = "production" } ] # Secrets from SSM Parameter Store (not hardcoded) secrets = [ { name = "DB_PASSWORD", valueFrom = "/prod/app/db_password" } ] logConfiguration = { logDriver = "awslogs" options = { awslogs-group = "/ecs/my-node-api" awslogs-region = "us-east-1" awslogs-stream-prefix = "api" } } }]) } ### SERVICE — keep 3 tasks running at all times ### resource "aws_ecs_service" "app" { name = "my-node-api" cluster = aws_ecs_cluster.main.id task_definition = aws_ecs_task_definition.app.arn desired_count = 3 launch_type = "FARGATE" network_configuration { subnets = [aws_subnet.private_a.id, aws_subnet.private_b.id] security_groups = [aws_security_group.app.id] assign_public_ip = false # private subnet — no public IP } load_balancer { target_group_arn = aws_lb_target_group.app.arn container_name = "api" container_port = 3000 } # Rolling deployment — replace one task at a time deployment_minimum_healthy_percent = 50 deployment_maximum_percent = 200 } # Deploy new version from CLI aws ecs update-service \ --cluster prod-cluster \ --service my-node-api \ --force-new-deployment # ECS pulls new :latest image and does rolling update

ALB — Application Load Balancer
Distribute HTTP traffic. Health checks. Path-based routing. SSL termination.
Networking
Real-World Scenario: Route /api/* to your Node.js backend and /* to your React frontend. Terminate SSL at the load balancer so your app servers don't need to handle HTTPS.
ALB with Path-Based Routing (Terraform)
resource "aws_lb" "main" { name = "prod-alb" internal = false load_balancer_type = "application" security_groups = [aws_security_group.alb.id] subnets = [aws_subnet.public_a.id, aws_subnet.public_b.id] } # Target groups — where to send traffic resource "aws_lb_target_group" "api" { name = "api-targets" port = 3000 protocol = "HTTP" vpc_id = aws_vpc.main.id target_type = "ip" # required for ECS Fargate health_check { path = "/health" healthy_threshold = 2 unhealthy_threshold = 3 interval = 30 } } # HTTPS listener on port 443 resource "aws_lb_listener" "https" { load_balancer_arn = aws_lb.main.arn port = 443 protocol = "HTTPS" certificate_arn = var.acm_cert_arn # SSL cert from ACM default_action { type = "forward"; target_group_arn = aws_lb_target_group.frontend.arn } } # Path-based rule: /api/* goes to the API target group resource "aws_lb_listener_rule" "api" { listener_arn = aws_lb_listener.https.arn priority = 10 action { type = "forward"; target_group_arn = aws_lb_target_group.api.arn } condition { path_pattern { values = ["/api/*"] } } } # HTTP → HTTPS redirect (port 80 to 443) resource "aws_lb_listener" "http_redirect" { load_balancer_arn = aws_lb.main.arn port = 80 protocol = "HTTP" default_action { type = "redirect" redirect { protocol="HTTPS"; port="443"; status_code="HTTP_301" } } }

CloudWatch — Monitoring, Logs & Alarms
AWS-native observability. Metrics, logs, alarms, dashboards — all in one.
Observability
Real-World Scenario: Get alerted on Slack if CPU goes above 80%, if the app starts returning 5xx errors, or if the EC2 runs out of disk space — before your users notice.
Set Up Alarms + Log Groups (AWS CLI)
# 1. Create a log group for your app (ECS sends here automatically) aws logs create-log-group --log-group-name /ecs/my-node-api aws logs put-retention-policy \ --log-group-name /ecs/my-node-api \ --retention-in-days 30 # 2. Read logs in real-time from CLI aws logs tail /ecs/my-node-api --follow # 3. Search logs for errors aws logs filter-log-events \ --log-group-name /ecs/my-node-api \ --filter-pattern '"ERROR"' \ --start-time $(date -d '1 hour ago' +%s000) # 4. Create CPU alarm — alert when EC2 CPU > 80% for 5 mins aws cloudwatch put-metric-alarm \ --alarm-name "High-CPU-prod-server" \ --namespace AWS/EC2 \ --metric-name CPUUtilization \ --dimensions Name=InstanceId,Value=i-1234567890 \ --statistic Average \ --period 300 \ --threshold 80 \ --comparison-operator GreaterThanThreshold \ --evaluation-periods 1 \ --alarm-actions arn:aws:sns:us-east-1:123:my-alerts-topic # 5. Create ALB 5xx error rate alarm aws cloudwatch put-metric-alarm \ --alarm-name "High-5xx-rate" \ --namespace AWS/ApplicationELB \ --metric-name HTTPCode_Target_5XX_Count \ --dimensions Name=LoadBalancer,Value=app/prod-alb/1234 \ --statistic Sum \ --period 60 \ --threshold 10 \ --comparison-operator GreaterThanThreshold \ --evaluation-periods 2 \ --alarm-actions arn:aws:sns:us-east-1:123:my-alerts-topic # 6. SNS → Slack (subscribe your Slack webhook Lambda to the SNS topic) aws sns subscribe \ --topic-arn arn:aws:sns:us-east-1:123:my-alerts-topic \ --protocol email \ --notification-endpoint devops-team@company.com
CloudWatch in Terraform
resource "aws_cloudwatch_metric_alarm" "cpu_high" { alarm_name = "cpu-high" comparison_operator = "GreaterThanThreshold" evaluation_periods = 2 metric_name = "CPUUtilization" namespace = "AWS/ECS" period = 300 statistic = "Average" threshold = 80 alarm_actions = [aws_sns_topic.alerts.arn] dimensions = { ClusterName = "prod-cluster" ServiceName = "my-node-api" } }

Lambda — Serverless Functions
Run code without servers. Pay per invocation. Perfect for event-driven tasks.
Serverless
Real-World Scenario: When a file is uploaded to S3 (e.g., a profile picture), automatically trigger a Lambda to resize it and store the thumbnail. No server running 24/7 — Lambda wakes up, runs, and dies.
Lambda Triggered by S3 Upload
# handler.js — the Lambda function code const AWS = require('aws-sdk'); const s3 = new AWS.S3(); exports.handler = async (event) => { // event.Records contains S3 trigger info const bucket = event.Records[0].s3.bucket.name; const key = event.Records[0].s3.object.key; console.log(`Processing: ${bucket}/${key}`); // Download, process, re-upload thumbnail const obj = await s3.getObject({ Bucket: bucket, Key: key }).promise(); // ... sharp/image processing logic ... await s3.putObject({ Bucket: bucket, Key: `thumbnails/${key}`, Body: thumbnail }).promise(); return { statusCode: 200 }; };
# Deploy Lambda with AWS CLI # 1. Zip the code zip -r function.zip handler.js node_modules/ # 2. Create the Lambda function aws lambda create-function \ --function-name image-processor \ --runtime nodejs18.x \ --handler handler.handler \ --role arn:aws:iam::123:role/LambdaS3Role \ --zip-file fileb://function.zip \ --timeout 30 \ --memory-size 512 # 3. Add S3 trigger (allow S3 to invoke Lambda) aws lambda add-permission \ --function-name image-processor \ --action lambda:InvokeFunction \ --principal s3.amazonaws.com \ --source-arn arn:aws:s3:::my-uploads-bucket \ --statement-id s3-trigger # 4. Configure S3 to notify Lambda on uploads aws s3api put-bucket-notification-configuration \ --bucket my-uploads-bucket \ --notification-configuration '{ "LambdaFunctionConfigurations":[{ "LambdaFunctionArn":"arn:aws:lambda:us-east-1:123:function:image-processor", "Events":["s3:ObjectCreated:*"], "Filter":{"Key":{"FilterRules":[{"Name":"prefix","Value":"uploads/"}]}} }] }' # 5. Update function code after changes zip -r function.zip . && aws lambda update-function-code \ --function-name image-processor --zip-file fileb://function.zip # 6. Tail logs in real-time aws logs tail /aws/lambda/image-processor --follow

SSM — Systems Manager
Connect to EC2 without SSH. Store secrets in Parameter Store. No open ports.
Management
Real-World Scenario: Store your database password, API keys, and config in SSM Parameter Store. Your app reads them at runtime. No secrets in .env files. No secrets in Git. No port 22 open on servers.
SSM Parameter Store — Store & Read Secrets
# Store a secret (SecureString = encrypted with KMS) aws ssm put-parameter \ --name "/prod/myapp/DB_PASSWORD" \ --value "super-secret-pass-123" \ --type SecureString \ --description "Production DB password" aws ssm put-parameter \ --name "/prod/myapp/JWT_SECRET" \ --value "jwt-secret-abc-xyz" \ --type SecureString # Read it back (--with-decryption required for SecureString) aws ssm get-parameter \ --name "/prod/myapp/DB_PASSWORD" \ --with-decryption \ --query 'Parameter.Value' \ --output text # Read all params under a path prefix aws ssm get-parameters-by-path \ --path "/prod/myapp/" \ --with-decryption # In your Node.js app — read at startup const { SSMClient, GetParameterCommand } = require("@aws-sdk/client-ssm"); const client = new SSMClient({ region: "us-east-1" }); const { Parameter } = await client.send(new GetParameterCommand({ Name: "/prod/myapp/DB_PASSWORD", WithDecryption: true })); const DB_PASSWORD = Parameter.Value; # In ECS Task Definition — inject as environment variable "secrets": [{ "name": "DB_PASSWORD", "valueFrom": "/prod/myapp/DB_PASSWORD" }]
SSM Session Manager — SSH Without Port 22
# No SSH key needed, no port 22 open — connect via SSM aws ssm start-session --target i-1234567890abcdef0 # Opens a shell directly in the browser or terminal # Run a command without interactive session aws ssm send-command \ --instance-ids i-1234567890 \ --document-name "AWS-RunShellScript" \ --parameters '{"commands":["docker ps","docker logs api --tail 50"]}' # Requirements: SSM Agent installed (default on Amazon Linux), # EC2 instance role with AmazonSSMManagedInstanceCore policy attached

Route 53 — DNS & Domain Management
Point your domain to your AWS resources. Health checks. Failover routing.
DNS
Real-World Scenario: Point api.myapp.com to your ALB. Get a free SSL cert from ACM. Set up health-check-based failover so if your primary region goes down, traffic auto-reroutes to a backup.
Point Domain → ALB + Free SSL (AWS CLI)
# 1. Get your hosted zone ID aws route53 list-hosted-zones --query 'HostedZones[?Name==`myapp.com.`].Id' --output text # → /hostedzone/Z1234567890ABC # 2. Create A record (alias to ALB — no IP hardcoding) aws route53 change-resource-record-sets \ --hosted-zone-id Z1234567890ABC \ --change-batch '{ "Changes":[{ "Action":"UPSERT", "ResourceRecordSet":{ "Name":"api.myapp.com", "Type":"A", "AliasTarget":{ "HostedZoneId":"Z35SXDOTRQ7X7K", "DNSName":"prod-alb-1234567890.us-east-1.elb.amazonaws.com", "EvaluateTargetHealth":true } } }] }' # 3. Request free SSL cert from ACM aws acm request-certificate \ --domain-name "api.myapp.com" \ --subject-alternative-names "*.myapp.com" \ --validation-method DNS # 4. The real learning path for AWS
Don't try to learn all services at once. Do this order: EC2 (console) → EC2 (User Data) → S3 + static site → IAM roles → VPC from scratch → RDS → ECR + ECS → ALB → CloudWatch alarms. Each one builds on the last. By the time you finish, you've built a production AWS stack from scratch.
