🔥 Advanced Scenario Questions — these are the hardest scenarios asked in DevOps interviews. Each has a structured answer showing investigative thinking.
SC01A developer accidentally committed AWS access keys to a public GitHub repo. What do you do, step by step?▼
ANSWER
This is a P1 security incident. Move fast — automated bots scan GitHub constantly and can abuse keys within minutes.

1. Deactivate the keys immediately:
AWS Console → IAM → Users → Security credentials → Deactivate the access key. Do this before anything else. Even if the key hasn't been used yet.

2. Check if the keys were already used:
AWS CloudTrail → filter by the Access Key ID → look for any API calls, especially in unusual regions. Check for new IAM users created, new EC2 launched, S3 data accessed.

3. Remove from Git history:
git filter-branch or BFG Repo Cleaner to remove the commit from history. Force-push to GitHub. Note: if public, assume the key is compromised regardless — bots already have it.

4. Generate new keys and update secrets securely:
Create new access keys. Store in AWS Secrets Manager or GitHub Actions secrets. Never in code.

5. Prevent recurrence:
Add pre-commit hook using git-secrets or truffleHog to scan for credentials before every commit. Enable GitGuardian or similar on the org.

deactivate firstcheck CloudTrail for abusepurge from Git historyadd pre-commit secret scanning
SC02Kubernetes pods are being OOMKilled repeatedly. How do you investigate and fix it?▼
ANSWER
OOMKilled = container exceeded its memory limit and was killed by the kernel.

1. Confirm OOMKilled:
kubectl describe pod <name> → in the container status section: Last State: OOMKilled, Exit Code: 137

2. Check actual memory usage before kill:
kubectl top pods — see current usage.
Look at Grafana → memory usage graph for that pod over time. Is usage growing? That's a memory leak.

3. Root cause options:
• Limit set too low: App genuinely needs more RAM. Increase resources.limits.memory.
• Memory leak: Usage climbs over time until OOM. The app needs profiling and fixing.
• Spike under load: App uses bursts of memory under high traffic. Increase limit or add horizontal scaling.

4. Immediate fix: Increase the memory limit in the deployment YAML. Long-term: profile the app for leaks, optimize queries, cache wisely.

Exit Code 137 = OOMKilledkubectl top + Grafanaincrease limit or fix leak
SC03Docker build works locally but fails in CI. How do you debug this?▼
ANSWER
The classic "works on my machine" problem — but now it's your Docker build instead of your app.

1. Read the exact CI error: Compare CI build log with local build output. What exact step fails?

2. Check environment differences:
• Base image version: CI might be pulling a newer node:latest tag. Pin to an exact version.
• Architecture: You're on Apple M1 (ARM64), CI runner is Linux (AMD64). Use docker buildx build --platform linux/amd64 locally to match.
• Network access: CI runner might be behind a proxy or unable to reach npm/pip registries. Check .npmrc or mirror configs.
• Build secrets: CI might be missing an env var or build arg that your local Docker has.
• Cache state: CI builds from scratch. A dependency that installed fine from cache locally might fail on a clean install.

3. Reproduce exactly: Run docker build --no-cache locally. If it fails now, you've reproduced it.

pin image tagscheck arch (ARM vs AMD64)build --no-cache locallycheck network + env vars
SC04Your Terraform state file is locked and no one is running terraform. How do you fix it?▼
ANSWER
With S3 + DynamoDB remote state, Terraform acquires a lock in DynamoDB during apply. If the process is killed mid-apply (CI timeout, network drop), the lock is never released.

1. Confirm it's stale:
Check DynamoDB table for the lock entry. Note the LockID and when it was created. Is anyone actually running Terraform? Check CI logs.

2. Force-unlock (carefully):
terraform force-unlock <LOCK_ID>
The Lock ID is in the error message when you try to run Terraform.

3. Before unlocking, verify:
Make sure no apply is actually in progress. Unlocking while an apply is running can corrupt state — two applies writing simultaneously. Check CI, check team Slack.

4. After unlocking, run:
terraform plan to verify state is consistent. Check if partial apply left resources in a bad state.

terraform force-unlock <ID>verify no apply is running firstterraform plan after
SC05After a new deployment, response times increased 10x. How do you find the cause?▼
ANSWER
Correlate the timing: Confirm response time increase started exactly at the deployment. Check Grafana — does the latency spike align precisely with the rollout?

1. Check the app layer:
kubectl logs <pod> — any slow query warnings? Any new errors? Timeout messages?

2. Check the database:
Was a new database migration part of this deploy? Did it add an unindexed column that a frequent query now uses? Run EXPLAIN ANALYZE on slow queries. Check DB slow query log.

3. Check external dependencies:
Did the new code add calls to an external API? Is that API slow? Check connection pool settings.

4. Check resource saturation:
kubectl top pods — is the new code CPU/memory heavy? Is it hitting limits and being throttled?

5. Compare the diff:
git diff v1.0..v2.0 — what changed? Look for new database queries, removed caching, synchronous operations that were async, N+1 query bugs.

If urgent: rollback first, investigate in staging.

correlate timing with deploycheck DB slow queries + missing indexkubectl top for throttlinggit diff the changes
SC06An S3 bucket was accidentally made public. What is your incident response?▼
ANSWER
1. Block public access immediately:
S3 Console → Block Public Access settings → enable all four blocks. This is instant. Takes <1 minute.

2. Determine what was exposed:
S3 Server Access Logs or AWS CloudTrail Data Events → who accessed what files and when? Any GetObject requests from external IPs? What data was in that bucket?

3. Assess the data sensitivity:
PII, credentials, internal configs, customer data? Escalate accordingly. If PII was exposed, legal/compliance team must be notified (GDPR, etc.).

4. Rotate exposed secrets:
If any credentials, API keys, or tokens were in the bucket — rotate them all immediately.

5. Root cause and prevention:
Who made it public and how? Was it Terraform config? A console click? Enable AWS Config rule: s3-bucket-public-read-prohibited — alerts immediately when any S3 bucket is made public.

block public access firstcheck CloudTrail for accessrotate any exposed secretsAWS Config rule to prevent recurrence
SC07Your CI pipeline takes 45 minutes. How do you reduce it to under 10?▼
ANSWER
Profile first — find the bottleneck: Which step takes longest? Tests? Docker build? Lint? You can't optimize what you can't measure.

1. Parallelize jobs:
Run unit tests, lint, and security scan in parallel (separate jobs in GitHub Actions). Don't wait for lint to finish before starting tests.

2. Fix Docker layer caching:
Move COPY package.json and RUN npm install BEFORE COPY . .. If your source code changes but deps don't, the install layer is cached — saves 5-10 min.

3. Cache dependencies in CI:
GitHub Actions: actions/cache@v3 for node_modules, pip cache, Maven .m2. Avoid re-downloading on every run.

4. Split test suites:
Run unit tests in CI on every push. Run integration/e2e tests only on PRs to main. Don't run 5000 unit tests on every commit.

5. Use faster runners:
Larger GitHub Actions runners (4 CPU vs 2 CPU) for compute-heavy steps. Self-hosted runners close to your registries.

6. Fail fast:
Run the fastest checks (lint, type-check) first. Fail early before expensive steps.

profile firstparallelize jobsfix Docker layer cache ordercache dependencies
SC08All Kubernetes nodes are NotReady. What happened and how do you recover?▼
ANSWER
NotReady = Kubelet on the worker node has stopped communicating with the Control Plane, or the node itself is down.

1. Check node status:
kubectl get nodes → all NotReady.
kubectl describe node <name> → conditions section shows why (DiskPressure, MemoryPressure, NetworkUnavailable, KubeletNotReady).

2. SSH into a worker node and check:
systemctl status kubelet — is Kubelet running? If crashed: journalctl -u kubelet -f for error logs.
Common causes: disk full (df -h), node OOM, kubelet config error after upgrade.

3. Check the network:
Can nodes reach the API Server? Is the CNI plugin (Calico, Cilium) healthy? kubectl get pods -n kube-system — are networking pods crashing?

4. Cloud provider check:
Are the EC2 instances actually running? Check AWS console. Did an ASG policy terminate them all? Is there a cloud region incident?

5. Recovery:
Restart kubelet: systemctl restart kubelet. If disk full, clean up logs. If all else fails, replace the nodes via ASG.

describe node = conditionssystemctl status kubeletcheck disk full + CNIcheck cloud instance health
SC09You need to roll back a Kubernetes deployment that included a database migration. What's the problem and how do you handle it?▼
ANSWER
This is one of the most important DevOps topics and most candidates miss the nuance.

The problem: kubectl rollout undo rolls back the application code to v1.0. But the database migration already ran and added/modified schema. v1.0 code may not be compatible with the new schema — it might crash, produce errors, or corrupt data.

Best practice — write backwards-compatible migrations:
• Never drop a column in the same release that stops using it. First release: add new column, code uses both old + new. Second release: migrate data. Third release: remove old column.
• This allows safe rollback at any point — v1.0 code still works with the new schema because the old column still exists.

If you're already in trouble:
• Roll back the app first to stop user impact.
• Write a down migration (reverses the schema change) and run it manually.
• Ensure no data was migrated that would be lost by the rollback.

backward-compatible migrationsnever drop column in same releaseapp rollback ≠ DB rollback
SC10Your database is running out of connections under load. What do you investigate?▼
ANSWER
1. Confirm the error:
App logs: "too many connections" or "connection pool exhausted." DB metric: active connections approaching max_connections.

2. Check connection pool configuration:
Every app instance opens a pool of connections. If you have 20 pods × 50 pool size = 1000 connections. Does your DB support that? RDS Postgres default max_connections is often 100 for small instances.

3. Solutions:
• PgBouncer / RDS Proxy — connection poolers that sit between your app and DB. Many app connections → few real DB connections. 1000 app connections → 100 actual DB connections. This is the right fix at scale.
• Reduce pool size per pod — if you have many pods, reduce pool size so total connections fit within DB limits.
• Increase DB max_connections — temporary fix. Each connection uses RAM, so this has limits.

4. Find connection leaks:
Are connections being released after use? Check for code that opens connections but doesn't close them on error paths.

pods × pool size = total connectionsPgBouncer/RDS Proxy = multiplexingcheck for connection leaks
SC11A Kubernetes CronJob hasn't run in 3 days. How do you debug it?▼
ANSWER
1. Check the CronJob itself:
kubectl describe cronjob <name> — look at "Last Schedule Time" and "Active" count. Any events showing failures?

2. Check if Jobs were created:
kubectl get jobs — was a Job object created? If not, the schedule expression might be wrong. Verify the cron expression at crontab.guru.

3. Check missed deadline:
CronJob has a startingDeadlineSeconds field. If the cluster was down during the scheduled time and this window passed, K8s considers the job "missed" and won't run it retroactively.

4. Check failed Jobs:
kubectl get jobs --field-selector status.successful=0 — any failed jobs from recent runs? Check pod logs of the failed job.

5. concurrencyPolicy:
If set to Forbid and a previous run is still running → new runs are skipped. Check for stuck running jobs.

kubectl describe cronjobverify cron expressioncheck concurrencyPolicystartingDeadlineSeconds
SC12A new engineer accidentally ran `terraform destroy` in production. What's your recovery plan?▼
ANSWER
Don't panic. Act fast.

Immediate:
1. How much was destroyed? Run terraform plan to see what's missing vs what's in the state file.
2. Is there a Terraform workspace or state backup? S3 versioning on the state bucket → restore previous state version from S3.

Recovery:
1. terraform apply — recreates all resources defined in your .tf files. Terraform's declarative nature means this should reconstruct the infrastructure.
2. Databases: check AWS RDS automated backups (retention period). Restore from the latest snapshot. This is why you enable automated backups and test restores.
3. Restore DNS: if Route 53 records were destroyed, update them.

Prevention (what you implement after):
• Enable lifecycle { prevent_destroy = true } on critical resources in Terraform.
• Require two-person approval for production applies (Atlantis with required approvers).
• Lock down terraform destroy in CI — never in automated pipelines, human-only.
• Enable AWS Delete Protection on RDS, ELB.

restore state from S3 versioningterraform apply recreatesrestore DB from snapshotprevent_destroy lifecycle rule
SC13Your application is deployed but the Kubernetes Service is returning "No endpoints available". Why?▼
ANSWER
"No endpoints" = the Service exists but has no pods backing it. The Service selector doesn't match any healthy pod labels.

1. Check the endpoints object:
kubectl get endpoints <service-name> — if it shows <none>, no pods are selected.

2. Check the Service selector vs Pod labels:
kubectl describe service <name> → look at "Selector" field (e.g., app=myapp)
kubectl get pods --show-labels → do any pods have that exact label?
Typo in the label or selector = no match = no endpoints. This is the most common cause.

3. Check pod readiness:
Even if labels match, pods must be Ready to receive traffic. If readinessProbe is failing, pods are excluded from endpoints even though they're running.
kubectl get pods → check the READY column (1/1 vs 0/1).

4. Check namespace:
Is the Service in the same namespace as the pods? By default, Services only select pods in the same namespace.

kubectl get endpoints = empty?selector label mismatchreadinessProbe failingsame namespace?
SC14You're asked to migrate a monolith to microservices on Kubernetes. How do you approach it?▼
ANSWER
This is a Strangler Fig migration — don't rewrite everything at once. Extract services gradually while the monolith still runs.

Phase 1 — Containerize the monolith first:
Before splitting anything, package the monolith in Docker and deploy to Kubernetes. This teaches your team K8s without the added complexity of microservices.

Phase 2 — Identify seams:
Find the parts of the monolith that are independently deployable: auth service, payment service, notification service. Start with the one that changes most frequently or causes the most pain.

Phase 3 — Extract one service at a time:
• Extract the service → deploy as a separate K8s Deployment.
• Route traffic to the new service via the Ingress (e.g., /api/payments → payment service).
• Keep the monolith running — both the monolith's payment code and the new service exist during transition.
• Once confident, disable the monolith's payment code.

Phase 4 — Data separation:
Each microservice should own its data — separate DB schemas or separate RDS instances.

Strangler Fig patterncontainerize monolith firstextract one service at a timeeach service owns its data
SC15You've been asked to set up a DevOps pipeline for a brand new project from scratch. Walk through everything you'd build.▼
ANSWER
The answer that shows you understand the full picture:

1. Source Control: GitHub repo, branch protection on main (require PR + CI pass to merge), .gitignore, conventional commits enforced via commit-msg hook.

2. CI Pipeline (GitHub Actions):
On every push: lint → unit tests → build Docker image → push to ECR.
On PR: additionally run integration tests + security scan (Trivy, Snyk).

3. Infrastructure (Terraform):
VPC + subnets + security groups + EKS cluster + RDS in private subnet + ALB. Remote state in S3 + DynamoDB lock. Separate workspaces for dev/staging/prod.

4. CD (GitHub Actions + kubectl/Helm):
On merge to main → deploy to staging automatically. Manual approval gate → deploy to production. Kubernetes rolling update, zero downtime.

5. Secrets: GitHub Actions secrets for CI. AWS Secrets Manager for production app secrets. Never hardcoded.

6. Monitoring: Prometheus + Grafana for metrics. CloudWatch for AWS infra. Alertmanager → PagerDuty. Liveness + readiness probes on all pods.

7. Documentation: Runbook for on-call. README with setup instructions. Architecture diagram.

Git → CI → IaC → CD → Secrets → Monitor → Docs
