🧱 Foundation for Docker
Before Dockerfiles and flags fly past you — let's build this from true zero: what a container actually is, the complete journey from source code to a running container, the real commands you'll type, and what a DevOps engineer actually spends their day doing with all of this.
Docker — Complete Foundation for DevOps
1. First: What even is a "container"?
A container is a small, self-contained box that has everything your app needs to run — the code, the exact right version of the language runtime, every library it depends on — all packaged together so it runs identically no matter what machine it lands on.
Your laptop 💻 ──"works on my machine"──→ 🤷 Your laptop 💻 ──ships a container──────→ ✅ (same result, every machine)
That's the entire problem Docker solves. Not speed, not magic — just "the exact same thing runs the exact same way, everywhere."
2. Why does DevOps even need this?
Because before containers, deploying an app meant manually matching a server's setup to whatever the developer happened to have installed — the right Node version, the right system libraries, the right everything. One mismatch, and the app breaks in a way nobody can reproduce.
Containers remove that entire category of problem. If it runs in the container on your laptop, it runs identically in the container on the server, in the container in the CI pipeline, and in the container in the cluster.
🔑 The uncomfortable truth: "it works on my machine" used to be a running joke because everyone's machine was actually different. Docker didn't make computers more reliable — it made the environment itself something you ship, instead of something you hope matches.
3. The complete flow — what actually happens when you run a container
This is the single most important mental model in this whole section. Walk through it slowly:
You write code + a Dockerfile │ ↓ docker build 🔨 "Follow these steps, package the result" │ ↓ Image created 📦 (a frozen, reusable snapshot — not running yet) │ ↓ docker run ▶️ │ ↓ ┌───────────────────────┐ │ Docker Engine │ ← reads the image, starts a process └───────────┬─────────────┘ │ ↓ Container 🏃 (the image, actually running, isolated from everything else) │ ↓ Your app is now reachable (if you mapped a port)
Every arrow in that diagram is something a DevOps engineer configures, automates, and eventually has to debug. That's the whole job, condensed into one picture.
4. Image vs Container — the foundation of "what" vs "running"
This single distinction trips up almost everyone at first, so slow down here:
Image = the recipe, frozen and packaged (a class, in programming terms) Container = an actual running instance of that recipe (an object, in programming terms)
Image — built once, doesn't change, can be copied anywhere. Think of it as a read-only template.
Container — a live, running process created from an image. You can start ten containers from the exact same image, and each one runs independently.
This is exactly why docker images lists your templates, and docker ps lists what's actually running right now — they're answering two completely different questions.
5. The Dockerfile — how an image actually gets built
A Dockerfile is a plain text list of steps, read top to bottom, that describes exactly how to build the image.
FROM node:20 ← start from an existing base image WORKDIR /app ← everything below happens inside /app COPY . . ← copy your code into the image RUN npm install ← install dependencies, baked into the image CMD ["npm", "start"] ← what to run when a container starts
Nothing mysterious here — it's a recipe. FROM is your starting point, and every line after it adds one more layer on top.
6. Layers — why Docker is fast to rebuild
Every instruction in a Dockerfile creates a "layer" — and Docker caches each one. If a layer hasn't changed since the last build, Docker reuses it instantly instead of redoing the work.
FROM node:20 → Layer 1 (cached — base image never changes) WORKDIR /app → Layer 2 (cached — never changes) COPY package.json . → Layer 3 (cached, UNLESS package.json changed) RUN npm install → Layer 4 (only reruns if Layer 3 changed above it) COPY . . → Layer 5 (changes almost every build — your code) CMD ["npm", "start"] → Layer 6
This is exactly why real Dockerfiles copy package.json and run npm install before copying the rest of the code — it means editing a source file doesn't force a full dependency reinstall on every single build.
7. The Docker daemon & client — how the CLI actually works
When you type a Docker command, you're not talking directly to your containers — you're talking to a background service that manages everything.
You type: docker run nginx │ ↓ Docker CLI (client) — just sends the request │ ↓ Docker daemon (dockerd) — does the actual work: pulls the image, creates the container, starts the process │ ↓ Container is now running
This matters in real DevOps work — it's why "is the Docker daemon running?" is one of the first things you check when a container command mysteriously hangs or fails.
8. Commands you actually type
Theory is nothing without the terminal. These are the commands you will genuinely reach for, in the order you'd actually reach for them building and running something for real.
docker build — "turn my Dockerfile into an image"
docker build -t myapp:1.0 .
[+] Building 4.2s => [1/4] FROM node:20 => [2/4] WORKDIR /app => [3/4] COPY . . => [4/4] RUN npm install => exporting to image => naming to myapp:1.0
-t myapp:1.0 tags the image with a name and version, and the trailing . means "use the Dockerfile in this folder."
docker run — "actually start a container from that image"
docker run -d -p 3000:3000 myapp:1.0
a1b2c3d4e5f6 (container ID, running in the background)
-d runs it detached (in the background), -p 3000:3000 connects port 3000 on your machine to port 3000 inside the container.
docker ps — "what's actually running right now?"
docker ps
CONTAINER ID IMAGE STATUS PORTS a1b2c3d4e5f6 myapp:1.0 Up 2 minutes 0.0.0.0:3000->3000/tcp
The very first command to run when something "isn't working" — confirms whether the container is even alive.
docker logs — "what is it actually saying?"
docker logs -f a1b2c3d4e5f6
Server listening on port 3000 GET /health 200 OK
-f follows the log output live — the single most-used debugging command in all of Docker.
docker exec — "let me look around inside it"
docker exec -it a1b2c3d4e5f6 sh
/app # (you're now inside the running container)
Opens an interactive shell inside the already-running container — for poking around and checking files without stopping anything.
docker stop / rm — "shut it down and clean up"
docker stop a1b2c3d4e5f6 docker rm a1b2c3d4e5f6
stop gracefully shuts the process down; rm deletes the now-stopped container so it doesn't clutter docker ps -a.
9. What does a DevOps engineer actually DO with Docker, day to day?
This is the part most tutorials skip. Here's what it actually looks like in a real job:
Writing and trimming Dockerfiles — ordering instructions so the build cache works in your favor, and switching to smaller base images (like node:20-alpine) to cut image size and pull time.
Debugging "it built fine, why won't it start" — this is where docker logs and docker exec get used together to figure out exactly what's actually happening inside.
Wiring containers together — making sure an app container can actually reach a database container, usually via a shared Docker network or docker-compose.
Managing volumes — making sure a database container's data survives a restart instead of vanishing with the container.
Building images in CI — every push triggers a pipeline that builds a fresh image, tags it, and pushes it to a registry, ready to deploy.
Cleaning up disk space — old images and stopped containers quietly pile up on build servers; pruning them is a routine, recurring task.
10. The full picture, one more time
Dockerfile 📄 │ docker build │ ↓ ┌─────────────────────┐ │ Image 📦 │ ← frozen, reusable, shareable └──────────┬────────────┘ │ docker run │ ↓ ┌─────────────────────┐ │ Container 🏃 │ ← the image, actually running └──────────┬────────────┘ │ docker ps / logs / exec │ ↓ Debug, inspect, iterate
Every box is something you'll build. Every arrow is a command you'll eventually reach for without even thinking about it.

🧠 Kid-friendly memory trick
Think of Docker like baking:
Dockerfile ↓ Like a RECIPE card docker build ↓ Like actually BAKING the cake once Image ↓ The finished cake, boxed up — doesn't spoil, can be shipped anywhere docker run ↓ Taking a boxed cake out and putting a SLICE on a plate Container ↓ That plated slice — the thing actually being eaten right now You can plate ten slices (containers) from one boxed cake (image)
🔑 Key takeaway

Everything in Docker traces back to one idea: package it once, run it identically anywhere. An image is the frozen package. A container is that package, alive and running. Every command you'll ever type either builds the package, starts it, or lets you look inside it while it's running.

🎭 Real Scenarios — Learn Docker by Solving the Problem First
Read the situation, think about what you'd actually run, then click ▶ Run to reveal the command and its real output.
1
The situation: A container exits immediately after "docker run," with nothing obviously wrong printed to your terminal.
What would you run?
docker logs web
Error: Cannot find module 'express'
at Function.Module._resolveFilename
Why this command: The container's stdout/stderr from before it exited is captured here — the terminal itself shows nothing extra because the container already stopped by the time you'd see it.
2
The situation: Your app container can't reach a database container by hostname, even though "docker ps" shows both running fine.
What would you run?
docker network inspect app-net
"Containers": {
"db-container-id": { "Name": "db" }
// "web" is missing from this list
}
Why this command: The app container was never attached to the same custom network as the database — the default bridge network doesn't support name-based resolution, so "web" simply isn't in this network's container list.
3
The situation: You fixed a bug and rebuilt the image, but the running container still behaves like the old, broken version.
What would you run?
docker ps
CONTAINER ID IMAGE STATUS
a3f9d2c1b8e4 myapp:v1 Up 2 hours
Why this command: Rebuilding an image never touches an already-running container — it's still running the old image entirely. The fix is "docker stop web && docker rm web" followed by a fresh "docker run" from the new tag.
4
The situation: A CI runner's disk is nearly full after months of repeated image builds piling up unused layers.
What would you run?
docker system prune -a
Total reclaimed space: 4.2GB
Why this command: Every build leaves behind untagged intermediate layers and old images that never clean themselves up — this sweeps out everything not currently in use by a container in one shot.
5
The situation: You need to grab one config file out of a running container, without opening a full interactive shell session.
What would you run?
docker cp web:/etc/nginx/nginx.conf ./nginx.conf
(file copied to ./nginx.conf)
Why this command: cp moves a single file straight out of the container's filesystem to the host — faster than exec-ing in, catting the file, and manually copying the output.
6
The situation: "docker ps" shows a container marked (unhealthy), and you need to know exactly why before restarting it.
What would you run?
docker inspect --format='{{json .State.Health}}' web
{"Status":"unhealthy","FailingStreak":3,"Log":[{"Output":"curl: (7) Failed to connect"}]}
Why this command: The Health object logs the actual output of each failed probe — here, the healthcheck's own curl command couldn't connect, telling you exactly what's failing and not just that something is.
7
The situation: You're about to launch a production container and want it to come back up automatically if it ever crashes.
What would you run?
docker run -d --restart unless-stopped --name web nginx
a3f9d2c1b8e4
# container now auto-restarts on crash or host reboot
Why this command: Without a restart policy, a crash or host reboot leaves the app down until someone notices and manually restarts it — this is a near-default setting for anything in production.
8
The situation: You need to spin up an app, a database, and a cache together for local development, without three separate "docker run" commands.
What would you run?
docker compose up -d
[+] Running 3/3
✔ Container myapp-db-1 Started
✔ Container myapp-redis-1 Started
✔ Container myapp-web-1 Started
Why this command: compose reads docker-compose.yml and starts every defined service in the correct dependency order — one command instead of three separate ones, and the services can already reach each other by name.
