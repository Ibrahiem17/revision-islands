🎭 Real Scenarios — Learn Kubernetes by Solving the Problem First
Read the situation, think about what you'd actually run, then click ▶ Run to reveal the command and its real output.
1
The situation: A pod keeps entering CrashLoopBackOff, restarting over and over, and you need to know why.
What would you run?
kubectl logs web-7d8f9c6b5d-abcde --previous
Error: Cannot find module 'express'
at Function.Module._resolveFilename
Why this command: --previous shows the log from the container that already crashed, not the fresh restart attempt — which usually has no output yet. This is exactly the same idea as "docker logs" needing the crashed container's own output.
2
The situation: A pod has been stuck in "Pending" status for several minutes and never actually starts.
What would you run?
kubectl describe pod web-7d8f9c6b5d-abcde
Events:
Warning FailedScheduling 0/3 nodes are available: 3 Insufficient memory.
Why this command: describe's Events section is where the scheduler explains exactly why it couldn't place the pod — here, every node is genuinely out of free memory to fit it.
3
The situation: Another pod can't reach a service, and you suspect there might be no healthy pods actually behind it.
What would you run?
kubectl get endpoints web
NAME ENDPOINTS
web <none>
Why this command: An empty endpoints list confirms nothing is actually behind the service — no pod currently matches its selector, so any traffic sent to it simply has nowhere to go.
4
The situation: You need to test a service directly from your laptop, without setting up a public LoadBalancer or Ingress.
What would you run?
kubectl port-forward svc/web 8080:80
Forwarding from 127.0.0.1:8080 -> 80
Forwarding from [::1]:8080 -> 80
Why this command: port-forward tunnels a local port straight to the service inside the cluster — no public exposure needed, perfect for a quick local check.
5
The situation: A deployment you just pushed is clearly broken in production, and you need to recover immediately.
What would you run?
kubectl rollout undo deployment/web
deployment.apps/web rolled back
Why this command: This instantly reverts to the last known-good revision — no rebuild, no re-deploy script, just one command while you investigate the real fix.
6
The situation: You need to change an app's log level without rebuilding or redeploying its container image.
What would you run?
kubectl create configmap app-config --from-literal=LOG_LEVEL=debug
configmap/app-config created
Why this command: ConfigMaps keep config outside the image entirely — changing one (then restarting the pods that read it) never requires touching the image at all.
7
The situation: You're about to run a risky delete command and want to confirm you're actually allowed to first.
What would you run?
kubectl auth can-i delete pods --namespace production
no
Why this command: Confirming access ahead of time beats finding out only after the real command fails — and here, it just saved you from a permission error mid-incident.
8
The situation: A big sale is coming up, and pods need to scale up and down automatically as traffic rises and falls.
What would you run?
kubectl autoscale deployment web --min=2 --max=10 --cpu-percent=70
horizontalpodautoscaler.autoscaling/web autoscaled
Why this command: This sets up a Horizontal Pod Autoscaler that reacts to real CPU load automatically — no one has to be online during the sale to manually run kubectl scale.
