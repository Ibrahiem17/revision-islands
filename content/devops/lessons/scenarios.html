🐧 Linux & OS Scenarios
S01A server's CPU is spiking to 100% and it's unresponsive. Walk me through how you find the culprit.▼
APPROACH
1. SSH into the box (if you can — if completely unresponsive, use cloud console/serial access).
2. top or htop — sort by CPU. Identify the PID consuming it. Note the process name.
3. ps aux --sort=-%cpu | head -10 — non-interactive version, good for scripting.
4. strace -p <PID> — see what system calls the process is actually making right now. Is it stuck in a loop? Waiting on I/O?
5. dmesg | tail -50 or cat /var/log/messages — check for kernel-level errors (OOM kills, hardware errors, driver issues).
6. If it's a runaway process: kill -9 <PID> as last resort.

top/htop → PIDstrace = what it's doingdmesg = system errors
S02"No space left on device" error, but df -h shows 20% disk space free. What's going on?▼
APPROACH
This is the classic inode exhaustion problem — and interviewers love it because most people don't know it exists.

Every file on Linux takes up one inode (an index node — metadata entry). You can have physical disk space free but run out of inodes if there are millions of tiny files.

Verify: df -i — shows inode usage. If Use% is 100% on a filesystem, that's your culprit.
Find the directory: find / -xdev -printf '%h\n' | sort | uniq -c | sort -rn | head — shows which directory has the most files.

Second possibility: A deleted file is being held open by a running process — the disk space isn't reclaimed until the process closes the file handle.
Check: lsof | grep deleted — find processes holding deleted file handles. Restart that process to free the space.

df -i = inode usageinode exhaustion = millions of tiny fileslsof | grep deleted = held-open files
S03The OOM killer keeps terminating your main application. How do you troubleshoot and fix it?▼
APPROACH
1. Confirm the OOM killer fired:
dmesg | grep -i "oom\|killed" — you'll see "Out of memory: Kill process <PID> (<name>)"
cat /var/log/syslog | grep oom-killer

2. Investigate the cause:
• Memory leak? — watch free -h over time. If memory steadily climbs, the app has a leak. Profile it.
• Container limits too low? — if containerized, the cgroup memory limit might be set lower than the app needs. Check docker stats or kubectl describe pod for resource limits.
• Server genuinely lacks RAM? — the app's actual requirements exceed the server's memory. Scale up or optimize.

3. Short-term fix: Increase memory limits or add swap (not ideal but buys time).
4. Long-term fix: Fix the memory leak, right-size container limits, or upgrade instance.

S05Service can't connect to database. What's the difference between "Connection Refused" and "Connection Timeout"?▼
APPROACH
This tests TCP/IP fundamentals — a classic question.

Connection Refused — the packet reached the destination, but nothing is listening on that port. The server actively rejected it. Causes: DB service is down, DB is bound to 127.0.0.1 (localhost only) instead of 0.0.0.0.
Debug: Is the DB process running? What IP is it bound to? (ss -tlnp | grep 5432)

Connection Timeout — the packet never arrived or was silently dropped. No response at all. Causes: firewall blocking, security group denying traffic, wrong IP/port, routing issue.
Debug: Check security groups/firewall rules. Can you reach the host at all? (ping <db-host>)

Test both: telnet <db-host> 5432 or nc -zv <db-host> 5432

Refused = reached but nothing listeningTimeout = packet never arrivednc -zv to test TCP connectivity
S06Ping by hostname fails. Ping by IP works. nslookup resolves correctly. What's the issue?▼
APPROACH
This tests DNS resolution order — a subtle but important distinction.

nslookup queries DNS directly. But ping uses the OS resolver, which follows the resolution order defined in /etc/nsswitch.conf.

The OS might be checking /etc/hosts BEFORE querying DNS. If there's a stale or incorrect entry for that hostname in /etc/hosts, ping will use that wrong IP and fail — while nslookup queries DNS directly and gets the correct answer.

1. cat /etc/hosts — is there a hardcoded entry for this hostname with a wrong IP?
2. cat /etc/nsswitch.conf — check the hosts: line. It likely says files dns — meaning check files (/etc/hosts) first, then DNS.
Fix: Remove the bad entry from /etc/hosts, or reorder nsswitch.conf to query DNS first.

nslookup = DNS directping = OS resolver ordercheck /etc/hosts for stale entry/etc/nsswitch.conf = resolution order

S07A pod is stuck in CrashLoopBackOff. Walk through the exact commands.▼
APPROACH
1. kubectl get pods — confirm the state. CrashLoopBackOff means the container starts, crashes, K8s tries to restart, crashes again, with increasing delays.
2. kubectl describe pod <name> — read the Events section. Look for liveness probe failures, missing secrets/configmaps, resource limit kills.
3. kubectl logs <pod> --previous — crucial: shows logs of the container before it crashed. Current logs may be empty if the crash is immediate.
4. Common causes:
• App error on startup (bad env var, missing config, DB not reachable)
• Liveness probe misconfigured (fails before app is ready)
• Secret/ConfigMap referenced but doesn't exist
• OOMKilled — container hit memory limit

S08Pod is stuck in ImagePullBackOff. What are the potential reasons?▼
APPROACH
ImagePullBackOff = the worker node is trying to pull your Docker image and failing.

Reason 1 — Typo in image name or tag: Most common. myapp:lates instead of myapp:latest. Double-check the image name in your deployment YAML.

Reason 2 — Node can't reach the registry: Worker node has no internet access to Docker Hub / ECR. Check network/security group rules from the node.

Reason 3 — Private registry, missing imagePullSecrets: The registry requires authentication, but the pod spec doesn't have imagePullSecrets pointing to the credentials secret.
Fix: Create a K8s Secret with registry credentials and add imagePullSecrets to the deployment.

Debug: kubectl describe pod <name> — the Events section will say "Failed to pull image" with the exact reason.

🔧 CI/CD & Infrastructure Scenarios
S10CI pipeline fails randomly ~10% of the time on integration tests. How do you fix flaky tests?▼
APPROACH
Do NOT just add retries — that masks the problem and makes the pipeline non-deterministic.

Find the pattern: Which tests? Which CI runner? What time of day? Collect data.

Common root causes:
• Shared state: Multiple test runs hitting the same database and stepping on each other's data. Fix: each test run gets its own isolated DB/schema.
• Race conditions: Tests that depend on async operations completing without proper waits.
• External API timeouts: Tests calling real external services. Fix: mock them.
• CI runner resource starvation: CPU/memory contention between parallel jobs.

Reproduce locally: Run the failing test in an isolated Docker container to match the CI environment.

no retries = fix the root causeshared state = isolated DB per runmock external APIs
S11Docker build pipeline went from 2 minutes to 15 minutes. What do you investigate?▼
APPROACH
1. Check the Dockerfile first: Did someone change an instruction high up in the file (like adding an ENV, modifying a COPY, or changing a RUN command) that is busting the Docker layer cache? If a layer high in the file changes, every subsequent layer must rebuild. If the COPY command that copies source code was moved above the npm install step, every commit now reinstalls all dependencies.

2. Check CI runner health: Is the runner starved for CPU or disk I/O? top during the build — is something competing for resources?

3. Is the cache actually being used? Many CI systems don't persist Docker layer cache between runs by default. You may need to explicitly configure BuildKit cache mounts or use a registry-based cache.

4. New large dependency added? A massive npm/pip install that didn't exist before?

layer cache busted = most commonorder matters: deps before codeCI runner resource starvation

S14EC2 instance gets "Access Denied" trying to write to S3. Walk through checking permissions.▼
APPROACH
IAM permission debugging is layered — check each layer in order:

1. IAM Role on EC2: Go to EC2 → check the attached Instance Profile. Does it have a Role? Does that Role have a policy with s3:PutObject on this bucket?

2. S3 Bucket Policy: Even if the IAM role allows it, the bucket policy can explicitly DENY access. An explicit Deny overrides any Allow. Check the bucket's Permissions → Bucket Policy.

3. KMS Encryption: If the bucket uses KMS encryption, the EC2 role also needs kms:GenerateDataKey and kms:Decrypt permissions on that specific KMS key.

4. VPC Endpoint / Network: If the bucket has a VPC endpoint policy, the EC2 might be blocked at the network level.

Tip: Use AWS IAM Policy Simulator to test permissions without making real API calls.

🌐 The "google.com" Question
S16What happens exactly when you type google.com into your browser and hit Enter?▼
APPROACH
This tests DNS, networking, HTTP, and server knowledge end-to-end.

1. Browser cache: Is google.com already cached from a recent visit?
2. DNS Resolution: Browser asks OS → OS checks /etc/hosts, then queries the local DNS resolver → resolver checks its cache → queries root nameservers → TLD nameservers (.com) → Google's authoritative nameserver → returns IP address (e.g., 142.250.80.46).
3. TCP Connection: Browser opens a TCP connection to port 443 (HTTPS) via a 3-way handshake (SYN → SYN-ACK → ACK).
4. TLS Handshake: Client and server negotiate encryption. Server sends its TLS certificate. Browser verifies it against a CA. Session keys are exchanged.
5. HTTP Request: Browser sends GET / HTTP/2 Host: www.google.com
6. Load Balancer: Request hits Google's edge load balancer, routes to a backend server.
7. Response: Server returns HTML. Browser parses it, finds CSS/JS/image references, and makes more requests for those resources.
8. Render: Browser constructs the DOM, applies CSS, runs JS, displays the page.

DNS → TCP → TLS → HTTP → LB → server → render
🐳 Docker Scenarios
S17Your Docker container exits immediately after starting. How do you debug it?▼
APPROACH
1. docker ps -a — lists all containers including exited ones. Check the STATUS column — see the exit code. Exit code 0 = clean exit. Exit code 1 = error. Exit code 137 = OOM killed (out of memory).

2. docker logs <container-id> — read the output the container produced before dying. This usually has the actual error.

3. docker inspect <container-id> — look at the State section. Check ExitCode, OOMKilled, Error.

Common causes:
• CMD/ENTRYPOINT error — process exits immediately if the startup command fails
• Missing environment variable — app crashes on start because DB_URL is not set
• Missing required file — app can't find config file that wasn't COPYed into image
• Port already in use — app can't bind to the port
• OOMKilled — container hit memory limit

docker ps -a → exit codedocker logs → actual errorexit 137 = OOM killed
S18Your Docker image is 3GB. A teammate asks how to reduce it. What do you suggest?▼
APPROACH
1. Use a smaller base image: Switch from node:18 (~350MB) to node:18-alpine (~50MB). Alpine Linux is minimal by design.

2. Multi-stage build: Build in a heavy image, copy only the compiled artifact into a minimal production image. Build tools (compilers, npm dev-deps) stay in the builder stage and are discarded.

3. Add .dockerignore: Exclude node_modules/, .git/, tests/, docs/, *.md from being COPYed into the image.

4. Combine RUN commands: Each RUN = a layer. RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/* — install and clean up in one layer, not three.

5. Don't install dev dependencies in prod: npm install --omit=dev or pip install --no-dev.

alpine base = tinymulti-stage = only artifact.dockerignore = exclude junkcombine RUN layers
S19Two Docker containers need to communicate. Container A can't reach Container B. How do you debug?▼
APPROACH
1. Check if they're on the same network: docker network ls then docker inspect <network-name>. If containers are on different networks, they can't talk by default.

2. If using docker-compose: Services in the same docker-compose.yml are automatically on a shared network and can reach each other by service name (e.g., http://db:5432).

3. Manual network connection: docker network connect my-network container-b

4. Test from inside container A: docker exec -it container-a sh then ping container-b or curl http://container-b:3000. Use service/container name, not IP — IPs change on restart.

5. Check EXPOSE/port mapping: EXPOSE in Dockerfile just documents the port — it doesn't bind it. For external access use -p 3000:3000. Container-to-container on same network doesn't need -p.

☸️ Kubernetes Scenarios
S20A pod is in Pending state and never starts. How do you debug it?▼
APPROACH
Pending means the Scheduler cannot find a suitable node to place the pod.

1. kubectl describe pod <name> → read the Events section. It will say exactly why it's pending.

Common causes:
• "Insufficient CPU/memory" — the pod's resource request exceeds available capacity on all nodes. Fix: reduce requests, add nodes, or reduce other pod limits.
• "No nodes matching nodeSelector/affinity" — pod has a label constraint that no node satisfies. Fix: check your nodeSelector.
• "Unschedulable" — node is tainted and pod has no matching toleration. Fix: add toleration or remove taint.
• "PVC not bound" — pod needs a Persistent Volume Claim that hasn't been fulfilled. Fix: check kubectl get pvc.

2. kubectl get nodes — are all nodes Ready? A NotReady node won't accept pods.

Pending = Scheduler can't place poddescribe pod → Events sectioncheck resources, taints, PVC
S21Your Kubernetes cluster is running out of resources. Pods keep failing to schedule. What do you do?▼
APPROACH
1. Verify the problem: kubectl top nodes — which nodes are at capacity? kubectl describe nodes — look for "Allocatable" vs "Requests" section.

2. Find resource hogs: kubectl top pods --all-namespaces --sort-by=memory — which pods are consuming the most?

3. Right-size pod requests: Are pods requesting 4GB but only using 200MB? Over-requesting waste cluster capacity. Reduce requests to match actual usage.

4. Add nodes:
• AWS EKS: add to the Auto Scaling Group (manually or via cluster-autoscaler)
• kubectl scale won't help — that scales pods, not nodes

5. Enable Cluster Autoscaler: Watches for unschedulable pods and automatically provisions new EC2 instances. Scales down when nodes are underutilized.

6. Evict idle pods: Check for pods in namespaces you might have forgotten to clean up.

kubectl top nodesreduce over-requestingcluster-autoscaler for auto-scale

APPROACH
Immediate rollback (do this first):
kubectl rollout undo deployment/myapp — rolls back to the previous version immediately. Kubernetes keeps the last 10 revision history by default.

S23A pod is OOMKilled repeatedly. What does it mean and how do you fix it?▼
APPROACH
OOMKilled = Out Of Memory Killed. The container exceeded its memory limit and was forcibly terminated by the Linux kernel (OOM killer). The pod will restart, hit the limit again, get killed again — CrashLoopBackOff.

Verify: kubectl describe pod <name> → look for OOMKilled: true in the State section.

Investigate:
• kubectl top pods — what was the actual memory usage before it was killed?
• Check application code — is there a memory leak? Does memory grow over time or spike suddenly?

Fix options:
• Short term: Increase the memory limit in the pod spec. limits.memory: "1Gi" instead of "512Mi".
• Long term: Fix the memory leak. Profile the app, find what's growing, and fix it in code.

S24A developer accidentally pushed API keys to a public GitHub repo. What do you do immediately?▼
APPROACH
Assume the secret is already compromised — bots scan GitHub 24/7 and pick up leaked secrets within seconds. Deleting the commit is NOT enough — the history exists and the key is already stolen.

Immediate actions (do in parallel):
1. Revoke the key IMMEDIATELY — go to AWS Console → IAM → Access Keys → Deactivate/Delete the compromised key. This is the most critical step. Do it before anything else.

2. Rotate all affected credentials — create a new key for the service that needed it. Update all places that were using the old key.

3. Check for unauthorized activity — AWS CloudTrail will show what API calls were made with the leaked key. Look for unusual regions, services, or large data exfil.

4. Make the GitHub repo private (if not already) and use git filter-branch or BFG Repo Cleaner to remove the secret from history (prevents future accidental exposure).

5. Post-mortem + Prevention — add .env to .gitignore. Use GitHub's secret scanning. Add pre-commit hooks to detect secrets before commit (tools: git-secrets, truffleHog).

S25An EC2 instance can't connect to your RDS database. Walk through your debug steps.▼
APPROACH
Work through the layers systematically:

1. Is RDS actually running? AWS Console → RDS → check Status. Is it Available? If Stopped, start it. If Failing Over, wait.

2. Network connectivity: From the EC2, try nc -zv <rds-endpoint> 5432. Connection Refused or Timeout?

6. Check RDS parameter group: Is the DB accepting connections on the expected port?

S26Your Terraform state file is corrupted or locked. How do you handle it?▼

State file locked (most common): A previous terraform apply crashed and left a lock in DynamoDB. Terraform says "Error acquiring the state lock."
Fix: terraform force-unlock <LOCK_ID> (the lock ID is shown in the error message). Only do this if you're certain no other apply is running.

S28Your RDS database CPU is at 100%. How do you diagnose and respond?▼
APPROACH
Immediate (stop the bleeding):
1. AWS Console → RDS → Enhanced Monitoring or Performance Insights — see which queries are consuming the CPU.
2. Identify and kill the most expensive query: connect to the DB and run SELECT * FROM pg_stat_activity ORDER BY duration DESC; (Postgres). Kill with SELECT pg_terminate_backend(pid);.

Diagnose root cause:
• Missing index: A query is doing a full table scan. Check with EXPLAIN ANALYZE. Add an index on the column being filtered.
• Sudden traffic spike: More connections = more queries. Scale up the instance type or add a read replica for read-heavy workloads.
• N+1 query problem: App code making hundreds of queries in a loop where one query would do.
• Runaway scheduled job: A background job launched a massive query.

Longer term: Enable slow query log, add connection pooling (PgBouncer), add read replicas for read traffic, cache frequently-read data in Redis/ElastiCache.

S29Your CI/CD pipeline is deploying but the new code isn't reflecting in production. You've already ruled out browser cache. What next?▼

1. Was the right image built? Check the CI logs — did the Docker build actually pick up your latest code? Or did it use a cached layer that skipped your changes?

S30You need to investigate an EC2 instance but port 22 is closed and you can't SSH. How do you get in?▼
APPROACH
Port 22 being closed is actually a good security practice. There are proper alternatives:

Option 1 — AWS Systems Manager Session Manager (best practice):
AWS Console → EC2 → Select instance → Connect → Session Manager. Opens a browser-based terminal session. No port 22 needed, no inbound security group rules, full audit log in CloudTrail. Requires SSM agent on instance (pre-installed on Amazon Linux 2+) and correct IAM role.

Option 2 — EC2 Instance Connect:
AWS Console → EC2 → Connect → EC2 Instance Connect. AWS pushes a temporary SSH key. Still requires port 22 but only from AWS IP ranges (not 0.0.0.0/0).

Option 3 — Bastion Host:
SSH into a bastion/jump host in the public subnet (which has port 22 open but restricted to your IP), then SSH from there to the private EC2.

Option 4 — EC2 Serial Console:
For instances that won't boot or are completely unreachable. Low-level access via AWS Console.

S31Your application suddenly starts throwing "too many open files" errors on Linux. What's happening?▼
APPROACH
Linux limits the number of file descriptors a process can have open simultaneously (files, network connections, sockets all count). When the limit is hit, the process can't open new connections or files.

1. Check current limits:
ulimit -n — shows current per-process limit (often 1024 by default)
cat /proc/<PID>/limits — limits for a specific process

2. Check actual usage:
lsof -p <PID> | wc -l — how many files/connections the process has open

3. Fix temporary:
ulimit -n 65536 — increase limit for current session

4. Fix permanent:
