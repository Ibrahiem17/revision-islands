QF01What is the difference between a process and a thread?▼
ANSWER
A process is an independent program in execution with its own memory space. Isolated from other processes. If it crashes, it doesn't affect others.

A thread is a unit of execution within a process. Threads share the same memory space. Faster to create, faster to communicate — but one bad thread can crash the whole process.

process = isolated, own memorythread = shared memory, lighter
QF02What is the difference between virtualization and containerization?▼
ANSWER
Virtualization — a hypervisor (VMware, KVM) creates full virtual machines. Each VM has its own OS kernel, hundreds of MBs or GBs of overhead. Strong isolation.

Containerization — containers share the host OS kernel. Only the app + dependencies are isolated. Much lighter (MBs), starts in milliseconds, higher density (run 100 containers vs 10 VMs on same hardware).

Containers trade some isolation for speed and efficiency. VMs are preferred when you need complete OS isolation.

VM = full OS, heavy, strong isolationcontainer = shared kernel, lightweight, fast
QF03What is idempotency and why does it matter in DevOps?▼
ANSWER
An operation is idempotent if running it multiple times produces the same result as running it once.

Why it matters: CI/CD pipelines can retry failed steps. If your deploy script isn't idempotent, running it twice might create duplicate resources, corrupt state, or break things. Terraform applies are idempotent — running terraform apply 10 times always results in the same infrastructure. Ansible playbooks are idempotent — re-running them doesn't break things.

run once = run many = same resultTerraform + Ansible = idempotentcritical for retries in CI/CD
QF04What is immutable infrastructure?▼
ANSWER
Never patch, update, or modify a running server. Instead, build a new one from scratch with the desired configuration, deploy it, then destroy the old one.

Why: If you keep patching the same server over months, it accumulates differences from the original — "configuration drift." Debugging is a nightmare because each server is a unique snowflake. Immutable infra ensures every server is identical and predictable.

Docker + Kubernetes naturally enforce this — you update the image and roll out new pods rather than SSHing into running containers to apply patches.

build new, destroy oldno configuration driftDocker enforces this naturally
QF05What is the difference between authentication and authorization?▼
ANSWER
Authentication (AuthN) — verifying who you are. Proving identity. Username + password, SSH key, OAuth token. "Are you really Ibrahiem?"

Authorization (AuthZ) — determining what you're allowed to do. Given that I know who you are, what permissions do you have? IAM policies, RBAC roles. "Ibrahiem is allowed to read S3 but not delete EC2."

AuthN always happens before AuthZ.

AuthN = who are you?AuthZ = what can you do?AuthN first, then AuthZ
QF06What is the difference between stateful and stateless applications?▼
ANSWER
Stateless — each request is independent. The server doesn't remember previous requests. Any replica can handle any request. Easy to scale horizontally — just add more pods. Examples: REST APIs, web servers.

Stateful — the server remembers something between requests (session state, data). Requests from the same client must go to the same server (sticky sessions) or data must be shared (centralized session store, database). Harder to scale. Examples: databases, Kafka, anything with in-memory state.

DevOps implication: Stateless = Deployment (any replica identical). Stateful = StatefulSet (stable identity + persistent volume per pod).

stateless = any replica handles requeststateful = needs sticky session or shared data
QF07What is a race condition? How do you prevent it?▼
ANSWER
A race condition occurs when two processes/threads access shared data simultaneously and the outcome depends on the order of execution — which is unpredictable.

DevOps context: Two CI pipelines deploying at the same time, both reading and writing the same Terraform state file. Whichever runs second might overwrite the first's changes.

Prevention: State locking. Terraform + S3 remote state uses a DynamoDB lock table — only one pipeline can run terraform apply at a time. Any other attempt is blocked until the lock is released.

concurrent access to shared dataTerraform = DynamoDB lockprevent with locks/queues
QF08What are the 4 Golden Signals and what tool tracks them?▼
ANSWER
From Google's SRE book — the 4 signals that define the health of any service:

Latency — how long requests take. Track p50, p95, p99. p99 = 99% of requests are faster than this. High p99 with low p50 = outlier problem.
Traffic — requests per second. Establishes baseline. Sudden drops = traffic not reaching app. Sudden spikes = potential attack or viral traffic.
Errors — rate of failed requests (4xx/5xx). Anything above baseline = something is wrong.
Saturation — how "full" your system is. CPU %, memory %, queue depth. At 100% = system is overloaded.

Tracked with: Prometheus (collects) → Grafana (visualizes) → Alertmanager (alerts).

Latency + Traffic + Errors + SaturationPrometheus → Grafana
QF09What is a TCP 3-way handshake?▼
ANSWER
Before TCP can transfer data, it establishes a connection via a 3-step process:

1. SYN — Client sends a SYN (synchronize) packet to server: "I want to connect."
2. SYN-ACK — Server responds with SYN-ACK: "I acknowledge your SYN and I'm ready."
3. ACK — Client sends ACK: "I acknowledge your SYN-ACK. Connection established."

After this, data transfer begins. This is why TCP adds latency vs UDP — that 3-step handshake takes time. HTTPS adds the TLS handshake on top.

SYN → SYN-ACK → ACKestablishes reliable connectionhappens before every TCP connection
QF10What is the OSI model and which layers matter most for DevOps?▼
ANSWER
The OSI model has 7 layers describing how network communication works. The most relevant for DevOps:

Layer 7 (Application) — HTTP, HTTPS, DNS, SSH. Where you spend most time. ALB, API routing, CDN.
Layer 4 (Transport) — TCP/UDP, port numbers. Security Groups operate here. NLB. Connection refused vs timeout debugging.
Layer 3 (Network) — IP addressing, routing. VPC, subnets, route tables, NAT Gateway.

When debugging: start at L3 (can I reach the IP?) → L4 (is the port open?) → L7 (is the app responding correctly?).

L7 = HTTP/apps/ALBL4 = TCP/ports/Security GroupsL3 = IP/VPC/routing
QF11What are DORA metrics and why do interviewers ask about them?▼
ANSWER
DORA (DevOps Research & Assessment) identified 4 metrics that predict engineering team performance:

Deployment Frequency — how often you deploy to production. Elite = multiple times per day.
Lead Time for Changes — commit → production time. Elite = under 1 hour.
MTTR (Mean Time to Restore) — how fast you recover from incidents. Elite = under 1 hour.
Change Failure Rate — % of deployments causing production issues. Elite = 0-15%.

Interviewers ask because these metrics show whether your DevOps practices are actually working. Knowing them shows you think like an SRE, not just an operator.

deploy frequency + lead time + MTTR + failure rateelite = fast and reliable
QF12What is GitOps?▼
ANSWER
GitOps is an operating model where Git is the single source of truth for both application code AND infrastructure configuration (Kubernetes manifests, Helm charts).

A GitOps tool (ArgoCD, FluxCD) continuously watches the Git repo. When you merge a change, the tool automatically syncs the Kubernetes cluster to match. If someone manually changes something in the cluster, the tool detects the drift and reconciles back to Git.

Key benefit: Rollback is just a git revert. Full audit trail in Git history. No manual kubectl commands in production.

Git = single source of truthauto-sync to clusterdrift = auto-reconcile to Git
QF13What is a liveness probe vs readiness probe in Kubernetes?▼
ANSWER
livenessProbe — "Is this container alive?" Detects deadlocks, stuck processes, corrupted state. If it fails, Kubernetes restarts the container. Imagine an app that appears to be running but is stuck in an infinite loop — liveness catches this.

readinessProbe — "Is this container ready to serve traffic?" Detects when an app hasn't finished starting up yet (loading DB connections, warming caches). If it fails, the pod is removed from the Service's endpoints — no traffic is sent to it, but it's not restarted. Once it passes again, traffic resumes.

Combined: Readiness gates traffic in; liveness keeps the container healthy over time.

liveness fail → restart containerreadiness fail → remove from load balancer
QF14Where and how should you store secrets in a CI/CD pipeline?▼
ANSWER
NEVER: Hardcode in source code, Dockerfile, or commit to Git (even private repos — attackers scan these constantly).

In GitHub Actions: Store in Settings → Secrets and Variables → Actions. Reference as ${{ secrets.DB_PASSWORD }}. GitHub automatically masks them in logs.

In production apps: Use AWS Secrets Manager or Parameter Store. App fetches at runtime via SDK — never in the image itself.

For Kubernetes: Use Sealed Secrets (encrypt before committing) or External Secrets Operator (sync from AWS Secrets Manager to K8s Secrets).

never in code or GitGitHub Actions = repository secretsprod = AWS Secrets Manager or Vault
QF15What is an error budget and how does it change engineering decisions?▼
ANSWER
If your SLO is 99.9% availability, your error budget is 0.1% downtime (about 8.7 hours per year). This is the amount of unreliability you're allowed to have.

How it changes decisions:
• Error budget is full → ship features, take risks, move fast.
• Error budget is depleted → freeze new features, focus entirely on reliability and fixing tech debt.

It creates a concrete, measurable way for dev and ops teams to negotiate: "We can ship this risky feature if we have budget. We can't if we don't." Removes politics from reliability discussions.

SLO = 99.9% → budget = 0.1% downtimefull budget = ship fastempty budget = fix reliability
