1️⃣ 📍 IP Addressing ⭐⭐⭐⭐⭐
An IP address is just a machine's "phone number" on a network. Every device gets one — a private one (like 192.168.1.100) that only works inside your own network, and often a public one that the whole internet can see. 127.0.0.1 is special — it always means "this machine, talking to itself." CIDR notation like /24 says how many addresses are in a block — the deep math is in the 🌐 Networking tab; here, just recognize it when you see it.
🧪 Build a lab: Run ip addr on your own machine, and separately run curl ifconfig.me. Write down both numbers. One is your private IP (only your router/home network can reach it) — the other is your public IP (what the entire internet sees you as). If you're behind a router — which almost everyone is — these two numbers will be completely different. That difference is the whole lesson.
2️⃣ 🌍 DNS ⭐⭐⭐⭐⭐
DNS is the internet's phonebook — it turns a name like google.com into an IP address, because humans remember names and computers need numbers. An A record maps a name to an IPv4 address (the most common one). AAAA does the same for IPv6. CNAME points one name at another name instead of an IP. MX says where email for a domain should go. TXT holds arbitrary text, often used to prove you own a domain.
🧪 Build a lab: Run dig (or nslookup) against three different domains — github.com, google.com, and amazon.com — and write down the IP address each one resolves to. Notice they're all completely different numbers, run by completely different companies, and DNS is the only reason typing a name instead of a raw IP works at all.
3️⃣ 🔌 Ports ⭐⭐⭐⭐⭐
If an IP address is a building, a port is the specific apartment number inside it — one machine can run many services at once, each one "listening" on its own port. A port is listening if something is actively waiting for connections on it, and closed if nothing is. Worth memorizing: 22 SSH · 53 DNS · 80 HTTP · 443 HTTPS · 3306 MySQL · 5432 PostgreSQL · 6379 Redis · 27017 MongoDB.
🧪 Build a lab: Start any tiny local web server (even python3 -m http.server 3000 works) so it's listening on port 3000. Open http://localhost:3000 in a browser to confirm it responds — then, in a terminal, use ss -tuln to find port 3000 in the listening list, and lsof -i :3000 to see exactly which process owns it. Stop the server and run both commands again — notice port 3000 disappears from both.
4️⃣ 🔀 TCP vs UDP ⭐⭐⭐⭐⭐
TCP is reliable and connection-oriented — it checks every piece of data arrived, in order, and resends anything lost. Slower, but nothing goes missing. UDP is connectionless and faster — it just fires data and doesn't look back. Nothing is guaranteed to arrive, but there's no handshake overhead either. Neither is "better" — they're for different jobs.
🧪 Build a lab: Without looking it up, guess whether each of these is TCP or UDP, then check your reasoning: SSH, HTTP, DNS, a live video call. (Answer: SSH → TCP, HTTP → TCP — a dropped byte in a web page would actually break it. DNS → UDP, video calls → UDP — speed matters more than a perfectly reliable single lookup or frame.) The pattern: anything where losing a little data is fine, but delay isn't, leans UDP — everything else leans TCP.
5️⃣ 🌐 HTTP and HTTPS ⭐⭐⭐⭐⭐
Every web request is a request going out and a response coming back — each one has headers (metadata) and often a body (the actual content). The method says the intent: GET read, POST create, PUT/PATCH update, DELETE remove. The status code says the outcome: 200/201 success, 301 redirected, 400/401/403/404 a problem with the request, 500/502/503 a problem on the server. HTTPS is the exact same thing, wrapped in TLS/SSL encryption using a certificate, so nobody in between can read or tamper with it.
🧪 Build a lab: Make a tiny Express API — literally just app.get("/", (req, res) => res.send("Hello")) — run it locally, then hit it three different ways: curl localhost:3000 (see the body), curl -I localhost:3000 (see only the status/headers), and curl -v localhost:3000 (see the entire request AND response). Same endpoint, three completely different levels of detail.
6️⃣ 🔑 SSH ⭐⭐⭐⭐⭐
SSH is how you remotely log into another machine's terminal, securely. Password authentication works but is weaker and annoying to type every time. SSH keys are the real-world default: a private key that stays on your machine forever and a public key you copy onto every server you want to access — the server can verify it's really you without a password ever crossing the network.
🧪 Build a lab: Launch a small AWS EC2 instance (the ☁️ VPC & EC2 tab covers this in depth), generate a key pair with ssh-keygen if you haven't already, and connect to your new instance with ssh -i your-key.pem user@your-instance-ip. The moment your terminal prompt changes to show the instance's hostname, you're genuinely operating a real remote computer.
7️⃣ 🛡️ Firewalls ⭐⭐⭐⭐⭐
A firewall decides what traffic is allowed in or out. Inbound is traffic coming TO this machine; outbound is traffic leaving it. An allow rule lets specific traffic through; a deny rule blocks it. The golden rule everywhere in DevOps: only open exactly the ports that need to be open.
🧪 Build a lab: With your Node app running on port 3000, block it with sudo ufw deny 3000 and try to reach it — it should now time out or refuse the connection, even though the app itself is still running fine. Then run sudo ufw allow 3000 and try again — it works instantly. This is the clearest possible proof that "the app is running" and "the app is reachable" are two completely separate questions.
8️⃣ 🛣️ Routing ⭐⭐⭐⭐
A router forwards traffic between networks. Every machine has a default gateway — the router it sends anything to when it doesn't have a more specific route. The routing table is the actual list of rules deciding where each destination's traffic goes.
🧪 Build a lab: Run traceroute google.com and read every hop out loud, in order: your laptop → your router → your ISP → the wider internet → Google's own network. Each line is a real, physical (or virtual) network your request actually passed through in milliseconds — this is what "the internet" concretely is.
9️⃣ 🔁 Reverse Proxies (Nginx) ⭐⭐⭐⭐⭐
A reverse proxy sits in front of your real app and forwards ("proxies") requests to it — users only ever talk to the proxy, never directly to your app. This is also called port forwarding in the simplest case: taking a request on one port and quietly handing it to a different port behind the scenes.
🧪 Build a lab: With your Node app still running on port 3000, install Nginx and add the proxy_pass http://localhost:3000; config from the pill above. Reload Nginx, then visit your server on plain port 80 (no ":3000" in the URL) — you should see your app's exact response. Browser → Nginx → Node.js, three hops, one seamless response.
🔟 ⚖️ Load Balancing ⭐⭐⭐⭐
Load balancing exists because one server can only handle so much, and one server dying shouldn't take your whole app down with it. A load balancer distributes incoming traffic across several identical backends, which is exactly what gives a system high availability — no single point of failure.
🧪 Build a lab: Run two copies of the exact same tiny Node app — one on port 3000, one on port 3001 (each printing which port it's on, so you can tell them apart). Put Nginx in front of both using the upstream block from the pill above. Refresh the page in your browser a few times and watch the response alternate between "3000" and "3001" — that alternation IS load balancing, happening live in front of you.
1️⃣1️⃣ 📦 APIs and JSON ⭐⭐⭐⭐
A REST API is just a web server whose responses are meant to be read by code instead of a browser. JSON is the plain-text format almost every API speaks — nested keys and values, easy for both humans and programs to read. An API "request" and "response" are genuinely just HTTP, exactly like everything else in this tab.
🧪 Build a lab: Install jq (sudo apt install jq), then run curl https://jsonplaceholder.typicode.com/posts/1 and read the dense, one-line result. Now pipe the exact same command into jq and compare — same data, but suddenly indented and genuinely readable. This one habit will save you real time on every API you ever debug.
1️⃣2️⃣ ☁️ AWS Networking ⭐⭐⭐⭐⭐
A VPC is your own private network inside AWS — nothing in it is reachable by anyone until you explicitly allow it. Inside a VPC, subnets split it into smaller pieces — a public subnet can reach the internet, a private subnet can't (on purpose — that's where your database usually lives). An Internet Gateway is what actually provides that internet access. A Security Group acts like a firewall around individual resources. A Route Table controls where each subnet's traffic is allowed to go. This is genuinely everything above (IPs, ports, firewalls, routing) — just AWS's specific names for the same ideas. The ☁️ VPC & EC2 tab covers building these step by step in real depth.
VPC └─ Public subnet └─ Internet Gateway (gives it internet access) └─ Security Group (firewall around your instance) └─ EC2 instance ← your actual server
🧪 Build a lab: Following the ☁️ VPC & EC2 tab, create a VPC → a public subnet → attach an Internet Gateway → open a Security Group rule for port 22 (and 80, once your app is on it) → launch an EC2 instance inside that subnet. Then deploy your tiny Node app to it. Every single piece you just clicked through has a name from earlier in THIS tab — a VPC is a network, a subnet is a smaller network, a Security Group is a firewall, and SSH is still just SSH.
1️⃣3️⃣ 🧯 Troubleshooting ⭐⭐⭐⭐⭐ — Probably the Most Important Skill in This Whole Tab
When something breaks, you don't need to be a genius — you need to check things in order, one layer at a time, and stop as soon as you find the one that's actually broken. This exact order works for almost every "it's not working" networking problem you'll ever hit:
Application isn't working. │ ↓ Is the application running? → ps aux / ss -tuln │ ↓ Is the port open? → ss -tuln / lsof -i :port │ ↓ Can I ping the server? → ping <ip> │ ↓ Does DNS work? → dig / nslookup │ ↓ Can I SSH into it? → ssh user@ip │ ↓ Is the firewall blocking it? → sudo ufw status │ ↓ Is Nginx configured correctly? → cat /etc/nginx/sites-available/default │ ↓ Are the AWS Security Groups correct? → check inbound rules in the AWS console
