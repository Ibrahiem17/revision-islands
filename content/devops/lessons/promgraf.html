📡 PROMETHEUS — Deep Dive
🔄 Pull-Based Scraping
Prometheus pulls metrics from targets — targets don't push to Prometheus.

Each target exposes a /metrics HTTP endpoint. Prometheus hits it every 15s (configurable) and stores the data.

Why pull, not push? Prometheus knows if a target goes down (it stops responding). Push-based systems don't know if silence = healthy or dead.
🗄️ Time-Series Database (TSDB)
All data stored as metric_name + labels + timestamp + value.

Example entry: http_requests_total{method="GET", status="200", endpoint="/api"} 1452 1714000000

Labels let you slice data: "show me only POST errors on /login". Stored efficiently on disk — compresses well since values change slowly.
📏 4 Metric Types
Counter — only goes up. Total requests, total errors. Use rate() to get per-second rate.
Gauge — goes up and down. Current memory, active connections, queue size.
Histogram — samples observations into buckets. Request duration, response size. Enables p95/p99 latency.
Summary — like histogram but calculates quantiles client-side. Less flexible.
🎯 Service Discovery
In Kubernetes you don't hardcode targets. Prometheus uses service discovery to auto-find pods with the right annotations:

prometheus.io/scrape: "true"
prometheus.io/port: "3000"

Any new pod with these annotations gets automatically scraped.
📄 What a /metrics endpoint looks like
# HELP http_requests_total Total number of HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200",path="/api/users"} 8473
http_requests_total{method="POST",status="201",path="/api/users"} 312
http_requests_total{method="GET",status="404",path="/api/users"} 17
http_requests_total{method="POST",status="500",path="/api/login"} 3

# HELP process_resident_memory_bytes Resident memory size in bytes
# TYPE process_resident_memory_bytes gauge
process_resident_memory_bytes 52428800

# HELP http_request_duration_seconds HTTP request latency
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{le="0.05"} 7231
http_request_duration_seconds_bucket{le="0.1"} 7890
http_request_duration_seconds_bucket{le="0.5"} 8450
http_request_duration_seconds_bucket{le="+Inf"} 8473
💡 Prometheus scrapes this URL on your app every 15s and stores every line as a time-series data point. Your app exposes this — you add a library like prom-client (Node.js) or prometheus_client (Python).
🔍 PromQL — The Query Language
PromQL is how you ask Prometheus questions about your data. Grafana uses PromQL to build its panels. Alertmanager uses PromQL to decide when to fire alerts. You don't need to memorize all of it — you need to understand the patterns.
📈 Request Rate (most used)
# Requests per second over last 5 mins
rate(http_requests_total[5m])

# Only GET requests
rate(http_requests_total{method="GET"}[5m])

# Error rate (5xx only)
rate(http_requests_total{status=~"5.."}[5m])
rate() takes a counter (always increasing) and calculates per-second rate. Always use rate() on counters — never the raw value.
💾 Memory & CPU
# Memory used (bytes)
node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes

# Memory used %
(1 - (node_memory_MemAvailable_bytes /
      node_memory_MemTotal_bytes)) * 100

# CPU usage % (all cores, 5m avg)
100 - (avg by(instance)(
  rate(node_cpu_seconds_total{mode="idle"}[5m])
) * 100)
⏱️ Latency (p95 / p99)
# 95th percentile latency over 5m
histogram_quantile(0.95,
  rate(http_request_duration_seconds_bucket[5m])
)

# 99th percentile (the "worst" users)
histogram_quantile(0.99,
  rate(http_request_duration_seconds_bucket[5m])
)
p95 = 95% of requests are faster than this. Interviewers love when you talk p99 instead of average — average hides pain.
💽 Disk Usage
# Disk used %
(1 - (node_filesystem_avail_bytes{mountpoint="/"} /
      node_filesystem_size_bytes{mountpoint="/"})) * 100

# Predict when disk will fill (linear extrapolation)
predict_linear(
  node_filesystem_avail_bytes[6h], 4*3600
)
🐳 Container Metrics
# Container CPU usage
rate(container_cpu_usage_seconds_total{
  name="my-container"
}[5m])

# Container memory usage
container_memory_usage_bytes{name="my-container"}

# Kubernetes pod restarts (bad sign!)
kube_pod_container_status_restarts_total
🔢 Aggregation Functions
sum(metric)         # total across all instances
avg(metric)         # average
max(metric)         # worst case
min(metric)
count(metric)       # number of time series

# Group by a label:
sum by(endpoint)(rate(http_requests_total[5m]))
# → request rate per endpoint
⚙️ prometheus.yml — The Config File Explained
# prometheus.yml
global:
  scrape_interval: 15s          # how often to scrape all targets
  evaluation_interval: 15s      # how often to evaluate alert rules
  scrape_timeout: 10s

# Rules files (alert rules live here)
rule_files:
  - "alert_rules.yml"

# Alertmanager connection
alerting:
  alertmanagers:
    - static_configs:
        - targets: ['alertmanager:9093']

# What to scrape
scrape_configs:
  # Prometheus monitors itself
  - job_name: 'prometheus'
    static_configs:
      - targets: ['localhost:9090']

  # Linux server metrics via Node Exporter
  - job_name: 'node-exporter'
    static_configs:
      - targets: ['node-exporter:9100']

  # Your Node.js application
  - job_name: 'myapp'
    static_configs:
      - targets: ['app:3000']
    metrics_path: '/metrics'     # default — can be changed

  # Docker containers via cAdvisor
  - job_name: 'cadvisor'
    static_configs:
      - targets: ['cadvisor:8080']

  # Kubernetes auto-discovery
  - job_name: 'kubernetes-pods'
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: 'true'
🚨 Alert Rules — When Prometheus Pages You
# alert_rules.yml
groups:
  - name: application_alerts
    rules:

      # Fire if error rate > 1% for 5 minutes
      - alert: HighErrorRate
        expr: rate(http_requests_total{status=~"5.."}[5m]) > 0.01
        for: 5m                   # must be true for 5 mins before firing
        labels:
          severity: critical
        annotations:
          summary: "High error rate on {{ $labels.instance }}"
          description: "Error rate is {{ $value | humanizePercentage }}"

      # Fire if CPU > 80% for 10 minutes
      - alert: HighCPU
        expr: |
          100 - (avg by(instance)(
            rate(node_cpu_seconds_total{mode="idle"}[5m])
          ) * 100) > 80
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "High CPU on {{ $labels.instance }}"

      # Fire if disk will fill within 4 hours
      - alert: DiskFillingSoon
        expr: predict_linear(node_filesystem_avail_bytes[6h], 4*3600) < 0
        for: 30m
        labels:
          severity: warning
        annotations:
          summary: "Disk filling up on {{ $labels.instance }}"

      # Fire if pod is crash-looping
      - alert: PodCrashLooping
        expr: rate(kube_pod_container_status_restarts_total[15m]) > 0
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Pod {{ $labels.pod }} is crash-looping"
📬 Alertmanager — Route Alerts to Slack
# alertmanager.yml
global:
  slack_api_url: 'https://hooks.slack.com/services/YOUR/WEBHOOK'

route:
  group_by: ['alertname']
  group_wait: 30s               # wait before sending first alert in group
  group_interval: 5m            # time before re-sending grouped alerts
  repeat_interval: 4h           # time before re-sending unresolved alerts
  receiver: 'slack-notifications'

receivers:
  - name: 'slack-notifications'
    slack_configs:
      - channel: '#alerts'
        title: '{{ .GroupLabels.alertname }}'
        text: '{{ range .Alerts }}{{ .Annotations.description }}{{ end }}'
📊 GRAFANA — Deep Dive
🎨 What Grafana actually does
Grafana is purely a visualization layer. It stores no metrics itself.

It connects to data sources (Prometheus, CloudWatch, Loki, MySQL, ElasticSearch — 50+ supported) and turns query results into panels: graphs, gauges, stat numbers, tables, heatmaps, geo maps.
📋 Dashboards
A dashboard = collection of panels.
Each panel = a PromQL query + visualization type.

Variables — dropdowns at the top. $instance lets you switch which server you're viewing without editing queries. Defined as label values from Prometheus.
📦 Pre-built Dashboards (use these!)
grafana.com/dashboards has thousands of community dashboards. Import by ID:

6417 — Kubernetes pod resources
11074 — Node Exporter for Prometheus
🔔 Grafana Alerting
Grafana has its own alert engine (separate from Prometheus Alertmanager). You define alert rules on panels — if the PromQL value crosses a threshold, fire an alert.

Routes to Slack, PagerDuty, email, webhooks. In modern setups, teams pick one: Grafana alerts OR Prometheus Alertmanager. Not both.

🔧 Instrument Your App — Add /metrics to Node.js
Key insight: Prometheus can only collect metrics that your app exposes. You need to instrument your code — add a /metrics endpoint. This is a 10-minute task with the prom-client library. 
// Install: npm install prom-client
const express = require('express');
const client = require('prom-client');

const app = express();

// ── Auto-collect default Node.js metrics (CPU, memory, GC, etc.)
client.collectDefaultMetrics({ prefix: 'myapp_' });

// ── Custom counter: track HTTP requests
const httpRequests = new client.Counter({
  name: 'http_requests_total',
  help: 'Total number of HTTP requests',
  labelNames: ['method', 'route', 'status']
});

// ── Custom histogram: track request duration
const requestDuration = new client.Histogram({
  name: 'http_request_duration_seconds',
  help: 'Duration of HTTP requests in seconds',
  labelNames: ['method', 'route'],
  buckets: [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5]
});

// ── Middleware to auto-instrument all routes
app.use((req, res, next) => {
  const end = requestDuration.startTimer({ method: req.method, route: req.path });
  res.on('finish', () => {
    httpRequests.inc({ method: req.method, route: req.path, status: res.statusCode });
    end();
  });
  next();
});

// ── The /metrics endpoint Prometheus will scrape
app.get('/metrics', async (req, res) => {
  res.set('Content-Type', client.register.contentType);
  res.end(await client.register.metrics());
});

app.listen(3000);

🎯 Interview Q&A — Prometheus + Grafana
PG01"Why would you choose Prometheus over CloudWatch or Datadog?"▼
ANSWER
Prometheus advantages: Open source (free), runs on your infra (data never leaves), massively popular in Kubernetes ecosystems, huge community + pre-built dashboards, pull-based model gives better insight into target health.

CloudWatch advantages: Zero setup for AWS services (EC2, Lambda, RDS auto-report to it), tight AWS integration, managed service — no ops overhead.

Datadog advantages: Managed, one platform for metrics + logs + traces + APM, great UI, works across cloud providers. Expensive.

Real answer: Prometheus + Grafana for on-prem or K8s-heavy setups. CloudWatch when you're fully AWS serverless. Datadog when the company has money and wants one tool for everything.

Prometheus = free + K8s nativeCloudWatch = AWS managedDatadog = expensive but unified
PG02"What's the difference between a counter and a gauge? Give examples."▼
ANSWER
Counter — only ever increases (or resets to 0 on restart). Total requests served, total errors, total bytes sent. You never query the raw value — use rate(counter[5m]) to get a meaningful per-second rate.

Gauge — can go up or down freely. Current memory usage, current active connections, current temperature, queue depth. You query the raw value directly.

Memory trick: If the metric can decrease on its own during normal operation — gauge. If it only decreases when the app restarts — counter.

counter = total ever, use rate()gauge = current value, query directly
PG03"An alert fired for high memory at 3am. Walk me through your response."▼
ANSWER SCRIPT
"First I'd open Grafana and check the memory panel — is it still climbing or has it stabilized? I'd check the time range: did it start after a deployment? Did it correlate with a traffic spike?

I'd check container-level memory — which pod/container is consuming it. docker stats or kubectl top pods.

If memory is still climbing: check for a memory leak — is the app holding references it shouldn't? Restart the pod as a short-term fix. Open a ticket for root cause analysis.

If it was a one-time spike: check if a batch job ran. Was there an unusual traffic pattern? Document it and adjust the alert threshold if it was a false positive.

Post-incident: write a brief blameless post-mortem, note what the alert fired on, what caused it, what we fixed."

Grafana firstcorrelate with deploys/trafficcontainer-level drill-downblameless post-mortem
PG04"Why is average latency a bad metric? What should you use instead?"▼
ANSWER
Average hides the worst user experiences. If 999 requests take 10ms and 1 takes 10,000ms, the average is ~20ms — looks fine. But that 1 user had a terrible experience.

Use percentiles instead:
p50 (median) — half of users are faster/slower. Better than average.
p95 — 95% of users are faster than this. Your typical "slow" experience.
p99 — the experience of your worst 1%. Often what SLOs are written against.

PromQL: histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))

Interviewers love this answer — it shows you understand how real performance works.

average = hides outliersp95/p99 = real user experienceSLOs written against percentiles
PG05"What are the 4 Golden Signals and what would you alert on?"▼
ANSWER
1. Latency — how long requests take. Alert: p99 latency > 500ms for 5 minutes.

2. Traffic — how many requests per second. No alert directly — use it as context. A latency spike during 10x traffic is different from a spike during normal load.

3. Errors — error rate (4xx/5xx). Alert: error rate > 1% for 5 minutes. 5xx is user-facing failure. 4xx is usually client error (less critical unless it's 401 auth failures = potential attack).

4. Saturation — how full is the system. Alert: CPU > 80% for 10 minutes, memory > 85%, disk > 90%, connection pool utilization > 90%.

These come from Google's SRE book. Saying "4 Golden Signals" in an interview is an instant signal you've thought seriously about production systems.

latency + traffic + errors + saturationGoogle SRE origintraffic = context, not alert target
