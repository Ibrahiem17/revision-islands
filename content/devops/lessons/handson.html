🐳 TASK 1 — Containerize a Node.js App (End-to-End)
The Scenario: You have a Node.js app. Your interviewer says: "Containerize this so it runs the same everywhere — locally, on CI, and in production." Here's exactly what you do.
📁
STEP 01 Understand your app RECON
Before writing a single line of Dockerfile, answer 3 questions:
1. What runtime does it need? (Node 18? Python 3.11?)
2. What port does it listen on? (3000? 8080?)
3. What command starts it? (node index.js? npm start?)
💡 Say this out loud in your interview. It shows you think before you type — that's senior behavior.
📝
STEP 02 Write the Dockerfile DOCKERFILE
Create a file literally called Dockerfile (no extension) in your project root:
# 1. Base image — the OS + runtime your app needs
FROM node:18-alpine

# 2. Set the working directory INSIDE the container
WORKDIR /app

# 3. Copy dependency files FIRST (layer caching trick)
COPY package*.json ./

# 4. Install dependencies
RUN npm install --production

# 5. Copy the rest of your app code
COPY . .

# 6. Tell Docker which port your app uses
EXPOSE 3000

# 7. The command that starts your app
CMD ["node", "index.js"]
💡 Why COPY package.json BEFORE COPY . ? Docker caches layers. If your code changes but dependencies don't, it skips npm install on rebuild — saving minutes every time.
🚫
STEP 03 Add a .dockerignore OPTIMIZE
Create .dockerignore in your project root — tells Docker what NOT to copy into the image:
node_modules
.git
.env
*.log
README.md
💡 Without this, node_modules (sometimes 500MB+) gets copied in, bloating your image. This is a common interview gotcha.
🔨
STEP 04 Build the image docker build
Run this from the directory containing your Dockerfile:
# Syntax: docker build -t name:tag context
docker build -t myapp:latest .

# With your Docker Hub username (needed for pushing):
docker build -t ibrahiem/myapp:v1.0 .
Breaking it down:
-t myapp:latest → tag the image with name:version
. → build context (current directory)
💡 You'll see each Dockerfile instruction execute as a numbered step. Each step = one layer. Failed step = fix that layer and rebuild from cache.
▶️
STEP 05 Run the container docker run
Spin up a container from your image:
# Run detached + map port + name it
docker run -d -p 3000:3000 --name my-container myapp:latest

# Run with env variable
docker run -d -p 3000:3000 -e NODE_ENV=production myapp:latest
Port mapping: -p 3000:3000 = host:container
So localhost:3000 on your machine → hits port 3000 inside the container
💡 -d runs it in the background. Without it, logs flood your terminal and Ctrl+C kills the container.
🐛
STEP 06 Debug when things break DEBUG 
# See all containers (including stopped)
docker ps -a

# Read crash output
docker logs my-container

# Follow logs in real-time
docker logs -f my-container

# Open a shell INSIDE the running container
docker exec -it my-container sh

# Inspect container details (IP, env vars, mounts)
docker inspect my-container
💡 docker exec -it <name> sh is your "get inside the box" command — exactly like SSH into a server. Check files, test network, verify env vars.

⚡ TASK 4 — GitHub Actions: Auto Build & Push on Push to main
# .github/workflows/docker-build.yml
name: Build and Push Docker Image

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Log in to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ secrets.DOCKER_USERNAME }}/myapp:latest
⚠️ Secrets: Go to GitHub → Repo Settings → Secrets and Variables → Actions → add DOCKER_USERNAME and DOCKER_TOKEN. The workflow reads them as ${{ secrets.X }} — never visible in logs.

HO02"What's the difference between CMD and ENTRYPOINT in a Dockerfile?"▼
ANSWER
CMD = the default command to run. It can be fully overridden at docker run: docker run myapp node other.js replaces CMD entirely.

ENTRYPOINT = the executable that always runs. Arguments from docker run are appended to it, not replacing it.

Best practice combo: 
ENTRYPOINT ["node"]
CMD ["index.js"]
# docker run myapp           → node index.js
# docker run myapp server.js → node server.js
CMD = overridable defaultENTRYPOINT = always runscombine both for flexibility
HO03"How do you minimize Docker image size?"▼
ANSWER
4 techniques in order of impact:

1. Alpine base images — node:18-alpine is ~50MB vs node:18 at ~350MB.

2. Multi-stage builds — build in one stage, copy only output to a clean final stage. Dev deps never reach production: 
FROM node:18-alpine AS builder
WORKDIR /app
COPY . .
RUN npm install && npm run build

FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
CMD ["node", "dist/index.js"]
3. .dockerignore — exclude node_modules, .git, test files, logs.

4. Chain RUN commands — each RUN = one layer. Use && and clean up in the same layer.

HO05"How do containers differ from VMs?"▼
ANSWER
VMs virtualize hardware. Containers virtualize the OS.

VM: Each VM has its own full OS kernel. A hypervisor manages hardware. Heavy — gigabytes each, minutes to boot.

Container: All containers share the host OS kernel. Docker isolates processes using Linux namespaces and cgroups. Lightweight — megabytes, seconds to start.

The analogy: VMs = separate houses (own plumbing, electricity). Containers = apartments in one building — shared infrastructure, isolated living spaces.

VMs = full OS per instancecontainers = shared kernelcontainers = faster + lighterVMs = stronger isolation

🐧 TASK 5 — Set Up a Linux Server from Scratch
The Scenario: You just got SSH access to a fresh Ubuntu server. The interviewer says: "It's yours — secure it and make it production-ready."
① Update the system first
sudo apt update && sudo apt upgrade -y
Always start here. Stale packages = unpatched vulnerabilities.
② Create a non-root user
adduser ibrahiem
usermod -aG sudo ibrahiem
su - ibrahiem
Never run apps as root. Blast radius of a hack = everything if you do.
③ Set up SSH key auth
# On your LOCAL machine:
ssh-keygen -t ed25519 -C "ibrahiem@dev"
ssh-copy-id ibrahiem@SERVER_IP
Keys can't be brute-forced. Passwords can. Disable password auth after this.
④ Harden SSH config
# /etc/ssh/sshd_config
PermitRootLogin no
PasswordAuthentication no
Port 2222          # optional: change default port

sudo systemctl restart sshd
⑤ Configure UFW firewall
sudo ufw allow OpenSSH
sudo ufw allow 80      # HTTP
sudo ufw allow 443     # HTTPS
sudo ufw enable
sudo ufw status
Deny all by default, allow only what you need. Principle of least privilege.
⑥ Install & manage a service
sudo apt install nginx -y
sudo systemctl enable nginx   # start on boot
sudo systemctl start nginx
sudo systemctl status nginx
⑦ Monitor system health
top / htop          # CPU & memory live
df -h               # disk usage
free -h             # RAM usage
lsof -i :80         # what's using port 80?
journalctl -xe      # system logs
⑧ Set up cron job
crontab -e
# Run backup every day at 2am:
0 2 * * * /home/ibrahiem/backup.sh

# Check cron format: min hr day month weekday

⚡ TASK 8 — Full CI/CD Pipeline: Test → Build → Deploy
The Scenario: "Set up a pipeline that runs tests on every PR, and deploys to production only when merged to main." 
# .github/workflows/ci-cd.yml
name: CI/CD Pipeline

on:
  pull_request:
    branches: [main]          # runs tests on every PR
  push:
    branches: [main]          # deploys only when merged

jobs:
  # ─── JOB 1: Test (runs on every PR) ───────────────────────
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: '18'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci              # faster + stricter than npm install

      - name: Run tests
        run: npm test

      - name: Run linter
        run: npm run lint

  # ─── JOB 2: Build & Push (only on merge to main) ──────────
  build-and-push:
    needs: test                 # only runs if test job passes
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            ${{ secrets.DOCKER_USERNAME }}/myapp:latest
            ${{ secrets.DOCKER_USERNAME }}/myapp:${{ github.sha }}

  # ─── JOB 3: Deploy to EC2 ─────────────────────────────────
  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      - name: SSH into EC2 and redeploy
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.EC2_HOST }}
          username: ubuntu
          key: ${{ secrets.EC2_SSH_KEY }}
          script: |
            docker pull ${{ secrets.DOCKER_USERNAME }}/myapp:latest
            docker stop app || true
            docker rm app || true
            docker run -d -p 80:3000 --name app --restart=always \
              ${{ secrets.DOCKER_USERNAME }}/myapp:latest
Secrets needed: DOCKER_USERNAME, DOCKER_TOKEN, EC2_HOST (public IP), EC2_SSH_KEY (contents of your .pem file)
The flow: PR opened → tests run → PR blocked if fail → merge to main → build image → push to Hub → SSH into EC2 → pull new image → restart container ✅

🚨 K8s Pod Not Starting — Debug Flow
kubectl get pods                         # STATUS = CrashLoopBackOff / Pending / Error?
kubectl describe pod <pod-name>          # Events section at the bottom — the real error
kubectl logs <pod-name>                  # App crash output
kubectl logs <pod-name> --previous       # Logs from crashed previous instance
kubectl exec -it <pod-name> -- sh        # Shell into the pod (if it's running)

# Common causes:
# CrashLoopBackOff = app crashes on startup → check logs
# Pending = no node has enough resources → check resource requests
# ImagePullBackOff = image name wrong or registry auth missing
# OOMKilled = container exceeded memory limit → raise limits

🌐 TASK 11 — Configure Nginx as a Reverse Proxy
The Scenario: "Your Node app runs on port 3000. Make it accessible on port 80 (HTTP) so users don't need to type :3000." 
# /etc/nginx/sites-available/myapp
server {
    listen 80;
    server_name yourdomain.com www.yourdomain.com;

    location / {
        proxy_pass http://localhost:3000;    # forward to your app
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_cache_bypass $http_upgrade;
    }
}
# Enable the config (symlink to sites-enabled)
sudo ln -s /etc/nginx/sites-available/myapp /etc/nginx/sites-enabled/

# Test config for syntax errors BEFORE reloading
sudo nginx -t

# Apply config
sudo systemctl reload nginx

# Add HTTPS with Let's Encrypt (free SSL)
sudo apt install certbot python3-certbot-nginx -y
sudo certbot --nginx -d yourdomain.com
Why a reverse proxy? Your app can't run on port 80 without root (security risk). Nginx runs on 80 as root, then forwards to your unprivileged app on 3000. Bonus: Nginx also handles SSL termination, rate limiting, gzip compression, and can load balance across multiple app instances.
⌨️ TASK 12 — Write a DevOps Bash Script
The Scenario: "Write a script that checks if a service is running and restarts it if not." A classic DevOps automation task. 
#!/bin/bash
# healthcheck.sh — auto-restart a service if it dies

SERVICE="nginx"
LOG_FILE="/var/log/healthcheck.log"
TIMESTAMP=$(date '+%Y-%m-%d %H:%M:%S')

# Check if the service is running
if systemctl is-active --quiet "$SERVICE"; then
    echo "[$TIMESTAMP] $SERVICE is running ✅" >> "$LOG_FILE"
else
    echo "[$TIMESTAMP] $SERVICE is DOWN. Restarting..." >> "$LOG_FILE"
    systemctl restart "$SERVICE"

    # Check if restart succeeded
    if systemctl is-active --quiet "$SERVICE"; then
        echo "[$TIMESTAMP] $SERVICE restarted successfully ✅" >> "$LOG_FILE"
    else
        echo "[$TIMESTAMP] CRITICAL: $SERVICE failed to restart ❌" >> "$LOG_FILE"
        # Send an alert (email, Slack webhook, etc.)
    fi
fi

  scrape_interval: 15s

    static_configs:
      - targets: ['node-exporter:9100']

  - job_name: 'myapp'
    static_configs:
      - targets: ['app:3000']      # your app must expose /metrics endpoint
The 4 Golden Signals
Latency — how long requests take
Traffic — requests per second
Errors — error rate (4xx/5xx)
Saturation — how full is your system (CPU/memory at limit?)
PromQL — key queries
# CPU usage %
100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)

# HTTP error rate
rate(http_requests_total{status=~"5.."}[5m])

# Memory used
node_memory_MemAvailable_bytes
