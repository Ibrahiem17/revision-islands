🧱 Foundation for Git — Start Here If Any of This Feels Confusing
Before commits and branches and the live terminal below — let's build this from true zero: what git actually is, what a commit really means, what a branch really is (it's simpler than it sounds), and the handful of commands that cover almost everything you'll ever do.
Git — Complete Foundation for DevOps
1. First: what even IS git?
Git is a save-game system for your code. Instead of one file that just gets overwritten every time you save, git keeps a full history of every version you've ever committed — you can always go back and see (or restore) exactly how the code looked at any point.
Without git: app.js, app_v2.js, app_FINAL.js, app_FINAL_REAL.js 😩 With git: app.js (one file — every past version is saved automatically)
That's really it. Everything else in git is just tooling built around "save a snapshot, and let me move between snapshots safely."
2. Why does DevOps even need this?
Because more than one person touches the same code, at the same time, and someone has to make that not be chaos. Git lets everyone work independently, then combine their work back together — with a full, honest record of who changed what, and when.
🔑 The uncomfortable truth: without git (or something like it), "who broke production" is a guessing game. With git, it's one command — git log — away from a certain answer.
3. A commit — what it actually is
A commit is a snapshot of your entire project at one moment, plus a link pointing back to the commit right before it. String enough of those links together, and you get your whole history — a chain.
commit A ← commit B ← commit C ← commit D (this is where you are now)
Each commit has its own unique ID (like a3f9d2c), a message describing what changed, and that one link back to its parent. That's the entire data structure git is built on.
4. The three stops every change makes
Before a change becomes a permanent commit, it passes through three places, in order:
Working directory Staging area Repository (you edit a file) → (git add) → (git commit) "the file on disk" "what will be "permanently saved in the next commit" in history"
This two-step "add, then commit" might feel like an extra step at first — but it means you can carefully choose exactly what goes into each commit, instead of everything you've touched getting bundled together.
5. A branch — genuinely simpler than it sounds
This is the single biggest "aha" moment in git: a branch is NOT a copy of your code. It's just a small, movable label pointing at one specific commit.
main ──→ commit C ↑ (main is just a sticky note on this commit)
When you commit while "on" a branch, that branch's label automatically slides forward to point at the new commit. That's the entire mechanism — no copying, no duplicating files, just a label that moves.
6. HEAD — your actual "you are here" marker
HEAD is a pointer to whichever branch (or commit) you currently have checked out — it's how git knows what "here" means when you run a command.
HEAD → main → commit C
Switching branches with git checkout just moves HEAD to point somewhere else — and your files on disk update to match whatever that branch's latest commit looked like.
7. Merging — putting two histories back together
Two branches drift apart as each gets its own commits. Merging brings them back into one: either a simple fast-forward (if nothing moved on the other side), or a real merge commit with two parents (if both sides made progress).
main: A ── B ────── D (merge commit, 2 parents) \ / feature: C ─┘
You'll see this exact shape animate in the live graph below the moment you try Guided Scenario #2.
8. Remote (origin) — a copy living somewhere else
Everything above happens entirely on your own machine — that's your "local" repository. A remote (almost always named origin) is a copy of that same repository living somewhere else, usually GitHub.
Your laptop (local) ⟷ GitHub (origin/remote) git push → git pull ←
push sends your local commits up to the remote. pull brings the remote's commits down to you. That's the entire relationship.
9. Commands you'll actually use, in the order you'll actually use them
git init — "start tracking this folder"
git init
Run once, ever, per project. Creates the hidden .git folder where all the history actually lives.
git add — "stage this change"
git add .
The dot means "everything I've changed." Moves your edits into the staging area, ready to be committed.
git commit — "save this snapshot, permanently"
git commit -m "Add login page"
Turns whatever's staged into a real, permanent commit with a message explaining what changed.
git branch / git checkout -b — "start a separate line of work"
git checkout -b feature-login
Creates a new branch AND switches to it in one step — now any commits you make happen on this new line, not main.
git merge — "bring another branch's work into this one"
git checkout main git merge feature-login
Switch to where you want the work to end up FIRST, then merge the other branch into it.
git push / git pull — "sync with the remote"
git push origin main git pull origin main
Send your commits up, or bring everyone else's commits down.
10. What does a DevOps engineer actually DO with git, day to day?
Reviewing pull requests — reading someone else's commits before their branch merges into main.
Untangling a messy branch — someone's history is a wreck, and rebase or reset cleans it up before it merges.
Tracking down when a bug was introduced — using git log and git diff to find the exact commit that broke something.
Tagging releases — marking exactly which commit shipped as v1.0.0, v1.1.0, and so on.
Wiring git into CI/CD — a push or merge to main is usually the exact trigger that kicks off a deploy pipeline (see the 🐙 GitHub Actions tab).

🧠 Kid-friendly memory trick
Think of git like a video game's save system:
git commit ↓ Pressing SAVE — a checkpoint you can always return to git branch ↓ Starting a "what if" save file, without touching your main one git checkout ↓ Loading a specific save file git merge ↓ Combining progress from two save files into one HEAD ↓ The save file you're CURRENTLY playing on
🔑 Key takeaway

Everything in git traces back to one idea: every change is a saved snapshot, linked to the one before it — and a branch is just a movable label pointing at one of those snapshots. Once "branch = label, not a copy" genuinely clicks, the live terminal below stops being mysterious — you're just watching labels move and new snapshots appear.

🎭 Guided Scenarios — Watch a Real Workflow Play Out
Click ▶ Run This Scenario and watch every step execute against the graph above, one at a time.
1
The situation: Start a new feature without touching main until it's ready — the most common branching pattern there is.
git checkout -b feature-login
git add . && git commit -m "Add login form"
git checkout main
git merge feature-login
What to watch for: main never moved while feature-login was being built, so the merge is a fast-forward — main's pointer just slides forward to feature-login's tip, no new merge commit needed.
2
The situation: Two people work in parallel — one on main, one on a feature branch — and both make progress before merging.
git checkout main
git add . && git commit -m "Update README"
git checkout -b feature-payments
git add . && git commit -m "Add payment gateway"
git checkout main
git add . && git commit -m "Fix typo in README"
git merge feature-payments
What to watch for: this time main moved too, so a fast-forward isn't possible — git creates a real merge commit with two parent arrows, one to each line's tip.
3
The situation: A commit already made it into history and turned out to be broken — and it may have already been shared with others.
git add . && git commit -m "Accidentally break the build"
git revert HEAD
What to watch for: revert adds a brand-new commit that undoes the change — the broken commit is still right there in history, just canceled out. Nothing is rewritten, which is why revert is safe on shared branches.
4
The situation: A feature branch is falling behind main, and you want its history to look like it was built on top of main's latest work.
git checkout -b feature-cleanup
git checkout main
git add . && git commit -m "Update dependencies"
git checkout feature-cleanup
git add . && git commit -m "Remove dead code"
git rebase main
What to watch for: feature-cleanup's old commit fades out (unreachable) and a brand-new commit with a new ID appears sitting right on top of main — rebase doesn't move commits, it replays them as new ones.
5
The situation: A one-line fix landed on a hotfix branch, and you need that exact fix on main too — without merging the whole branch.
git checkout main
git checkout -b hotfix-typo
git add . && git commit -m "Fix typo in footer"
git checkout main
git cherry-pick hotfix-typo
What to watch for: a new commit with the same message appears on main's line, separate from hotfix-typo's own copy — cherry-pick duplicates one specific commit instead of merging everything on that branch.
6
The situation: You're mid-change with nothing committed yet, and suddenly need to switch branches for something urgent.
git add .
git stash
git checkout -b urgent-fix
git add . && git commit -m "Urgent fix"
git checkout main
git stash pop
What to watch for: stash shelves your in-progress work with no commit and no graph change at all — it's not part of history, just a saved-aside pile you can restore later with stash pop.
7
The situation: A build is finally stable enough to mark as an official release that should never move.
git add . && git commit -m "Release-ready build"
git tag v1.0.0
What to watch for: the tag lands on that exact commit and stays put forever — unlike a branch label, which keeps sliding forward with every new commit, a tag is a fixed, permanent marker.
8
The situation: Local commits exist only on your machine so far, and it's time for the team to actually see them.
git remote add origin https://github.com/you/project.git
git add . && git commit -m "Ready to share"
git push origin main
What to watch for: a dashed, greyed-out origin/main tag appears once you push — that's your remote-tracking branch, showing exactly what the remote has last seen, separate from your own local main.
