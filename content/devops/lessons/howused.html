🎬 Example 1 of 5 — Shipping a Code Change to Production
Click any step below to open it — click again to close it.
01
Start from a clean main, create a branch
You never edit code directly on main — ever
git
CMD
# make sure you're starting from the latest, real main branch git checkout main git pull origin main # create + switch to a new branch for JUST this fix git checkout -b fix/health-check-db
WHY
This is the single most repeated habit in any real dev/DevOps job. A feature branch keeps your unfinished, unproven work completely isolated from the code everyone else is running. Nothing you do for the next several steps can break anything for anyone else.
↓ now you actually go find the bug
02
Open the real file and find the actual bug
This is the whole reason the ticket exists
before
FILE
routes/health.js — as it is right now
const express = require('express'); const router = express.Router(); router.get('/health', (req, res) => { res.status(200).json({ status: 'ok' }); // always "ok" — never checks anything! }); module.exports = router;
WHY
Found it in about ten seconds. The endpoint doesn't check anything at all — it's hardcoded to say "ok" no matter what. That's exactly why monitoring never noticed the database had gone down: the health check was lying the whole time.
↓ so you fix it
03
Make the fix — small and boring, on purpose
Most real fixes are a handful of lines, not a rewrite
after
FILE
routes/health.js — after your edit
const express = require('express'); const router = express.Router(); const db = require('../db'); router.get('/health', async (req, res) => { try { await db.query('SELECT 1'); // actually ping the real database res.status(200).json({ status: 'ok' }); } catch (err) { res.status(503).json({ status: 'db unreachable' }); // now it can actually fail } }); module.exports = router;
WHY
Four real lines changed. It now runs one tiny query against the database — if that fails, the endpoint honestly reports 503 instead of lying. This is what "fixing a bug" looks like 90% of the time in a real job: small, targeted, boring.
↓ before you tell anyone, you check it yourself
04
Run it locally — never push code you haven't tested
The cheapest place to catch a mistake is your own laptop
local
CMD
npm test
OUTPUT
Health endpoint ✓ returns 200 when db is reachable (42ms) ✓ returns 503 when db is down (38ms) 2 passing
WHY
This takes seconds and happens before a single other person or system is involved. Catching a mistake here costs you nothing. Catching it later — in CI, or worse, in production — costs everyone time.
↓ it works locally, so now it leaves your laptop
05
Commit and push the branch
Your change becomes visible to the team for the first time
git
CMD
git add routes/health.js git commit -m "fix: health check now verifies DB connection" git push origin fix/health-check-db
WHY
The commit message says what changed and why — the fix: prefix follows Conventional Commits (covered in the Git tab). Six months from now, someone reading history understands this instantly without asking you.
↓ this is where GitHub itself starts reacting to what you did
06
Open a Pull Request — the literal clicks
Not a diagram — this is exactly what's on your screen
GitHub UI
ON SCREEN
1. GitHub shows a yellow banner on the repo page: "fix/health-check-db had recent pushes — Compare & pull request" 2. You click [ Compare & pull request ] 3. Title field: "Fix: health check now verifies DB connection" 4. Description box: "QA reported /health always returns 200 even when the DB is down. This adds a real DB ping so monitoring can actually detect outages." 5. Reviewers panel, right side → you add your tech lead 6. You click [ Create pull request ]
WHY
The PR isn't optional busywork — it's the gate. From this point, nothing you wrote can reach main without going through everything below.
↓ you didn't click anything for this next part — it just happens
07
CI fires automatically on your PR
This YAML file already existed — you didn't write it today
GitHub Actions
FILE
.github/workflows/ci.yml — already sitting in the repo
name: CI on: pull_request: branches: [main] jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: node-version: 18 - run: npm install - run: npm test
ON YOUR PR PAGE
✓ CI / test (pull_request) — Successful in 34s
WHY
Someone on your team set this file up once, months ago. Since then it has run on every single pull request, automatically, forever — no one has to remember to run tests manually. This is the entire, literal meaning of "CI": a YAML file plus a trigger. If this check were red, GitHub would grey out the Merge button — broken code physically cannot merge.
↓ the robot approved it — now a human does
08
Code review — a real teammate reads your diff
The human safety net sitting right next to the automated one
review
ON SCREEN
Your teammate opens the PR → "Files changed" tab Reads the red/green diff of routes/health.js Leaves a comment: "LGTM, good catch 👍" Clicks [ Approve ]
WHY
LGTM = "looks good to me," probably the most-typed phrase in software. Tests catch things a human might miss; a human catches things tests can't — like "wait, should this actually be a 500, not a 503?"
↓ one click here is the trigger for literally everything after it
09
Merge — the click that starts the release
Nothing else needs to happen manually from here
GitHub UI
ON SCREEN
You click the big green [ Merge pull request ] button → then [ Confirm merge ] → GitHub shows: "Pull request successfully merged and closed" → your fix/health-check-db branch's code is now inside main
WHY
This single click is the cause of every remaining step below. You will not touch a keyboard again for the rest of this example — everything from here runs by itself.
↓ a SECOND, completely different pipeline wakes up — not the one from step 7
10
Build the Docker image and push it to the registry
A different trigger, a different job, running for a different reason
GitHub Actions
FILE
.github/workflows/deploy.yml — a separate file from ci.yml
name: Deploy on: push: branches: [main] # not pull_request — this fires on the MERGE itself jobs: build-and-push: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: docker/login-action@v3 with: username: ${{ secrets.DOCKERHUB_USER }} password: ${{ secrets.DOCKERHUB_TOKEN }} - run: docker build -t mycompany/api:${{ github.sha }} . - run: docker push mycompany/api:${{ github.sha }}
WHY
Notice the trigger: on: push to main — different from ci.yml's on: pull_request. Two separate YAML files firing at two separate moments for two separate reasons. ${{ github.sha }} tags the image with the exact commit hash, so at any point later you can look at a running image and know precisely which code is inside it.
↓ the image exists in the registry now — but nothing is running it yet
11
Tell Kubernetes to actually run the new image
The moment your fix genuinely goes live
kubectl
FILE
.github/workflows/deploy.yml — one more step, same job
- name: Deploy to Kubernetes run: | kubectl set image deployment/api-deployment \ api=mycompany/api:${{ github.sha }} \ --record
OUTPUT
deployment.apps/api-deployment image updated
WHY
kubectl set image tells the existing Deployment (from the Kubernetes tab) "swap your containers for this new image." Kubernetes then does a rolling update on its own — old pods keep serving traffic until new ones are confirmed healthy, so no user of the API notices anything happened.
↓ "the pipeline finished" is not the same as "it actually works" — so you check
12
Verify it's actually live — the step beginners skip
A real engineer never trusts a green checkmark alone
verify
CMD
kubectl rollout status deployment/api-deployment curl https://api.mycompany.com/health kubectl logs -l app=api --tail=20
OUTPUT
deployment "api-deployment" successfully rolled out {"status":"ok"} 2024-01-15 api-7d9f8 Server listening on port 3000 2024-01-15 api-7d9f8 DB connection verified on /health check
WHY
This is the step most beginners forget. A finished pipeline just means "the steps ran" — it doesn't guarantee the fix behaves correctly against a real, running system. A real engineer always closes the loop by actually looking.
🔁
That's the whole thing, nothing skipped
Ticket → branch → code → local test → push → PR → automatic CI → human review → merge → automatic Docker build → automatic deploy → manual verify. Every tool from every other tab in this cheatsheet — Git, Docker, GitHub Actions YAML, Kubernetes — is just one link in this exact chain. That's genuinely all "DevOps" means at a real company: making this chain run itself, safely, every single day.
🐳 Example 2 of 5 — Running Your First App in Docker
Click any step below to open it — click again to close it.
This one is deliberately small. No Git branches, no Pull Request, no CI, no Kubernetes — just Docker, by itself, so the basic idea actually clicks before you touch anything more advanced. Every terminal output below is written to look exactly like what your real terminal will show — same layout, same wording — so when you try this yourself on a real computer, nothing looks unfamiliar or scary.

The goal: take a tiny app, put it inside a container, run that container, actually talk to it, read its logs, then clean up after yourself. That's it. That's the whole example — and it's also the exact foundation underneath everything Example 1 automated.
01
The app — as simple as it gets
One file, zero dependencies, nothing to install
index.js
FILE
index.js
const http = require('http'); // built into Node — nothing to npm install const server = http.createServer((req, res) => { res.end('Hello from inside a container! 🐳'); }); server.listen(3000, () => { console.log('Server running on port 3000'); });
WHY
That's genuinely the whole app. No framework, no package.json, no npm install step — on purpose. This example is about understanding Docker, not Node, so everything that isn't Docker has been stripped down to almost nothing.
↓ now you tell Docker how to package it
02
Write the Dockerfile — 4 lines, explained one at a time
A Dockerfile is just a short recipe, read top to bottom
Dockerfile
FILE
Dockerfile
FROM node:20-alpine WORKDIR /app COPY index.js . CMD ["node", "index.js"]
WHY — line by line
FROM node:20-alpine — start from a tiny, ready-made Linux system that already has Node.js installed. You are not building an operating system — you're borrowing one that already exists.

WORKDIR /app — make a folder called /app inside that system, and treat it as the "current folder" for every line after this one.

COPY index.js . — copy your index.js from your own computer into that /app folder, inside the image.

CMD ["node", "index.js"] — the command that runs automatically the moment someone starts a container from this image.
↓ turn that recipe into an actual image
03
Build the image
This is exactly what your own terminal will print
docker build
CMD
docker build -t hello-app:1.0 .
OUTPUT
[+] Building 1.8s (9/9) FINISHED => [internal] load build definition from Dockerfile 0.0s => [internal] load .dockerignore 0.0s => [internal] load metadata for docker.io/library/node:20-alpine 1.2s => [1/3] FROM docker.io/library/node:20-alpine 0.0s => [internal] load build context 0.0s => [2/3] WORKDIR /app 0.1s => [3/3] COPY index.js . 0.1s => exporting to image 0.2s => => writing image sha256:9f8e7d6c5b4a3c2d1e0f9a8b7c6d5e4f => => naming to docker.io/library/hello-app:1.0
WHY
Each => line is one instruction from your Dockerfile being carried out. -t hello-app:1.0 just gives the result a name and a version tag so you can refer to it later instead of typing a long hash.
↓ check that it's actually sitting on your machine now
04
Confirm the image exists
It's a saved template now — nothing is running yet
docker images
CMD
docker images
OUTPUT
REPOSITORY TAG IMAGE ID CREATED SIZE hello-app 1.0 9f8e7d6c5b4a 3 seconds ago 134MB
WHY
This is the important mental split beginners usually miss: an image is just a saved, inert file sitting on disk — like a .zip you haven't extracted yet. Nothing is running. That only happens in the next step.
↓ now actually start it
05
Run it as a container
Every flag explained — nothing left as a mystery
docker run
CMD
docker run -d -p 3000:3000 --name hello-app hello-app:1.0
OUTPUT
9f8e7d6c5b4a3c2d1e0f9a8b7c6d5e4f3a2b1c0d9e8f7a6b5c4d3e2f1a0b9c8d
WHY — every flag
-d — "detached": run in the background and give me my terminal back immediately.

-p 3000:3000 — connect port 3000 on your real computer to port 3000 inside the container. Format is always host:container. Without this flag, the app runs, but nothing outside the container can ever reach it.

--name hello-app — give this specific running container a name you can refer to, instead of typing that long ID every time.

That long string printed back is just the full container ID — you'll rarely need the whole thing.
↓ double check it's really running
06
Confirm it's actually running
The command you'll type more than any other Docker command
docker ps
CMD
docker ps
OUTPUT
CONTAINER ID IMAGE COMMAND CREATED STATUS PORTS NAMES 9f8e7d6c5b4a hello-app:1.0 "node index.js" 8 seconds ago Up 8 seconds 0.0.0.0:3000->3000/tcp hello-app
WHY — the columns, quickly
CONTAINER ID / IMAGE — which image it came from. COMMAND — what's actually running inside. STATUS — "Up 8 seconds" means healthy and alive right now. PORTS — confirms the 3000→3000 connection from step 5 actually took effect. If this list is empty, your container isn't running — that's the very first thing to check when something feels broken.
↓ it's running — so actually talk to it
07
Actually talk to it
The entire point of everything above
curl / browser
CMD
curl http://localhost:3000
OUTPUT
Hello from inside a container! 🐳
WHY
You could type localhost:3000 into a browser instead and see the exact same text. Walk the round trip in your head: your request left your terminal → hit port 3000 on your real machine → Docker forwarded it through the tunnel from -p 3000:3000 → your Node server inside the container answered → the response came back out the same way. That tunnel is the entire reason the -p flag exists.
↓ see what the app itself has been saying
08
Check its logs
Usually the very first thing you look at when debugging
docker logs
CMD
docker logs hello-app
OUTPUT
Server running on port 3000
WHY
Anything your app prints with console.log ends up here — nowhere else. When something goes wrong later with a real app, this is the first command almost anyone reaches for.
↓ and finally, clean up after yourself
09
Stop it, then remove it
The image is untouched — you can start fresh anytime
cleanup
CMD
docker stop hello-app docker rm hello-app
OUTPUT
hello-app hello-app
WHY
Docker just echoes the name back — that's genuinely all it prints, which surprises a lot of beginners expecting more output. stop shuts the container down gracefully. rm actually deletes it. Your hello-app:1.0 image from step 3 is completely untouched — run docker run again any time and you get a brand-new container from the exact same image.
🧱
This is the foundation everything else stands on
Write code → describe it in a Dockerfile → build an image → run a container from it → talk to it → read its logs → clean up. Go back and look at Example 1's steps 10 and 11 — the automatic docker build and the automatic deploy. That's this exact sequence, just triggered by a robot instead of by you typing it. Once this feels boring and obvious, Example 1 stops looking like magic.
⚡ Example 3 of 5 — Your First Full CI/CD Pipeline
Click any step below to open it — click again to close it.
If YAML, GitHub Actions, "secrets," and "deployments" have ever felt intimidating, that feeling ends here. Every single thing below is something you already did with your own two hands in Example 2 — build an image, run it, check it, ship it. The only difference in this example is that a computer types those exact same commands for you, automatically, every time you push code, without getting tired or making a typo. That's genuinely the entire concept of "CI/CD." Nothing more mystical than that.

Every screen shown below is copied from what GitHub and Docker Hub actually show you — same labels, same layout, same wording — researched live for this exact page, so nothing surprises you the first time you open the real thing yourself.
01
The one new file — a GitHub Actions workflow
6 steps, each one you can already explain to yourself
.github/workflows/ci-cd.yml
FILE
.github/workflows/ci-cd.yml
name: CI/CD on: push: branches: [main] jobs: build-test-deploy: runs-on: ubuntu-latest steps: - name: Checkout code uses: actions/checkout@v4 - name: Set up Node uses: actions/setup-node@v4 with: node-version: 20 - name: Run the test run: node test.js - name: Log in to Docker Hub uses: docker/login-action@v3 with: username: ${{ secrets.DOCKERHUB_USER }} password: ${{ secrets.DOCKERHUB_TOKEN }} - name: Build and push image run: | docker build -t mycompany/hello-app:${{ github.sha }} . docker push mycompany/hello-app:${{ github.sha }} - name: Deploy run: kubectl set image deployment/hello-app hello-app=mycompany/hello-app:${{ github.sha }}
WHY — every named step, one sentence each
Checkout code — downloads your repo's code onto GitHub's temporary computer, so it has something to work with.

Set up Node — installs Node.js on that temporary computer. Same idea as installing it on your own laptop.

Run the test — runs the exact test.js file from the next step. If it fails, everything below never runs.

Log in to Docker Hub — logs into your Docker Hub account using two secret values saved once in Settings → Secrets and variables → Actions, so GitHub is allowed to push images on your behalf. You never type a password in the YAML itself.

Build and push image — the exact same docker build command from Example 2, plus docker push, now run automatically instead of by you.

Deploy — tells Kubernetes to swap in the freshly-pushed image, the same kubectl set image idea from Example 1's step 11.
↓ but "run the test" needs an actual test.js file to run
02
The test — no framework, no npm install, still real
Proof the app actually answers before anything ships
test.js
FILE
test.js
const http = require('http'); require('./index.js'); // this line alone starts the server on port 3000 setTimeout(() => { http.get('http://localhost:3000', (res) => { if (res.statusCode === 200) { console.log('✓ Server responded with 200 OK'); process.exit(0); } else { console.error('✗ Unexpected status:', res.statusCode); process.exit(1); } }).on('error', (err) => { console.error('✗ Request failed:', err.message); process.exit(1); }); }, 500);
WHY
No Jest, no test runner, nothing to install — just plain Node starting the server and checking it actually says "200 OK" before anything gets built or shipped. process.exit(1) is the one line that makes the whole pipeline stop dead if the app is broken. That's the entire mechanism behind "CI catches broken code" — an exit code, nothing more magical.
↓ both files exist — now the one action that starts everything
03
Push — the exact same git you already know
Identical to Example 2's git steps, plus two new files
git
CMD
git add . git commit -m "add CI/CD pipeline" git push origin main
WHY
Nothing new here at all — this is the identical git add / commit / push sequence from Example 2. You're just pushing two new files this time: the workflow YAML and test.js.
↓ you didn't click anything else — GitHub noticed the push on its own

🚨 Example 4 of 5 — When Something Breaks (The Most Common DevOps Day)
Click any step below to open it — click again to close it. Yellow glowing rings mark exactly what you'd click in real life.
Examples 1–3 were all about shipping new code. But the single most common thing a DevOps engineer actually does, day after day, isn't shipping something new — it's noticing something broke and calmly fixing it, using the exact same tools already covered. This example is that story, in the smallest steps possible.
Think of it like a toy that stopped working. You wouldn't take it apart blindly. You'd check what changed last — new batteries? — put the old batteries back if that's what worked before, and check if it works now. That's this entire example. Website instead of toy, that's the only difference.

Notice something is wrong
You can't fix a problem you don't know exists
Grafana
WHY — before anything else
Nobody sits and stares at a website hoping to catch it breaking. Instead, a dashboard watches it automatically, all day, every day — this is the Monitor phase from the Lifecycle tab, finally shown in action. The moment something looks wrong, it tells you before a single user has to complain.

02
Figure out what changed recently
Almost every "it broke" moment traces back to the last deploy
GitHub Actions
WHY — before touching anything
Apps don't randomly break on their own while sitting still. Almost always, something changed — and the most recent change is the very last thing that got deployed. Before guessing, go look at exactly what shipped last.
2.1Open the Actions tab — find the most recent run
UI

WHY this is the important part
Notice it says ✓ Success. That's not a contradiction — the tests that existed all passed. It just means nobody had written a test for this exact situation yet. A green checkmark means "the bugs we thought to test for didn't happen," not "there are zero bugs." That's exactly why the Grafana dashboard from Step 1 still matters even after CI passes.
↓ a suspect isn't proof — go check the actual evidence
03
Confirm it with real evidence
Don't guess — look at what the running app is actually doing
kubectl
WHY — before rolling anything back
A suspicious commit is a theory, not proof. Kubernetes is what's actually running the app right now — so ask it directly what's happening, the same way you'd check a patient's vitals before deciding on treatment.
3.1Check the pods
CMD
kubectl get pods
OUTPUT
NAME READY STATUS RESTARTS AGE hello-app-7d9f6b7c8-x2k9p 0/1 CrashLoopBackOff 6 8m
3.2Read what it's actually saying
CMD
kubectl logs hello-app-7d9f6b7c8-x2k9p
OUTPUT
Server running on port 3000 TypeError: Cannot read properties of undefined (reading 'total') at /app/checkout.js:14:22 Process exited with code 1
WHY
CrashLoopBackOff just means "it crashes, Kubernetes restarts it, it crashes again" — on repeat. The log confirms the theory from Step 2: the checkout fix broke on a real input it wasn't tested against. Now it's not a guess anymore.
↓ now — restore service first, investigate deeper later
04
Stop the bleeding — roll back immediately
Restore service first. Debugging deeply can wait a few minutes.
kubectl rollout undo
WHY this comes before "fixing" it properly
Real users are hitting errors right now. Sitting down to carefully write and test a proper fix takes time they don't have. The fastest safe move is going back to the exact version that was working ten minutes ago — Kubernetes already remembers it.
4.1Roll back to the previous version
CMD
kubectl rollout undo deployment/hello-app
OUTPUT
deployment.apps/hello-app rolled back
4.2Watch it come back up
CMD
kubectl rollout status deployment/hello-app
OUTPUT
Waiting for deployment "hello-app" rollout to finish... deployment "hello-app" successfully rolled out
4.3Double-check the pod is actually healthy
CMD

05
Fix it where it actually lives — the code
Rolling back the app isn't enough — the bug is still sitting in Git
git revert
WHY this step can't be skipped
Step 4 fixed the running app, not the source code. If nobody touches Git, the very next person who deploys — maybe next week, maybe by accident — will re-ship the exact same broken commit, and this whole thing happens all over again.
5.1Find the exact commit that broke it
CMD
git log --oneline -3
OUTPUT
a3f9c1e Fix null check on checkout total 7b2e0d4 Bump minor dependency c19a44f Add checkout summary page
5.2Undo that exact commit, and push it
CMD
git revert a3f9c1e git push origin main
OUTPUT
[main 9c4d21a] Revert "Fix null check on checkout total" 1 file changed, 1 insertion(+), 4 deletions(-) To github.com/you/hello-app.git a3f9c1e..9c4d21a main -> main
WHY
git revert doesn't erase history — it adds a new commit that undoes the old one, so there's an honest record of what happened. That git push is the exact same trigger from Example 3 — it automatically re-runs the whole CI/CD pipeline, tests it, builds it, and re-deploys it. Nobody has to remember any extra step.
↓ "should be fixed now" is a guess — go confirm it like a real user would

Verify it's actually fixed
"Looks fixed to me" isn't good enough — check it from the outside
curl + Grafana
WHY
It's tempting to assume "the pipeline went green, so it's fine." Confirm it the same way a real visitor would — actually hit the app — and then confirm the dashboard agrees over time, not just in the first second.

WHY this counts as part of the job
Fixing it silently helps for exactly one day. Writing three short sentences — what broke, what fixed it, what changes going forward — helps the whole team, forever. This is the "close the loop" step that feeds back into Plan, all the way back at the start of the Lifecycle tab.
