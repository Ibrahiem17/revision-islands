Q1What is the difference between CI and CD?▼
ANSWER
CI (Continuous Integration) automatically builds and tests code on every push. Goal: always have a working codebase, catch bugs early.

CD has two meanings:
• Continuous Delivery — every passing build is ready to deploy, but a human approves the final push.
• Continuous Deployment — every passing build deploys automatically with zero human approval.

CI = build + testDelivery = human gateDeployment = fully automated
Q2What happens when a test fails in the pipeline?▼
ANSWER
The pipeline stops immediately — "fail fast" principle. No Docker image is built, nothing deploys. The developer gets notified with the failing test and logs.

This is intentional. A bug caught in CI costs minutes — the same bug live can cost hours of downtime.

pipeline haltsdev notifiedno deployfix and repush

Q4Explain a webhook and how it triggers a Jenkins pipeline.▼
ANSWER
A webhook is an HTTP POST request that GitHub sends to Jenkins the moment you push code. Jenkins receives it and automatically starts the pipeline.

The alternative — polling — has Jenkins check GitHub every few minutes. Polling is slow and wasteful. Webhooks are real-time and efficient.

Zero-downtime means users never see an outage during a release.

1. Rolling Update — replace old containers gradually. Traffic keeps flowing.
2. Blue-Green — two identical envs. Deploy to green, test, flip 100% traffic instantly.
Bonus: Canary — route a small % to new version, validate, then increase.

Q13What's the difference between > and >> in Linux? What about pipes?▼
ANSWER
> = overwrite redirect. Sends output to a file, destroying existing content.
>> = append redirect. Adds output to end of file, keeping existing content.
| = pipe. Output of left command becomes input of right command.

grep "error" app.log | wc -l — count error lines without creating a temp file.

Think of pipe as a conveyor belt between commands.

> = overwrite (dangerous)>> = safe append| = chain commands
Q14What's the difference between kill and kill -9?▼
ANSWER
kill PID — sends SIGTERM. A polite request to stop. The process can finish current work, close connections, then exit cleanly.

kill -9 PID — sends SIGKILL. OS kills the process instantly, no cleanup. The process can't handle it.

Always try kill PID first. Use kill -9 only if the process is frozen and won't respond — abrupt termination can corrupt files or leave open connections.

SIGTERM = politeSIGKILL = forcegraceful first-9 = last resort

Q17What is the difference between git fetch and git pull?▼
ANSWER

git pull — fetch + merge combined. Immediately integrates remote changes into your current branch. Faster but less control.

2. Open the conflicting file — look for <<<<<<<, =======, >>>>>>> markers

Q20What is the difference between git revert and git reset?▼
ANSWER
git revert <hash> — creates a new commit that reverses the changes of a previous commit. Safe for shared/public branches because it doesn't rewrite history. Team members won't have conflicts.

git reset --soft HEAD~1 — moves the branch pointer back, undoing the last commit but keeping changes staged. Only safe on commits you haven't pushed yet.

git reset --hard — undo commit AND delete all changes. Dangerous — no recovery possible.

Rule: use revert on shared branches. Use reset only on local, unpushed commits.

revert = safe, adds undo commitreset = rewrites history--hard = dangerous

ANSWER

Microservices — application split into small, independent services that communicate via APIs. Each service can be deployed, scaled, and updated independently.

DevOps angle: Microservices align better with DevOps because each team can ship their service without waiting for others. But it means more containers, more complexity — you need Kubernetes to manage them all.

Q22What does "shift left" mean in DevOps?▼
ANSWER
"Shift left" means moving quality, security, and testing activities earlier in the software development lifecycle — to the "left" on the timeline.

Traditionally, testing and security reviews happened at the end, right before deployment. Shift left means: write tests while you code, run security scans in CI, catch issues at commit time — not at deployment time.

Why it matters: A bug caught at commit time = minutes to fix. Same bug in production = hours of downtime + potential data loss. Cheaper, faster, safer to catch early.

Q24What is git reflog and why is it a lifesaver?▼
ANSWER
git reflog records every single movement of HEAD — commits, merges, rebases, resets, branch switches. Unlike git log which only shows commit history, reflog includes everything, even deleted branches and reset commits.

Why it's a lifesaver: If you accidentally delete a branch, do a bad git reset --hard, or lose commits after a rebase, reflog shows you the hash of what was there before. You can recover it with git checkout <hash> or git branch recovered <hash>.

Q25What are git hooks and give an example of how you'd use them in DevOps?▼
ANSWER
Git hooks are executable scripts in .git/hooks/ that run automatically at specific Git events. They enforce policies and automate tasks without requiring developer discipline.

Client-side examples:
• pre-commit — run linters/formatters before every commit. If lint fails, commit is rejected.

Q26What's the difference between git clone and forking a repo?▼

Q27What is a Dockerfile? Walk me through a basic example.▼
ANSWER
A Dockerfile is a text file with instructions for building a Docker image — essentially a recipe that defines what goes inside the container.

Walking through:
FROM node:14 — start with Node.js 14 as the base
WORKDIR /app — all subsequent commands run in /app
COPY package*.json ./ — copy deps file first (caching!)
RUN npm install — install deps as a cached layer
COPY . . — copy app code (changes most often, so last)
EXPOSE 3000 — document the port (doesn't publish it)
CMD ["npm", "start"] — default start command

Why copy package.json first? Layer caching — if your code changes but deps don't, Docker skips re-running npm install. Massive speed improvement.

FROM = base imageRUN = build commandCMD = start commandEXPOSE ≠ publish
Q28What's the difference between a Docker image and a container?▼
ANSWER
Docker Image — a read-only blueprint made of layers. It contains the code, runtime, libraries, and configs. Like a class in OOP — it's the definition, not the running thing. You can't "run" an image — you run a container from it.

Container — a running instance of an image. Like an object instantiated from a class. It has its own filesystem, network, and process space. You can have many containers running from the same image simultaneously.

Analogy: Image = cookie cutter. Container = the actual cookie. One cutter, many cookies.

image = read-only blueprintcontainer = running instancemany containers, one image
Q29What are Docker layers and why does layer caching matter?▼
ANSWER
Each Dockerfile instruction creates a layer — a diff on top of the previous layer. Layers are cached: if a layer hasn't changed, Docker reuses the cached version instead of rebuilding it.

Why it matters for DevOps: Your app code changes constantly, but dependencies (package.json, requirements.txt) change rarely. By copying the deps file and running install before copying your app code, you ensure the expensive npm install step is cached and only reruns when deps actually change. Builds go from minutes to seconds.

Rule: Put rarely-changing steps first, frequently-changing steps last.

each instruction = layerunchanged layers = cacheddeps before code = fast builds
Q30What is a Docker volume and why do you need it?▼
ANSWER
Containers are ephemeral — when a container stops or is recreated, its filesystem is wiped. This is a problem for anything that needs persistent data (databases, uploaded files, logs).

A Docker Volume is persistent storage that lives outside the container's lifecycle. Mount it into a container and data survives restarts, crashes, and even container deletion.

docker run -v mydata:/app/data myapp — mounts a volume named "mydata" to /app/data inside the container.

Production use: Your PostgreSQL container uses a volume to store the database files. Even if the container crashes and is recreated, the data is still there.

containers are ephemeralvolumes persist dataessential for databases
Q31What is docker-compose and when would you use it?▼
ANSWER
docker-compose orchestrates multiple containers together via a single YAML file. Instead of running multiple docker run commands manually, one docker-compose up starts everything: your app, database, cache, message queue — all configured and networked together.

When to use it: Local development. You need your app + Postgres + Redis all running together. Compose handles networking between them automatically — containers can reach each other by service name.

Q32Explain the difference between rolling, blue-green, and canary deployments.▼
ANSWER
Rolling Deploy — update one server at a time. Take it out of rotation, update it, put it back. Repeat. No downtime, but briefly runs two versions simultaneously.

Blue/Green — two full identical environments. Green is live. Deploy to blue. Test blue. Flip the load balancer from green to blue. Rollback = flip LB back instantly. Cost: double the infra.

Canary — route 5-10% of traffic to new version. Monitor for errors/latency degradation. If healthy, gradually expand to 100%. Limits blast radius — if it breaks, only a small % of users affected.

When to use which: Rolling for most deploys. Blue-green when you need instant rollback guarantee. Canary for high-risk changes or A/B testing.

rolling = gradual server-by-serverblue-green = instant LB flipcanary = % traffic, limit blast radius
Q33What load balancing algorithms exist and when would you choose each?▼
ANSWER
Round Robin — requests distributed evenly across all servers in rotation. Simple and fair. Best for stateless apps with equal server capacity.

Least Connections — route to the server with fewest active connections. Smarter than round robin when requests vary in duration — avoids overloading a server that's handling slow requests.

IP Hash — same client IP always hits the same server. Provides sticky sessions without storing session state centrally. Useful when session data lives on the server itself.

Weighted — Server A gets 70%, Server B gets 30%. Use when servers have different capacity, or for canary deployments where you gradually shift traffic.

round robin = equal, simpleleast conn = smart, varied workloadsIP hash = sticky sessionsweighted = canary or unequal capacity

Q35How would you set up a CI/CD pipeline from scratch?▼
ANSWER
6-step approach:

Q36Explain the Kubernetes architecture — control plane vs worker nodes.▼
ANSWER
Control Plane (Master Node) — the brain. Controls everything:
• API Server — entry point for all commands (kubectl hits this)
• Scheduler — decides which worker node a new pod runs on
• Controller Manager — watches state, makes reality match desired state
• etcd — the cluster database. If etcd dies, cluster is blind.

Worker Nodes — where apps actually run:
• Kubelet — agent on every node, talks to control plane, ensures pods run
• Container Runtime — Docker/containerd, actually runs the containers
• Pods run here

Q37What are the main Kubernetes objects you need to know?▼
ANSWER
Pod — smallest unit. Wraps one or more containers sharing network and storage. Ephemeral — they die and get new IPs.

Deployment — manages desired state ("I want 3 replicas"). Creates/kills pods to match. Handles rolling updates. For stateless apps.

Service — stable network endpoint. Pod IPs change when pods restart — the Service IP never changes. Routes traffic to healthy pods.

Ingress — external HTTP routing. One entry point, path-based rules to different services.

ConfigMap — non-sensitive config injected into pods. Secret — sensitive data (passwords, tokens), base64-encoded.

HPA — Horizontal Pod Autoscaler. Scales replicas based on CPU or custom metrics.

Pod → Deployment → Service → IngressConfigMap = configSecret = sensitiveHPA = autoscale
Q38What's the difference between a Deployment and a StatefulSet?▼
ANSWER
Deployment — for stateless apps. All replicas are identical, interchangeable. Easy to scale up/down, rolling updates built-in. Use for APIs, web servers, workers.

StatefulSet — for stateful apps. Pods get stable, unique names (pod-0, pod-1, pod-2). Each pod gets its own Persistent Volume — data is tied to that specific pod identity. Used for databases, Kafka, Zookeeper — anything that needs to know which instance it is.

Key difference: in a Deployment, if pod-2 dies and restarts, it gets a random new name and can use any storage. In a StatefulSet, pod-2 always comes back as pod-2 and reconnects to its specific volume.

Deployment = stateless, identical replicasStatefulSet = stable identity + PV per pod
Q39What is a Kubernetes Service and what are the three types?▼
ANSWER
A Service provides a stable network endpoint in front of pods. Pods are ephemeral — they die and get new IPs. The Service IP never changes, so other services always know how to reach your app.

ClusterIP (default) — internal only. Reachable only from inside the cluster. Use for microservice-to-microservice communication.

NodePort — exposes service on a static port on every node's IP. Reachable from outside via NodeIP:Port. Simple but not production-grade.

LoadBalancer — creates a cloud load balancer (AWS ALB etc.) with an external IP. Production way to expose services. Each creates a separate LB — use Ingress to avoid paying for one per service.

ClusterIP = internalNodePort = node IP accessLoadBalancer = external + cloud LB
Q40What is Kubernetes Ingress and why is it important?▼
ANSWER
Ingress is an HTTP/HTTPS router that sits at the edge of your cluster and routes external traffic to the correct internal service.

Why it matters: Without Ingress, you'd need one LoadBalancer per service — expensive and unmanageable. With Ingress, one entry point uses path-based or host-based rules to route to many services:
• /api/* → backend service
• / → frontend service
• api.company.com → API service

Ingress needs an Ingress Controller to work — typically Nginx. The controller is the actual reverse proxy; Ingress is just the rules configuration.

one entry point for all servicespath-based routingneeds Ingress Controllerreplaces many LoadBalancers
Q41What is the difference between a ConfigMap and a Secret in Kubernetes?▼
ANSWER
Both inject configuration data into pods without hardcoding it in the image. The difference is the type of data:

ConfigMap — non-sensitive configuration. DB hostnames, API URLs, feature flags, config files. Plain text. Can be checked into Git.

Secret — sensitive data. Passwords, tokens, TLS certs, API keys. Base64-encoded (NOT encrypted by default). Should not be committed to Git — use sealed secrets or an external secrets manager (AWS Secrets Manager, Vault).

Why separate them? Different access controls, different audit trails. A developer can read ConfigMaps; Secrets should require elevated permissions.

ConfigMap = non-sensitive, plain textSecret = sensitive, base64not encrypted by defaultuse sealed secrets in prod
Q42What is Helm and why would you use it?▼

Instead of writing raw YAML for every K8s resource, you use a Helm chart — a reusable, parameterized template. Charts bundle all the manifests (Deployment, Service, Ingress, ConfigMap) for an app and let you configure them via values.

Q43Walk me through how Terraform works for managing infrastructure.▼
ANSWER
1. Write HCL config files — define what infrastructure you want (EC2 instances, VPCs, S3 buckets) in .tf files.

2. terraform init — downloads providers (AWS, Azure plugin) and initializes the workspace.

3. terraform plan — generates an execution plan showing exactly what will be created, changed, or destroyed. Review this before applying.

4. terraform apply — provisions the actual infrastructure. Creates/modifies/deletes resources to match your config.

5. State file — Terraform stores current infrastructure state in a .tfstate file. Store it in a remote backend (S3 + DynamoDB for locking) in teams — never commit it to Git.

6. Version control — store .tf files in Git. Infra changes reviewed as PRs. Never hardcode secrets.

HCL files → init → plan → apply → stateremote state for teamsnever hardcode secrets

Q45What is the difference between high availability and disaster recovery?▼
ANSWER
High Availability (HA) — the system stays accessible even if one or more servers go down. Achieved through redundancy within a region: multi-AZ deployment, multiple instances behind a load balancer, auto-scaling. If one server dies, others take over — users never notice.

Disaster Recovery (DR) — the ability to continue service even during a regional outage (when an entire AWS region goes down). Achieved through multi-region deployment: data replicated across regions, DNS failover redirects traffic to the backup region.

Difference in scope: HA handles single server/AZ failures. DR handles entire region failures.

HA = survive server/AZ failureDR = survive regional outageHA = multi-AZDR = multi-region

Q47What is a reverse proxy and what is it used for in DevOps?▼
ANSWER
A reverse proxy sits between clients and backend servers. It receives all incoming requests and forwards them to the appropriate backend server, then returns the server's response to the client.

What it provides:
• Load balancing — distribute traffic across multiple backends
• SSL termination — handle HTTPS at the proxy, backends use HTTP internally
• Caching — serve cached responses without hitting backends
• Security — hide backend IPs, rate limiting, WAF
• Single entry point — one domain, routes to many internal services

Nginx is the most common reverse proxy in DevOps. It also serves as the Kubernetes Ingress Controller.

sits between client and backendload balance + SSL + cacheNginx = most common
Q48What is ENTRYPOINT vs CMD in Docker? What happens when you override at runtime?▼
ANSWER
ENTRYPOINT sets the fixed executable that always runs. It cannot be overridden by docker run arguments — only the arguments to it change.

CMD sets the default arguments to pass to ENTRYPOINT, or the default command if no ENTRYPOINT is set. CMD can be fully overridden at docker run.

Example:
ENTRYPOINT ["node"]
CMD ["server.js"]

docker run myapp → runs node server.js
docker run myapp debug.js → runs node debug.js (CMD overridden)
docker run myapp --debug → the --debug replaces CMD but not ENTRYPOINT

ENTRYPOINT = fixed executableCMD = default args, overridableuse together for flexible containers
Q49What is IAM in AWS and what is the principle of least privilege?▼
ANSWER
IAM (Identity and Access Management) controls who can do what in AWS. It manages users, groups, roles, and policies.

Key concepts:
• User — a person or service with credentials
• Role — attach to EC2/Lambda to give them AWS permissions without hardcoding keys
• Policy — JSON document defining what actions are allowed on which resources

Principle of Least Privilege: give an entity only the minimum permissions it needs to do its job — nothing more. An EC2 running a web app that only reads from S3 should only have S3 read permission, not admin.

Never hardcode AWS access keys in code. Use IAM roles for EC2/Lambda service-to-service auth.

Q50What is Docker networking? What are the three main network types?▼
ANSWER
Docker networking controls how containers communicate with each other and the external world.

bridge (default) — containers on the same bridge network can talk to each other by container name. Isolated from the host network. Good for local development.

host — container shares the host's network stack. Container's port 3000 IS host's port 3000. No isolation, maximum performance. Least secure.

overlay — spans multiple Docker hosts. Used in Docker Swarm and Kubernetes. Allows containers on different machines to communicate as if on the same network.

bridge = default, isolated, container-to-containerhost = shared network, fastestoverlay = multi-host
Q51What is a multi-stage Docker build and why would you use it?▼
ANSWER
A multi-stage build uses multiple FROM instructions in one Dockerfile. Each stage can have different base images and tools. Only the final stage becomes the production image — intermediate stages are discarded.

Why it matters: The build stage needs compilers, test frameworks, npm packages, and other heavy dev tools. The production image needs only the compiled output and runtime. Without multi-stage builds, you'd ship all that build tooling to production — images can be 1GB+. With multi-stage, you copy only the final artifact into a tiny alpine image — often under 50MB.

Result: Faster pulls, smaller attack surface, lower ECR/registry storage costs.

build stage = heavyprod stage = tiny alpinecopy only artifact1GB → 50MB
Q52How do you reduce Docker image size?▼
ANSWER
4 main techniques:

1. Use smaller base images — node:18-alpine instead of node:18. Alpine is ~5MB vs ~150MB for standard Debian images.

2. Multi-stage builds — build in a heavy image, copy only the final artifact to a minimal image.

3. Layer optimization — combine RUN commands with && to reduce layer count. Clean up in the same layer: RUN apt-get install -y curl && rm -rf /var/lib/apt/lists/*

4. .dockerignore file — exclude node_modules, .git, test files, docs from being COPYed into the image.

Q53How do you debug a failing pod in Kubernetes?▼
ANSWER
This is one of the most common interview questions for DevOps roles. Here's the exact flow:

1. kubectl get pods — check the pod status. Is it Pending, CrashLoopBackOff, ImagePullBackOff, OOMKilled, or Error?

2. kubectl describe pod <name> — read the Events section at the bottom. Most answers are here: image pull failed, insufficient resources, liveness probe failing, ConfigMap/Secret missing.

3. kubectl logs <pod> — read the app's own output. What error did it throw?

4. kubectl logs <pod> --previous — if pod keeps crashing, get logs from the PREVIOUS run before it died.

5. kubectl exec -it <pod> -- sh — if pod is running but misbehaving, shell inside and inspect.

get pods → describe → logs → execEvents section = gold--previous for crash loops
Q54What happens when a pod crashes in Kubernetes?▼
ANSWER
K8s is self-healing — it automatically responds to pod crashes:

1. The Kubelet on the worker node detects the container exited.
2. It reports this to the Control Plane via the API Server.
3. The Controller Manager sees that actual state (2 pods) doesn't match desired state (3 pods).
4. It creates a new pod. The Scheduler assigns it to an available node. The Kubelet starts it.
5. If the pod keeps crashing immediately on restart, K8s goes into CrashLoopBackOff — it keeps retrying but with increasing delays (exponential backoff).

You never need to manually restart pods. The Deployment's desired state definition is what makes this work.

Kubelet detects crashController Manager recreatesCrashLoopBackOff = keeps failingself-healing
Q55What is etcd in Kubernetes and why is it critical?▼
ANSWER
etcd is a distributed key-value store that acts as Kubernetes' brain/database. It stores the entire cluster state — all the desired configurations, current state, pod specs, secrets, ConfigMaps, everything.

Why it's critical: Every kubectl command goes to the API Server, which reads from and writes to etcd. If etcd is down, the control plane is blind — it can't make scheduling decisions, can't create new pods, can't respond to failures. Existing running pods continue, but nothing new can happen.

In production: etcd is run in a cluster (3 or 5 nodes) for high availability. Regular backups of etcd = full cluster recovery capability.

cluster's source of truthall state stored hereetcd down = cluster blindbackup etcd = backup everything
Q56What is the difference between ECS and EKS on AWS?▼
ANSWER
ECS (Elastic Container Service) — AWS-native container orchestration. Simpler to set up and operate. Two launch modes:
• EC2 mode — you manage the underlying VMs
• Fargate — fully serverless, AWS manages the infrastructure. You just provide the Docker image.

EKS (Elastic Kubernetes Service) — managed Kubernetes. AWS handles the control plane. You manage worker nodes. Use when you need full Kubernetes compatibility, advanced scheduling, or are already using Kubernetes.

When to choose: ECS Fargate for simplicity and lower operational overhead. EKS for complex microservices systems, existing K8s tooling, or when Kubernetes expertise is available.

Q57What is a VPC in AWS and how do public vs private subnets work?▼
ANSWER
A VPC (Virtual Private Cloud) is your isolated private network inside AWS. All your resources (EC2, RDS, ECS) live inside a VPC. Other AWS accounts can't see into your VPC.

Subnets: A VPC is divided into subnets — sections with their own IP range.

Public subnet — has a route to an Internet Gateway. Resources here are directly reachable from the internet. Place your Load Balancer and Bastion hosts here.

Private subnet — no direct internet access. Place your application servers, databases, and caches here. They can reach the internet via a NAT Gateway (for updates/patches) but can't be reached from outside.

Security principle: Database should NEVER be in a public subnet. RDS goes in private subnet — only your app servers can reach it.

VPC = isolated private networkpublic = internet-facingprivate = internal onlyDB always in private

Q61"No space left on device" but df -h shows 20% free. What's happening?▼
ANSWER
Inode exhaustion — every file takes one inode. You can have physical space but no inodes left if there are millions of tiny files.

df -i — check inode usage per filesystem. If Use% = 100%, that's your culprit.
Find: find / -xdev -printf '%h\n' | sort | uniq -c | sort -rn | head

Second cause: deleted file held open by a running process. Disk space isn't freed until the process closes the handle. lsof | grep deleted — restart that process.

df -i = inode usagemillions tiny files = exhaustionlsof | grep deleted = held-open files

Q67What is the .git directory and what happens if you delete it?▼
ANSWER
The .git/ directory is the heart of a Git repository. It stores everything Git needs: the object database (all commits, file versions, directory structures stored as SHA-1 hashed files), branch references, the HEAD pointer, the staging index, config files, and hooks.

If you delete .git/, the project immediately stops being a Git repository. All commit history, branches, and tags are gone permanently. The working files remain, but there is no version history.

Key contents: objects/ (all data), refs/ (branches/tags as files), HEAD (current branch), index (staging area), config (repo settings), hooks/ (event scripts).

Q68What is git bisect and when would you use it?▼
ANSWER
git bisect is a debugging tool that uses binary search to find the exact commit that introduced a bug.

You tell Git a "bad" commit (where the bug exists) and a "good" commit (where it didn't). Git checks out the midpoint commit. You test — if the bug is there, tell Git "bad"; if not, "good". Git keeps halving the range until it pinpoints the exact first bad commit.

Why it's powerful: 500 commits would normally take 500 manual checks. Binary search finds the culprit in ~9 steps (log₂ 500 ≈ 9).

git bisect start → git bisect bad → git bisect good v2.0 → test each midpoint → git bisect reset

binary search through commitsfind bug-introducing commit500 commits = ~9 steps
Q69What is the difference between Git and SVN?▼
ANSWER
The fundamental difference is distributed vs centralized.

Git (distributed) — every developer has a full local copy of the entire repository history. You can commit, branch, and view history entirely offline. No single point of failure — every clone is a full backup. Branching is cheap and fast (just a pointer).

SVN (centralized) — one central server holds all history. Developers only have working files. Every operation (commit, log, branch) requires a network connection to the server. If the server dies, history is gone (unless backed up). Branching copies the entire directory tree — slow.

Git = distributed, full history everywhereSVN = central server, single point of failureGit branching = fast/cheap
Q70What is the difference between Git Flow and Trunk-Based Development?▼
ANSWER
Git Flow — uses multiple long-lived branches: main (production), develop (integration), plus supporting branches (feature/, release/, hotfix/). More structure, more ceremony. Good for scheduled release cycles and versioned software (mobile apps, packaged products).

Trunk-Based Development — everyone commits to a single main branch (trunk) directly or via very short-lived branches (merged within hours or 1-2 days max). Frequent integration, no long-lived branches. Feature flags hide incomplete work. Requires strong CI — tests must be fast and reliable.

What high-frequency teams use: Google, Netflix, and Facebook use trunk-based development. It's what enables continuous deployment — you can't ship 10x per day with Git Flow's ceremony.

Git Flow = structure, long-lived branchesTrunk = single branch, ship oftenhigh-frequency deploy = trunk-based
Q71What is Prometheus and how does it work?▼
ANSWER
Prometheus is an open-source monitoring and alerting toolkit. Key characteristics:

Pull-based scraping: Prometheus pulls metrics from targets on a schedule. Each target exposes a /metrics HTTP endpoint with current metrics. Prometheus scrapes it every 15 seconds by default.

Time-series database: Stores all metrics with timestamps. Efficient for queries like "what was my error rate at 3 AM last Tuesday?"

PromQL: The query language. Powers Grafana dashboards and alert rules. rate(http_requests_total[5m]) = request rate over last 5 mins.

Alertmanager: Separate component. Routes alerts to Slack, PagerDuty, email. Handles deduplication and silencing.

Q72What is the difference between monitoring and logging?▼
ANSWER
Monitoring — collecting and analyzing data about the current state of your system. Answers: "Is the system healthy right now? Is CPU at 90%? Are requests timing out?" Focuses on metrics (numbers over time). Tools: Prometheus, Grafana, CloudWatch.

Logging — collecting the historical record of what happened. Answers: "What did the app do at 2:17 AM? What error did user X encounter? Who called this endpoint?" Focuses on events and messages. Tools: ELK Stack (Elasticsearch + Logstash + Kibana), Loki, CloudWatch Logs.

In practice, you need both: monitoring to know something is wrong, and logging to understand why it went wrong.

Q73What is Configuration Management and why is Ansible used for it?▼
ANSWER
Configuration Management is the practice of maintaining consistent software and OS configuration across all servers.

The problem: You have 100 servers. You need Nginx installed, a cert updated, a user created on all of them. Manual SSH is unscalable. Bash scripts break. Servers drift apart over time ("snowflake servers" — each is unique).

Ansible solves this: Write a YAML playbook declaring desired state. Ansible connects via SSH (agentless), checks current state, applies changes only where needed. Idempotent — safe to run repeatedly. If Nginx is already installed, Ansible skips it.

Key terms: Playbook (YAML config), Inventory (list of target servers), Idempotent (same result whether run once or 10 times), Agentless (SSH only, no agent installed).

Q74What is rate limiting and what are the two main algorithms?▼
ANSWER
Rate limiting controls how many requests a client can make in a time window. It prevents abuse, protects servers from overload, and enforces API quotas.

Token Bucket — a bucket holds a fixed number of tokens. Tokens are replenished at a fixed rate. Each request consumes one token. When tokens run out, requests are rejected. Allows short bursts — if you saved up tokens, you can fire them all at once.

Leaky Bucket — a bucket fills with incoming requests. Requests leak out at a fixed rate regardless of how fast they came in. If the bucket overflows, new requests are dropped. Smooths bursts — output rate is always constant.

Key difference: Token Bucket allows bursts. Leaky Bucket enforces a constant output rate.

token bucket = allows burstsleaky bucket = constant rateprotects from abuse + overload
