🎯 Real Interview Q&A — 15 Questions, Straight From the Interviewer's Mouth
These are asked, word for word, in real DevOps interviews. Click any question to reveal the full answer — quick version first, then the deep version, a real story, the follow-up trap they'll spring next, and the mistake that gives away a shallow answer.
L1Walk me through what happens when you type >, >>, and 2> at the end of a command.▼
ANSWER
Quick answer: > overwrites a file with stdout, >> appends to it, and 2> redirects stderr instead of stdout.

Detailed answer: Every command in Linux talks through three streams — stdin (0), stdout (1), and stderr (2). When I run ls > files.txt, the shell sends stdout into the file, replacing whatever was there. >> appends — I use this for cron logs so I don't lose history. 2> catches errors specifically. To silently ignore errors I do command 2> /dev/null. To capture both, I use > file 2>&1 or &>.

💬 Quick story: I once had a script writing to /var/log/myapp.log using > instead of >> — every cron run was overwriting the previous log. Lost three days of debugging data before I caught it. Since then, >> is muscle memory.

⚠️ Follow-up trap: If they ask "what does 2>&1 mean and why is the order important?" — explain it redirects stderr to wherever stdout is currently going. Order matters: > file 2>&1 works, but 2>&1 > file doesn't.

🚫 Common mistake: Saying "> is for output and 2> is for errors." Surface-level. Mention file descriptors (0, 1, 2) — that's what separates memorization from understanding.
L2Disk is at 95% on a production server. Your senior just pinged you on Slack. What do you actually run?▼
ANSWER
Quick answer: df -h to confirm the mount, du -sh /* to find the heavy directory, then find to spot huge or old files for rotation.

Detailed answer: First — df -h to confirm which filesystem is full. Then I cd into the suspect path and run du -sh * | sort -hr | head -10 to see top offenders. Nine times out of ten it's /var/log with unrotated logs. I run find . -type f -size +500M for huge files, or find /var/log -type f -mtime +30 for old ones. For logs, I truncate with > /var/log/bigfile.log — never rm an open log file. Then I set up logrotate so it doesn't repeat.

💬 Quick story: The first time I dealt with this, I rm'd a 40 GB log file and watched df -h still show 95%. The application had the file open. I had to restart the service to release the descriptor.

⚠️ Follow-up trap: "What if du shows everything is small but df says full?" — deleted-but-open files. Use lsof | grep deleted to find processes holding deleted file descriptors, then restart that service.

🚫 Common mistake: Don't jump straight to rm -rf. Senior engineers want to hear that you investigate first, fix the root cause (set up rotation), and never delete anything you can't recover.
L3What's the difference between a hard link and a soft link? And when have you actually used either one?▼
ANSWER
Quick answer: A hard link is a second name for the same inode; a soft link is a separate file pointing to a path. Delete the original — hard link still works, soft link breaks.

Detailed answer: Every file in Linux is an inode (the actual data) plus a name pointing to it. A hard link gives you a second name for the exact same inode — both equal, no "original." Delete one, the data stays until the last name is gone. A soft link is its own tiny file containing a path — if the target moves or gets deleted, it dangles. I use soft links daily — pointing /usr/bin/python to python3.11, symlinking config into /etc/nginx/sites-enabled/. Hard links I've used for backup scripts where I want multiple snapshots without duplicating disk.

💬 Quick story: We had a deploy script that created a symlink current → release-v23. To roll back, we just repointed the symlink to v22 — instant rollback, no file copy. Symlinks make tricks like this possible.

⚠️ Follow-up trap: "Can you hard-link across filesystems?" — No. Hard links share inodes, and inodes are filesystem-specific. Soft links can cross filesystems because they just store a path.

🚫 Common mistake: Don't say "a hard link is a copy." It's not — same data, two names. Saying "copy" loses the interviewer instantly.
L4Some service is using port 8080 and you don't know who. How do you find the process?▼
ANSWER
Quick answer: sudo lsof -i :8080 or sudo ss -tulnp | grep 8080 — both give you the PID and process name.

Detailed answer: On modern systems I prefer ss over netstat — faster, pre-installed. Flags: -t TCP, -u UDP, -l listening, -n numeric, -p process. So sudo ss -tulnp | grep 8080 gives me everything. If ss isn't there, sudo lsof -i :8080 works and shows the user. Once I have the PID, ps -p <pid> -f shows the full command line.

💬 Quick story: I once spent 20 minutes trying to start a Docker container on port 8080 before realizing a leftover python http.server from a previous test was still running in a detached tmux session. lsof -i :8080 solved in 2 seconds what 20 minutes of docker logs couldn't.

⚠️ Follow-up trap: "Can you find it without sudo?" — You can't see other users' processes without sudo. The PID column will be blank. That's a Linux security feature, not a bug.

🚫 Common mistake: Don't say netstat -anp. Deprecated on most modern distros. ss kept up.
L5Tell me the difference between ps, top, and htop — and which one you reach for in production.▼
ANSWER
Quick answer: ps is a snapshot, top is a live view that ships with every Linux box, htop is the prettier interactive version — but not always installed.

Detailed answer: ps gives a one-time snapshot — I use it for scripting because output is parseable: ps -ef | grep nginx. top is what I reach for first on any production box because it's always there. Updates every few seconds, shows CPU, memory, load average. htop I install on dev boxes — colored, tree view, click-to-kill, scrollable. Same data, friendlier UI. In an incident, I start with top, hit M to sort by memory or P by CPU, and find the offender in seconds. Press H for threads.

💬 Quick story: A Java service slowly ate memory in staging. top showed the JVM at 8 GB and climbing. Sorted by memory with M, confirmed a leak, dug into GC logs. Without top, I'd have stared at Grafana for an hour.

⚠️ Follow-up trap: "What does load average actually mean?" — the average number of processes in a runnable or uninterruptible state over 1, 5, 15 minutes. Load 4 on a 4-core box = 100% utilization. Load 8 on the same box = processes queuing.

🚫 Common mistake: Don't say load average is "CPU usage." It includes processes waiting on disk I/O. Mixing them up tells the interviewer you've never debugged a real I/O bottleneck.
L6What does chmod 755 file.sh actually mean? Break the numbers down for me.▼
ANSWER
Quick answer: Owner gets read-write-execute (7), group gets read-execute (5), others get read-execute (5). Standard for executable scripts.

Detailed answer: Three permission groups (owner, group, others) and three permissions (read=4, write=2, execute=1). Add them: 7 = 4+2+1 (full), 5 = 4+1 (read+execute), 4 (read-only). For a script anyone should run, 755 is right. For a private SSH key, 600. For a config with secrets, 640 or 600.

💬 Quick story: I once chmod 777'd a directory because I was tired of fighting permissions on a shared dev box. Two days later, our security scanner flagged it and I had to write up an incident report. 777 is almost always the wrong answer.

⚠️ Follow-up trap: "Difference between chmod and chown?" — chmod changes permissions (what), chown changes ownership (who). Used together: chown to assign the right user, then chmod to set permissions.

🚫 Common mistake: Don't memorize "755 means executable." Understand the math. If they ask about 2755, you should derive it on the spot — the leading 2 introduces setgid, which trips up most candidates.
L7Walk me through scheduling a job to run every 5 minutes. And how would you debug it if it doesn't run?▼
ANSWER
Quick answer: crontab -e, add */5 * * * * /path/to/script.sh, and if it doesn't run I check journalctl -u cron plus the script's output redirection.

Detailed answer: Cron format: minute, hour, day-of-month, month, day-of-week. */5 * * * * means every 5th minute. I always redirect both stdout and stderr: */5 * * * * /path/to/script.sh >> /var/log/myscript.log 2>&1 — cron has a stripped-down environment with almost no PATH and silent failures. If it's still not running, check journalctl -u cron. Nine times out of ten it's PATH — the script works in my shell, cron doesn't know where kubectl or python live. Fix: absolute paths, or source /etc/profile at the top.

💬 Quick story: Wrote a backup cron, tested manually, forgot output redirection. Silently failed for two weeks because cron emailed output to root@localhost and there was no mail daemon. Two weeks of zero backups. >> file 2>&1 is now mandatory in every cron line I write.

⚠️ Follow-up trap: "Run every 5 minutes during business hours only?" — */5 9-17 * * 1-5 /path/to/script.sh.

🚫 Common mistake: Don't forget cron's environment is not your shell's. Test with env -i bash -c "/path/to/script.sh" to simulate cron's empty environment before trusting it.
L8kill, kill -9, kill -15 — what's the difference and which should you use first?▼
ANSWER
Quick answer: kill defaults to -15 (SIGTERM, polite), -9 is SIGKILL (forced, no cleanup). Always start with -15; only escalate to -9 if it refuses.

Detailed answer: SIGTERM is "please shut down." The process catches it, finishes current work, closes DB connections, flushes logs, exits cleanly. SIGKILL bypasses the process — the kernel kills it instantly. No cleanup means open files might corrupt, transactions left half-done, child processes orphaned. My rule: -15 first, wait 10–15 seconds, only -9 if genuinely stuck.

💬 Quick story: A teammate kill -9'd a stuck PostgreSQL during an incident. The DB came back up, but one table was inconsistent — four hours of recovery. I treat -9 as last resort, not first move.

⚠️ Follow-up trap: "What if a process ignores SIGTERM?" — Some catch it and refuse to die because they're waiting on something (like a stuck NFS mount). At that point, SIGKILL is the only option because the kernel handles it directly.

🚫 Common mistake: Saying "-9 is the safe option because it always works." It "works" in that it terminates — but at the cost of data integrity. Red flag in any production-minded interview.
L9What is journalctl and how do you use it to debug a service that's failing to start?▼
ANSWER
Quick answer: The systemd log query tool. For a failing service: journalctl -u <service> -n 100 --no-pager for the last 100 lines, or -f to tail live.

Detailed answer: On any modern Linux, systemd manages services and journalctl reads its logs. Flags I use most: -n 200 last 200 lines, -u nginx filter by service, -f follow live, --since "10 min ago", -p err errors only. My flow: systemctl status <service> first — gives recent log lines and the exit code. If I need more, journalctl -u <service> -n 500. I look for the first error, not the last — cascading failures hide the real cause.

💬 Quick story: Jenkins refused to start. systemctl status said "failed." journalctl -u jenkins showed "Java not found in PATH." Root cause: someone had uninstalled Java for a "cleanup." Two minutes saved a full rebuild.

⚠️ Follow-up trap: "How do you keep journal logs from growing forever?" — Edit /etc/systemd/journald.conf: SystemMaxUse=2G or MaxRetentionSec=1month.

🚫 Common mistake: Saying "I'd tail /var/log/syslog." On systemd distros, services log to journal first — syslog may have something or nothing. journalctl is authoritative.
L10grep, awk, sed — explain when you'd reach for each one. Make it real.▼
ANSWER
Quick answer: grep finds lines, awk extracts and processes columns, sed edits text in place. I use them together in pipelines where each does what it's best at.

Detailed answer: grep: searching — "does this line contain X?" Use -i case-insensitive, -v invert, -E extended regex. awk: column-aware, a mini language. Logs and CSVs are home turf. awk '{print $1, $7}' on access.log gives column 1 and 7. awk '$9 == 500' filters where column 9 equals 500. sed: in-place editing. sed -i 's/old/new/g' file.txt replaces every "old" with "new" — I use it for find-and-replace across config files during deploys. A pipeline I run all the time: cat access.log | grep " 500 " | awk '{print $1}' | sort | uniq -c | sort -rn | head -10 — top 10 IPs hitting my server with 500 errors, in one line.

💬 Quick story: During an incident, the app was returning 500s. I had load balancer logs but no fancy dashboard. That one-liner identified a single IP making 90% of bad requests in seconds. Blocked it, traffic normalized.

⚠️ Follow-up trap: "Could you do all this in awk alone?" — Technically yes: awk '/pattern/ && $9==500 {print $1}'. But mixing tools in a pipeline is more readable than a 200-character awk script. Readability matters at 3 AM.

🚫 Common mistake: Saying awk is "for printing columns." That's 1% of what it does — it has variables, conditionals, loops, regex, a full language. Underselling it tells the interviewer you've used it once.
L11How do you find files modified in the last 24 hours?▼
ANSWER
Quick answer: find /path -type f -mtime -1 — modified less than 1 day ago. Or -mmin -60 for the last 60 minutes.

Detailed answer: find uses three time flags: -mtime modification time in days, -atime access time, -ctime inode-change time. Negative means "less than" — -mtime -1 is "modified less than 24 hours ago." Positive means "more than." Add -type f for files only, -type d for directories. For sub-day precision, use -mmin in minutes. To run a command on each result: -exec ls -lh {} \;.

💬 Quick story: Production was acting weird after a deployment. I ran find /etc -type f -mtime -1 and found two config files someone had hot-patched manually. They never told the team. Diff against Git answered the rest.

⚠️ Follow-up trap: "Difference between mtime, atime, ctime?" — mtime = content changed, atime = file was read, ctime = inode changed (permissions, ownership). ctime is the one most candidates miss.

🚫 Common mistake: Confusing -mtime 1 (exactly 1 day) with -mtime -1 (less than 1 day). The sign matters.
L12What is a zombie process and how do you handle it?▼
ANSWER
Quick answer: A zombie is a child process that's finished but its parent hasn't called wait() to read its exit status. It holds a PID slot until the parent reaps it.

Detailed answer: When a process exits, the kernel keeps minimal info (PID, exit code) until the parent reads it via wait(). If the parent doesn't, the child sits in <defunct> state — a zombie. It uses no CPU or memory, but it holds a PID. If a buggy parent never reaps and keeps spawning, you eventually exhaust the PID table and can't fork new processes. To check: ps aux | grep defunct. You can't kill a zombie directly — it's already dead. You kill the parent, and init (PID 1) adopts and reaps the orphans.

💬 Quick story: A Python app on a customer's server stopped accepting new connections. ps aux showed 30,000 zombies. The parent process was spawning workers but never calling wait(). We killed the parent, init reaped them, and the server breathed again.

⚠️ Follow-up trap: "What's the difference between a zombie and an orphan?" — Orphan: parent died, init adopts. Zombie: child died, parent didn't reap. Different problems.

🚫 Common mistake: Saying "I'd kill -9 the zombie." You can't — it's already dead. Killing the parent is the fix.
L13Explain the Linux boot process in brief.▼
ANSWER
Quick answer: BIOS/UEFI → bootloader (GRUB) → kernel + initramfs → init system (systemd) → target/runlevel → user login.

Detailed answer: Power on: BIOS or UEFI runs hardware checks (POST), finds the bootloader on disk. GRUB loads, shows the boot menu, hands control to the kernel. The kernel decompresses, mounts initramfs (a tiny RAM filesystem with just enough drivers to mount the real root). Once root is mounted, the kernel hands off to PID 1 — usually systemd. Systemd reads its target (like multi-user.target or graphical.target), starts services in dependency order, and finally launches getty for login. The whole thing takes seconds on modern hardware.

💬 Quick story: A box wouldn't boot after a kernel update. Got the GRUB screen, but the kernel kicked into an emergency shell. journalctl from the rescue shell showed initramfs was missing the SCSI driver. Booted the previous kernel, rebuilt initramfs with dracut, problem solved.

⚠️ Follow-up trap: "What's the difference between BIOS and UEFI?" — UEFI is the modern replacement: faster boot, supports drives >2TB, secure boot, GUI-friendly. BIOS is legacy 16-bit firmware.

🚫 Common mistake: Skipping initramfs entirely. It's the bridge between the kernel and the real root filesystem — interviewers love asking why it exists.
L14How do you write an idempotent shell script?▼
ANSWER
Quick answer: Make every operation safe to run multiple times — check before acting. Use if [ ! -f file ]; then create file; fi instead of blind creation.

Detailed answer: Idempotent means: run it 10 times, the result is the same as running it once. For file creation: [ -f /etc/myconfig ] || cp template /etc/myconfig. For directories: mkdir -p instead of mkdir. For users: check id user >/dev/null 2>&1 || useradd user. For packages: most package managers are already idempotent — apt install -y nginx is safe to re-run. For lines in config files: use grep -q "pattern" file || echo "pattern" >> file. The principle: never blindly append, overwrite, or create — always check state first.

💬 Quick story: Wrote a non-idempotent setup script that appended a line to /etc/hosts. Re-ran it three times during testing. Ended up with three duplicate entries breaking DNS resolution. Now every config-modifying script I write starts with a state check.

⚠️ Follow-up trap: "How is this different from Ansible?" — Ansible's modules are idempotent by design. Same logic, just wrapped in a higher-level abstraction. Ansible is essentially industrial-strength idempotent shell.

🚫 Common mistake: Saying "I use set -e for idempotency." set -e makes scripts exit on error — that's safety, not idempotency. Different concepts.
L15What's the difference between &, &&, |, and ||?▼
ANSWER
Quick answer: & runs in background, && runs the next command only if the previous succeeded, | pipes output between commands, || runs the next command only if the previous failed.

Detailed answer: &: long-script.sh & backgrounds it, frees the shell. &&: make && make install — install only runs if make succeeded. |: cat file | grep error — stdout of the left becomes stdin of the right. ||: cmd || echo "failed" — fallback if cmd fails. You can chain: backup.sh && echo "ok" || echo "failed". Common pattern: command || exit 1 in scripts to bail early on failure.

💬 Quick story: A teammate's deploy script had build & deploy instead of build && deploy. Build was running in the background while deploy started immediately on stale artifacts. Looked random in CI. One character, one production rollback.

⚠️ Follow-up trap: "What does $? hold?" — The exit code of the last command. 0 = success, anything else = failure. && and || both check this.

🚫 Common mistake: Confusing | and ||. A single pipe is data flow, a double pipe is a logical OR. Completely different worlds.

What would you run?
ss -tulpn | grep 3000
(no output — nothing is listening on port 3000)
Why this command: Empty output here is itself the answer — the app never actually started, or it's listening on a different port than you think. Confirm this BEFORE spending an hour debugging firewalls for a problem that isn't there.
5
The situation: Your CI pipeline fails with Permission denied trying to run ./deploy.sh — the exact same script that works fine when you run it locally.
What would you run?
chmod +x deploy.sh git add deploy.sh git commit -m "fix: make deploy.sh executable"
before: -rw-r--r-- deploy.sh after: -rwxr-xr-x deploy.sh
Why this command: Git tracks the execute bit. If the file was ever committed without it, every fresh checkout — including your CI runner — loses execute permission, even though your own local copy still has it set.
6
The situation: You're migrating to a new API domain. Before you change anything, you need to find every single config file that still mentions the old one.
What would you run?
grep -rl "old-api.example.com" /etc/
/etc/nginx/sites-enabled/app.conf /etc/myapp/config.yml 2 files found
Why this command: -r searches every subfolder, -l prints just the filenames (not every matching line) — exactly the checklist you need before a domain migration, in one command.
7
The situation: A stuck process refuses to shut down. You already tried asking it nicely — it ignored you.
What would you run?
first, the polite request (already tried, ignored): kill 4821 it's still running 15 seconds later — now force it: kill -9 4821
process 4821 terminated
Why this order matters: plain kill sends SIGTERM — a clean shutdown request the process can catch and finish up gracefully. -9 is SIGKILL, enforced instantly by the kernel with zero cleanup. Always try the polite version first.
8
The situation: You just edited nginx's config file to fix a routing bug. You reload the site — nothing changed. The bug is still there.
What would you run?
sudo systemctl restart nginx
nginx.service restarted
Why this command: Editing a config file only changes the file on disk — the running process keeps using whatever it loaded into memory at startup. Nothing takes effect until the service actually restarts and re-reads it.
9
The situation: systemctl status myapp just shows "failed" — no explanation. You need the actual error, not just the word "failed."
What would you run?
journalctl -u myapp -n 50 --no-pager
10:14:02 myapp Started myapp.service 10:14:03 myapp Error: connect ECONNREFUSED 127.0.0.1:5432 10:14:03 myapp Process exited with code 1
Why this command: "failed" is systemd's one-word summary — journalctl -u shows the actual log lines that service printed right before it died. The real cause is almost always in the last few lines before the exit.
10
The situation: Your backup script runs perfectly every time you test it by hand. Every night at 2am via cron, it silently does nothing.

📁 Linux Filesystem Cheatsheet — Where Everything Actually Lives
Every folder off the root / has one specific job. Once you know what lives where, you stop guessing and start going straight to the answer.
/etc
/etc ↓ System configuration files
Examples:
/etc/passwd → users /etc/group → groups /etc/hosts → hostname-to-IP mapping /etc/fstab → filesystem mount configuration /etc/crontab → scheduled tasks /etc/ssh → SSH configuration
Commands you'll use:
cat /etc/passwd cat /etc/hosts grep '^john:' /etc/passwd
/home
/home ↓ User home directories
Examples:
/home/steve /home/tony /home/banner
Each user's personal files are stored here.
/root
/root ↓ Root user's home directory
Normal users: /home/steve Root user: /root
/var
/var ↓ Frequently changing data
Examples:
/var/log /var/cache /var/tmp
Disk problems often start here.
/var/log
/var/log ↓ Log files
Examples:
/var/log/messages /var/log/secure /var/log/httpd /var/log/nginx
Application crashing? Look here first.
Commands you'll use:
cd /var/log ls find . -type f -size +500M
/tmp
/tmp ↓ Temporary files
Applications store temporary data here. Files may be deleted automatically.
/opt
/opt ↓ Optional or third-party software
Examples:
/opt/app /opt/backups /opt/scripts
You'll see /opt a lot in KodeKloud labs.
/usr
/usr ↓ Programs and application files
Examples:
/usr/bin /usr/sbin /usr/local
/usr/bin
/usr/bin ↓ Regular executable commands
Examples:
python grep cat ssh
Command: which python Output: /usr/bin/python
/usr/sbin
/usr/sbin ↓ Administrative commands
Examples:
useradd nologin systemctl
Command: which nologin Output: /usr/sbin/nologin
/bin
/bin ↓ Essential commands
Examples:
ls cp mv rm
/boot
/boot ↓ Boot files
Examples: Kernel, GRUB, bootloader files.
Remember:
BIOS/UEFI ↓ GRUB ↓ Kernel ↓ systemd ↓ Login
/dev
/dev ↓ Devices
Examples:
/dev/sda /dev/sda1 /dev/null
Disks, partitions, and devices appear here.
/proc
/proc ↓ Process information
Examples:
/proc/cpuinfo /proc/meminfo
System information lives here.
~
~ ↓ Your home directory
Example:
User = steve ~ → /home/steve
~/.bashrc
~/.bashrc ↓ Bash configuration
Examples:
alias ll='ls -la' export APP_ENV=production
After editing:
source ~/.bashrc
