🔥 Deep Design Questions
FE01Design a zero-downtime database migration strategy for a production app with millions of users.▼
ANSWER
This tests understanding of backward compatibility, deployment sequencing, and rollback safety.

The core problem: You can't take the DB offline. You can't deploy app + DB migration simultaneously — the old app will hit new schema during rollout, and the new app will hit old schema before migration completes.

The Expand-Contract Pattern (3 phases):

Phase 1 — Expand (backward compatible change):
Add the new column/table as nullable. Deploy nothing yet. Existing app still works with old schema. Run the migration to add the column.

Phase 2 — Migrate (dual-write or backfill):
Deploy new version of app that writes to BOTH old and new columns. Backfill existing rows with a background job. Once backfill completes and new column has all data, both versions of the app work.

Phase 3 — Contract (remove old column):
Deploy app version that only reads/writes new column. Then drop the old column in a separate migration.

Key rule: Never deploy a breaking schema change and application change simultaneously. Always make schema changes backward compatible first.

expand → migrate → contractbackward compatible firstnever simultaneous app + schema deploy
FE02How do you secure a Kubernetes cluster end-to-end? Walk through every layer.▼
ANSWER
Layer 1 — API Server access:
Disable anonymous authentication. Use RBAC — no wildcard permissions. Audit logging on. Never expose the API server to the internet — use a bastion or VPN.

Layer 2 — Node security:
Workers in private subnets. Security groups block all but necessary ports. OS hardened. Automated patch management via managed node groups (EKS handles this).

Layer 3 — Pod security:
Run containers as non-root (runAsNonRoot: true). Read-only root filesystem. Drop all Linux capabilities, add back only what's needed. Pod Security Admission enforces these standards.

Layer 4 — Network security:
NetworkPolicies — by default all pods can talk to all pods. Apply least-privilege NetworkPolicies: payment service can only talk to DB, not to the logging service.

Layer 5 — Secrets:
Never store real secrets in K8s Secrets unencrypted. Use Sealed Secrets or External Secrets Operator (sync from AWS Secrets Manager). Encrypt etcd at rest.

Layer 6 — Images:
Only pull from trusted registries. Scan images for CVEs in CI (Trivy, Snyk). Use image digest pinning instead of mutable tags (:latest is dangerous).

Layer 7 — Audit + Monitoring:
K8s audit logs → Cloudwatch/SIEM. Runtime threat detection (Falco watches for suspicious syscalls). Alert on privilege escalation attempts.

RBAC + no wildcardsnon-root podsNetworkPoliciesencrypted secretsimage scanning
FE03Design a disaster recovery plan for a multi-region AWS application with an RTO of 1 hour and RPO of 5 minutes.▼
ANSWER
RTO (Recovery Time Objective) = how long can you be down? 1 hour max.
RPO (Recovery Point Objective) = how much data can you lose? 5 minutes max.

Data strategy (RPO = 5 mins):
RDS Multi-AZ for same-region HA (synchronous replication, ~0 RPO). Cross-region: enable RDS Read Replica in us-west-2 with async replication (lag ~1-3 mins, meets 5 min RPO). For S3: enable Cross-Region Replication with versioning.

Compute strategy (RTO = 1 hour):
Run a "warm standby" in the secondary region — ECS/EKS cluster at minimum capacity (1 pod per service). Can scale up in ~10 minutes. Keep AMIs replicated cross-region for fast EC2 launch.

Networking:
Route 53 health checks on primary region. Failover routing policy: if primary health check fails, Route 53 automatically routes traffic to secondary region's ALB. DNS TTL set to 60 seconds so failover propagates in ~1 min.

Runbook automation:
Pre-written runbook (ideally automated with AWS Systems Manager). Promotes RDS read replica to primary. Scales up secondary compute. Updates any hardcoded endpoints. Target: RTO under 15 minutes in practice.

Regular DR drills:
Test the failover quarterly. "Game days" — actually fail over to secondary. A DR plan never tested is not a DR plan.

RDS cross-region replica (5 min lag)warm standby computeRoute 53 health check + failoverdrill quarterly
FE04Your microservices system has 50 services. Deploys have become slow and risky. How do you redesign the CI/CD architecture?▼
ANSWER
Problem analysis: With 50 services, a monorepo pipeline that rebuilds everything on every commit is catastrophic. A polyrepo without shared standards leads to 50 different pipeline configs.

Solution: Service-specific pipelines with shared templates:

1. Affected-only builds: Only build and deploy services whose code actually changed. Use tools like Nx, Turborepo (monorepo) or trigger detection scripts that check which directories changed via git diff.

2. Pipeline templates: Create reusable GitHub Actions workflow templates / Jenkins shared libraries. Every service uses the same tested template. Change the template once, all services get it.

3. GitOps for deployments: Separate application code repos from deployment config repos. CI writes the new image tag to the deployment repo. ArgoCD picks it up and syncs. Rollback = revert a Git commit.

4. Parallel execution: Independent services build and test in parallel. Only sequential steps are: test → build image → deploy to staging → integration test → deploy to prod.

5. Contract testing: Instead of expensive full integration tests, use consumer-driven contract tests (Pact). Each service tests its interface contracts independently — no full stack needed.

6. Progressive delivery: All production deploys via canary (5% → 25% → 100%). Automated rollback if error rate spikes. Operators monitor, not babysit.

FE05How would you migrate a legacy monolith from bare-metal servers to AWS with zero downtime?▼
ANSWER
Phase 1 — Lift and Shift (0 risk):
Mirror the monolith to EC2 first. Don't refactor yet. Use AWS Server Migration Service or manually replicate. Set up the same environment. Validate it works identically.

Phase 2 — Database migration:
Use AWS DMS (Database Migration Service) to continuously sync the on-premise DB to RDS with CDC (Change Data Capture) replication running live. Zero data loss.

Phase 3 — Traffic shifting:
Both environments running simultaneously. Use weighted DNS (Route 53) to shift 5% → 25% → 50% → 100% of traffic to AWS. Monitor error rates at each step. Rollback = flip DNS weight back.

Phase 4 — Cutover:
Once 100% traffic on AWS, freeze on-premise writes, run final DB sync, promote RDS as primary. Decommission on-premise.

Phase 5 — Containerize (optional, later):
Once stable on AWS, containerize into Docker/ECS. Then, if needed, break apart into microservices (Strangler Fig pattern).

Key principle: Lift and shift first. Optimize after. Never try to refactor AND migrate at the same time — too risky.

🔥 More Scenario Questions
FE06A Kubernetes pod is stuck in "Pending" state for 20 minutes. Walk through every possible cause.▼
ANSWER
Pending = the pod has been accepted by K8s but no node has been assigned yet. The Scheduler couldn't place it.

Run first: kubectl describe pod <name> — read the Events. The answer is almost always in there.

Cause 1 — Insufficient resources: Pod requests 4 CPU but no node has 4 free CPUs. Events say "Insufficient cpu" or "Insufficient memory". Fix: scale up the node group or reduce resource requests.

Cause 2 — No matching node (NodeSelector/Affinity): Pod has a nodeSelector requiring type: gpu but no GPU nodes exist. Fix: add the right nodes or remove the constraint.

Cause 3 — Taints and Tolerations: All nodes have taints the pod doesn't tolerate. Fix: add tolerations to the pod spec.

Cause 4 — PVC not bound: Pod requires a PersistentVolumeClaim that hasn't been provisioned yet or the StorageClass can't provision in this AZ. Events say "waiting for volume to be created". Fix: check PVC status with kubectl get pvc.

Cause 5 — Image pull limit (indirect): Sometimes indirectly — if init containers are failing during scheduling evaluation.

Cause 6 — Cluster autoscaler delay: Node group needs to scale up to accommodate the pod. Check if a new node is being provisioned with kubectl get nodes.

describe pod = look at Eventsinsufficient resourcesnodeSelector mismatchPVC not bound
FE07Your Docker image is 2.4GB. The team wants it under 100MB. How do you do it?▼
ANSWER
Step 1 — Diagnose first: docker image history myapp:latest — see which layers are large. dive myapp:latest (tool) for interactive layer inspection.

Step 2 — Switch to Alpine or Distroless base:
FROM node:18 = ~950MB. FROM node:18-alpine = ~170MB. FROM gcr.io/distroless/nodejs18 = ~100MB. This alone often cuts 80%.

Step 3 — Multi-stage build:
Build in a full image (with compilers, dev dependencies). Copy only the final compiled artifact to a minimal runtime image. The build tools never end up in production.

Step 4 — .dockerignore:
Add node_modules/, .git/, tests/, *.md, coverage/. These shouldn't be COPY'd into the image.

Step 5 — Combine RUN commands:
Each RUN is a layer. Combine: RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*. Cleaning up in the same layer prevents the garbage from persisting.

Step 6 — Don't install dev dependencies:
npm install --production or npm ci --only=production. Dev packages can be 10x the size of prod packages.

FE08You run `terraform apply` and it destroys a production database. It wasn't supposed to. Why did this happen and how do you prevent it?▼
ANSWER
Why it happened — common causes:

1. Resource rename: Someone renamed the Terraform resource block (e.g., resource "aws_db_instance" "db" → resource "aws_db_instance" "prod_db"). Terraform sees the old one as deleted and new one as created. Result: destroy + create.

2. Force-replace flag: Someone ran terraform apply -replace=aws_db_instance.db.

3. Changed an immutable attribute: Some AWS resource attributes can't be updated in-place (e.g., changing RDS engine version). Terraform destroys and recreates.

Prevention — multiple layers:

lifecycle prevent_destroy:
resource "aws_db_instance" "prod_db" {
  lifecycle {
    prevent_destroy = true
  }
}
Terraform will refuse to destroy this resource. Any plan attempting to destroy it will fail.

Require plan review: Never run terraform apply directly in prod. CI/CD pipeline generates a plan, posts it as PR comment, requires human approval before applying.

terraform state mv: If you need to rename a resource, use terraform state mv old_name new_name to rename it in the state file without destroying it.

Separate state per environment: Prod infra in a completely separate state file and workspace. Mistakes in dev don't affect prod.

prevent_destroy lifecycleplan before applyterraform state mv for renamesseparate state per env
FE09Your AWS bill doubled this month with no new features shipped. How do you investigate?▼
ANSWER
1. AWS Cost Explorer: Filter by service. Which service increased most? Filter by resource tag to find the specific resource.

2. Common culprits to check:
• NAT Gateway: Often a hidden cost driver. Every GB processed costs money. Check if something is routing unnecessary traffic through NAT (e.g., EC2 downloading S3 data via NAT instead of VPC endpoint).
• Data transfer: Cross-AZ or cross-region data transfer adds up. Are services unnecessarily talking across AZs?
• EC2 instances left running: Someone spun up large instances for testing and forgot. Check for untagged resources.
• CloudWatch Logs: An app logging verbosely — millions of log events per day. Check log ingestion costs.
• RDS storage: RDS auto-storage-scaling kicked in, can't scale back down.
• Snapshot/backup accumulation: Old AMI snapshots or DB snapshots accumulating for months.

3. AWS Cost Anomaly Detection: Enable this — it uses ML to detect unusual spending patterns and alerts you before the bill arrives.

4. Tagging enforcement: Every resource should have Environment, Owner, Project tags. Without tags, you can't trace which team/service caused the cost.

FE10Explain how you would implement a GitOps workflow for Kubernetes from scratch.▼
ANSWER
The components you need:

1. Two Git repos:
• App repo: source code, Dockerfile, tests
• Config repo: Kubernetes manifests, Helm charts, Kustomize overlays per environment

2. CI pipeline (in app repo):
On merge to main: run tests → build Docker image → push to ECR with commit SHA as tag → update the image tag in the config repo (automated PR or direct commit to a branch)

3. ArgoCD (in the cluster):
Install ArgoCD. Create an Application resource pointing at your config repo + path + target namespace. ArgoCD continuously polls the config repo. When image tag changes, ArgoCD syncs the cluster to the new state.

4. Environment promotion:
Config repo has envs/staging/ and envs/production/ directories. CI auto-updates staging. Promotion to prod = merge PR that updates prod's image tag. ArgoCD detects and deploys.

5. Rollback:
git revert the tag update commit in the config repo. ArgoCD detects and rolls the cluster back. No kubectl needed in production.

Security benefit: No CI/CD system needs write access to the cluster. The cluster pulls from Git. Much smaller attack surface.

FE11How would you debug a memory leak in a Dockerized production application?▼
ANSWER
Step 1 — Confirm it's a leak:
kubectl top pods or docker stats — watch memory over time. Does it grow continuously and never come down? That's a leak. Does it grow and then GC kicks in and it drops? That's normal.

Step 2 — Confirm via container restarts:
kubectl get pods — high RESTARTS count + OOMKilled in describe = memory is hitting the container limit. Immediate evidence of a leak.

Step 3 — Correlate with traffic:
Does memory grow proportionally with requests? Might be a connection or object that's not being properly released per request.

Step 4 — Language-specific profiling:
• Node.js: --inspect flag → Chrome DevTools heap snapshots
• Java: JVM heap dumps (jmap -dump) → VisualVM or Eclipse MAT
• Python: tracemalloc, objgraph

Step 5 — Short-term mitigation:
Set memory limits and enable automatic pod restarts. HPA or scheduled restart as a bandage while you fix the root cause. Communicate to the team — don't silently paper over it.

Step 6 — Fix and verify:
Deploy fix, run extended load test, verify memory stays flat over time. Only then close the ticket.

kubectl top pods = memory over timeOOMKilled = hitting limitheap dump for root causememory limits = short-term mitigation
FE12Production is getting DDoS'd. Traffic is 50x normal. Walk through your response.▼
ANSWER
Immediate (first 5 minutes):
Check CloudWatch — is this real user traffic or attack traffic? Look at request patterns: same IP? Same User-Agent? Same endpoint being hammered? Bots usually have patterns.

Layer 1 — AWS Shield:
AWS Shield Standard is already on by default — protects against L3/L4 DDoS. If attacks are sophisticated, AWS Shield Advanced (paid) adds 24/7 DRT (DDoS Response Team) support and cost protection.

Layer 2 — AWS WAF (Web Application Firewall):
Attach WAF to CloudFront or ALB. Create rate-based rules: block IPs sending more than 1000 req/5min. Create geo-blocking rules if traffic is from unexpected countries. Enable AWS managed rule groups (bot protection).

Layer 3 — CloudFront:
If not already in front of your app, enable CloudFront. Acts as a buffer — absorbs traffic at the edge, not at your origin. Enable cache for static content (takes load off origin).

Layer 4 — Auto Scaling:
If legitimate traffic is also spiking (viral event), ensure ASG and HPA are configured to scale fast enough. ALB spreads the load.

Layer 5 — Rate limiting at application level:
API gateway rate limiting per IP. Nginx limit_req_zone.

After the attack:
Review WAF logs to understand the attack pattern. Tune rules. Add Cloudflare or AWS Shield Advanced if appropriate. Post-mortem.

WAF rate-based rulesCloudFront as DDoS bufferAWS Shield Standard = free baselinegeo-blocking for bot traffic
FE13How do you handle configuration management across 4 environments (dev/staging/uat/prod) without duplicating Terraform code?▼
ANSWER
The problem: If you copy-paste your Terraform for each environment, you have 4x maintenance burden and they drift apart.

Solution 1 — Terraform Workspaces:
Same code, different state files. terraform workspace new staging creates an isolated state. Use terraform.workspace variable to vary config per environment.
Downside: all environments share the same code — risky if environments need very different configurations.

Solution 2 — Terraform Modules + Separate Variable Files (recommended):
Write reusable modules (e.g., module "vpc", module "ecs_service"). Each environment has its own directory with a main.tf that calls the modules and a terraform.tfvars with environment-specific values.
envs/
  prod/main.tf     # calls modules, uses prod.tfvars
  staging/main.tf  # calls same modules, uses staging.tfvars
modules/
  vpc/
  ecs_service/
Solution 3 — Terragrunt:
DRY wrapper for Terraform. Define common config once, inherit and override per environment. Manages remote state config automatically.

modules = reusable codetfvars per environmentseparate state per envTerragrunt for DRY
FE14You need to run a one-time data migration job in Kubernetes. What's the right way to do it?▼
ANSWER
Use a Kubernetes Job, not a Deployment.

A Job runs one or more pods to completion and then stops. It's designed for batch work: database migrations, data transformations, one-off scripts.

Key properties:
• restartPolicy: OnFailure — retry on failure, but don't restart after success
• completions: 1 — need exactly 1 successful run
• backoffLimit: 3 — retry up to 3 times before marking as failed

For database migrations specifically:
Use an Init Container in your deployment — runs the migration before the main containers start. This ensures the schema is always up to date before the app starts serving traffic. But it runs on every pod restart, so the migration must be idempotent.

Alternatively, run the migration as a Helm hook (helm.sh/hook: pre-upgrade) — runs the migration job before Helm applies the new deployment.

What NOT to do: Don't run migrations inside the app on startup (race condition with multiple replicas). Don't use a Deployment (keeps restarting after success).

Job = runs to completionInit Container = before main app startsHelm pre-upgrade hooknever Deployment for one-time work
FE15What is observability and how is it different from monitoring? What are the three pillars?▼
ANSWER
Monitoring = watching known things. You define what metrics to collect and alert on. You can only answer questions you thought to ask in advance. "Is CPU above 80%?"

Observability = understanding a system's internal state from its external outputs. You can answer questions you didn't think to ask. "Why is user 12345 getting slow responses only when making requests from Germany at 3 PM on Tuesdays?"

The 3 Pillars of Observability:

1. Metrics — numerical measurements over time. CPU, memory, request rate, error rate. Good for alerting, dashboards, trending. Tools: Prometheus, CloudWatch.

2. Logs — timestamped events. "User X failed to authenticate at 14:32:11". Good for debugging specific incidents. Tools: ELK Stack, Loki, CloudWatch Logs.

3. Traces (Distributed Tracing) — follow a single request as it travels through multiple microservices. Shows exactly where time was spent and which service caused a slowdown. Tools: Jaeger, Zipkin, AWS X-Ray. This is the pillar most teams are missing.

Correlation: The real power is when you can go from a metric alert → the relevant logs → the trace for the slow request. Tools like Grafana Tempo or Datadog connect all three.

observability = understand why3 pillars: metrics + logs + tracestraces = most valuable for microservices
