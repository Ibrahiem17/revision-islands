🧠 How to Actually Think About Writing a Script
This is the part tutorials usually skip — not "here's the syntax," but "here's the actual thought process," start to finish.
1
Do it by hand firstbefore writing anything
Before you write a single line of a script, run the actual commands yourself, one at a time, in your real terminal, until they do what you want. A script isn't where you invent the steps — it's where you write down steps you already proved work.
2
Find what changes each time→ variables & arguments
Look at the commands you just ran by hand. Which words would be different the next time you run this — a filename, a server name, an environment? Those become variables, or better, arguments ($1, $2) so the script stays reusable instead of hardcoded.
3
Find what could go wrong→ conditionals & exit codes
For every command, ask: "what does it look like when this fails?" A missing file, a failed network call, an empty variable. Each answer becomes a check — an if, a test like [ -f file ], or an exit 1 that stops things before they get worse.
4
Find what repeats→ loops & functions
Doing the same thing to multiple items — servers, files, environments? That's a for loop. Doing the same few steps in more than one place in the script? Pull them into a function instead of copy-pasting.
5
Test each piece alonebefore gluing it together
Run the variable line by itself. Run the loop by itself with an echo instead of the real command inside it. A script that's assembled from pieces you already know work is infinitely easier to debug than one written all at once and tested for the first time as a whole.
6
Add safety last→ set -euo pipefail
Once the logic actually works, put set -euo pipefail on line 2. Not before — while you're still figuring out the logic, you want to see things fail loudly and understand why. Once it's correct, this line makes sure it stays correct by refusing to continue after anything unexpected.

🎭 Real Scenarios — Learn Shell Scripting by Solving the Problem First
Read the situation, think about what you'd actually write, then click ▶ Run to reveal the command and its real output.
1
The situation: You need a backup script to run automatically every night at 2 AM, with no one around to trigger it manually.
What would you run?
crontab -e
# then add:
0 2 * * * /scripts/backup.sh
(saved — cron now runs backup.sh at 2:00 AM every day)
Why this command: Cron is the standard Linux scheduler for exactly this — "run this command at this time, every day, forever," with zero human involvement needed.
2
The situation: A deploy script creates a lockfile, but if it crashes partway through, the lockfile is left behind and blocks every future run.
What would you run?
trap 'rm -f /tmp/deploy.lock' EXIT
(lockfile is removed no matter how the script ends — success, failure, or interruption)
Why this command: An EXIT trap runs on every possible way the script can end, guaranteeing cleanup even when the script crashes or is killed midway through.
3
The situation: Your deploy script is always called like "./deploy.sh -e production -v" and needs to actually parse those real flags.
What would you run?
while getopts "e:v" opt; do
case $opt in
e) env="$OPTARG";;
v) verbose=true;;
esac
done
env=production, verbose=true
Why this command: getopts is built specifically for parsing real -flag style arguments, instead of hoping $1 and $2 always show up in the exact right order.
4
The situation: A deploy script needs to wait until a freshly started app is actually responding before it declares the deploy successful.
What would you run?
until curl -sf http://localhost:3000/health; do
sleep 2
done
Waiting...
Waiting...
(loop exits the moment curl succeeds)
Why this command: "until" keeps polling until the health check actually succeeds — far more reliable than a fixed sleep that guesses how long startup will take.
5
The situation: A script kicks off three independent tasks that could run at the same time, and needs to wait for all three before continuing.
What would you run?
./task1.sh &
./task2.sh &
./task3.sh &
wait
echo "All three finished"
All three finished
Why this command: Backgrounding all three with "&" lets them run in parallel, and "wait" with no argument pauses until every backgrounded job has completed.
6
The situation: You need to watch a long deploy script's output live in the terminal, but also keep a saved copy of the full log afterward.
What would you run?
./deploy.sh | tee deploy.log
Deploying v2.0...
Deploy finished
# shown live AND saved to deploy.log
Why this command: tee splits the output two ways at once — to your screen for live viewing and to a file for a permanent record — instead of forcing a choice between the two.
7
The situation: A script isn't behaving as expected, and you need to see exactly what it's actually executing, line by line.
What would you run?
set -x
# rest of the script runs as normal below this line
+ count=3
+ echo 3
Why this command: Debug tracing prints every command as it actually runs, with variables already expanded — far faster than sprinkling echo statements everywhere to guess what's happening.
8
The situation: A Docker entrypoint script starts the real app as its last step, and needs signals like SIGTERM to reach that app directly.
What would you run?
exec node server.js
(node server.js replaces the script's own process — signals now reach it directly)
Why this command: Without exec, the app runs as a child process and a "docker stop" signal can get stuck waiting on the wrapper script instead of reaching the app that needs to actually handle it.
