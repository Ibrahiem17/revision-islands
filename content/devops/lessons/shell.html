SSH — Complete Foundation
1. First: What is SSH?
SSH = Secure Shell
It lets you securely connect from your computer → another computer/server over a network.
Your computer 💻 │ │ SSH 🔐 ↓ Remote Linux server 🖥️
Once connected, you can use your terminal to control the remote server.
2. Why do we need SSH?
Suppose your company's server is in an AWS data center:
Your laptop 🇵🇰 │ │ Internet ↓ AWS data center 🌍 │ ↓ Linux server 🖥️
You can't physically sit beside the server.
SSH lets you work on it remotely.
For example:
systemctl status nginx
This checks Nginx on the server, not your laptop.
3. What information do we need?
To SSH into a server, you generally need:
Username
Server IP address
Authentication method
For example:
Username: ubuntu IP: 203.0.113.25 Key: my-server.pem
These are template/example values, not a real server.
4. The basic SSH command
The basic form is:
ssh <username>@<server-ip>
Example:
ssh ubuntu@203.0.113.25
Read it as:
"Connect to the server at 203.0.113.25 as user ubuntu."
Breakdown:
ssh ↓ SSH program ubuntu ↓ username @ ↓ at 203.0.113.25 ↓ server's IP address
5. What is the IP address?
Every machine on a network can have an IP address used to identify it.
For example:
203.0.113.25
Think of it like a computer's address.
House address ↓ 123 Main Street Computer address ↓ 203.0.113.25
So:
ssh ubuntu@203.0.113.25
means:
"Connect to the computer at this address using the ubuntu account."
6. What is the username?
The server has Linux users.
For example:
root
ubuntu
admin
devops
You must tell SSH which user you want to log in as.
For example:
ssh ubuntu@203.0.113.25
You're saying:
User → ubuntu
Server → 203.0.113.25
7. What happens after you run it?
You type:
ssh ubuntu@203.0.113.25
SSH contacts the server.
You might see:
The authenticity of host '203.0.113.25' can't be established. Are you sure you want to continue connecting (yes/no)?
You type:
yes
Then SSH authenticates you.
If successful, you'll eventually see something like:
ubuntu@server:~$
🎉 You're now inside the remote server.
8. How do you know you're inside?
Look at your prompt.
Before SSH:
ibrahiem@laptop:~$
After SSH:
ubuntu@server:~$
The prompt tells you which machine you're currently using.
Now:
pwd
might output:
/home/ubuntu
That's the server's filesystem.
9. What happens to your commands?
Suppose you type:
ls
Before SSH:
Your laptop ↓ ls ↓ your laptop's files
After SSH:
Remote server ↓ ls ↓ server's files
Same terminal.
Different computer.
That's the key idea.
10. SSH with an SSH key
For servers such as AWS EC2, you commonly authenticate using an SSH key pair instead of typing a normal password.
You might have:
my-server.pem
The command becomes:
ssh -i my-server.pem ubuntu@203.0.113.25
Breakdown:
ssh ↓ SSH -i ↓ identity/private-key file my-server.pem ↓ your private key ubuntu ↓ username @ ↓ at 203.0.113.25 ↓ server
So:
ssh -i my-server.pem ubuntu@203.0.113.25
means:
"Connect to this server as ubuntu, using my-server.pem as my identity/private key."
11. What is .pem?
A .pem file can contain a private cryptographic key.
For example:
my-server.pem
Think of it like a very special key 🔑 that proves:
"I am authorized to log into this server."
⚠️ Very important

Your private key should be kept private.

Don't:
❌ upload it to GitHub
❌ send it to random people
❌ paste it into chat
12. Why does SSH use keys?
Instead of:
Username + password
you can use:
Private key 🔑 ↓ SSH ↓ Server
The server has the corresponding public key configured for that user.
Very roughly:
Your computer Private key 🔑 │ ↓ SSH │ ↓ Server Public key 🔓
The cryptography proves that you possess the correct private key without sending the private key itself to the server.
13. What is -i?
You saw:
ssh -i my-server.pem ubuntu@203.0.113.25
Here:
-i → identity file
It tells SSH:
"Use this key file to authenticate me."
🧠 Trick:

-i = Identity
14. What if SSH uses a different port?
SSH normally uses:
Port 22
So:
ssh ubuntu@203.0.113.25
normally connects to port 22.
But a server could use another port, for example:
2222
Then:
ssh -p 2222 ubuntu@203.0.113.25
-p = port
Think:
-p → Port
15. Complete SSH template
Basic:
ssh <username>@<server-ip>
With private key:
ssh -i <private-key> <username>@<server-ip>
With custom port:
ssh -p <port> <username>@<server-ip>
With both:
ssh -i <private-key> -p <port> <username>@<server-ip>
Example using template data:
ssh -i my-server.pem -p 2222 ubuntu@203.0.113.25
16. What if you have a domain instead of IP?
You can also use a hostname/domain:
ssh ubuntu@example.com
Instead of:
ssh ubuntu@203.0.113.25
The important thing is:
username @ destination
17. What happens when you are finished?
You're connected:
ubuntu@server:~$
Run:
exit
You'll see something like:
logout Connection to 203.0.113.25 closed.
Now you're back on your own computer.
Your laptop 💻 ↑ exit ↑ Remote server 🖥️

🔐 SSH Keys — Complete Foundation
1. First, what problem are we solving?
You want to connect to a remote Linux server:
ssh ubuntu@SERVER_IP
The server needs to answer:
"How do I know you're allowed to log in?"
There are two common approaches:
Password authentication OR SSH key authentication
We're learning the second one.
2. Who has what?
There are two computers:
YOUR COMPUTER 💻 SERVER 🖥️
You want:
YOUR COMPUTER ───────SSH──────→ SERVER
Your computer will have the private key.
The server will have the public key.
YOUR COMPUTER SERVER │ │ Private key 🔐 Public key 🔓
Private key stays with you.
3. First, create the keys
You run this on your computer:
ssh-keygen -t ed25519
What is ssh-keygen?
It's a Linux program that generates SSH keys.
What is -t?
-t means:
type
What is ed25519?
It's a type of cryptographic algorithm used for SSH keys.
You don't need to understand its mathematics right now.
So:
ssh-keygen -t ed25519
means:
"Create an SSH key pair using the Ed25519 key type."
4. What gets created?
ssh-keygen creates two files:
~/.ssh/ ├── id_ed25519 └── id_ed25519.pub
They are:
id_ed25519 ↓ PRIVATE KEY 🔐 id_ed25519.pub ↓ PUBLIC KEY 🔓
You didn't manually create these files.
ssh-keygen created them.
5. What do we do with the keys?
This is the most important part.
Private key
Keep it on:
YOUR COMPUTER ~/.ssh/id_ed25519
Never give it to the server or other people.
Public key
Put it on:
SERVER
The server stores it in:
~/.ssh/authorized_keys
So:
YOUR COMPUTER SERVER ──────────────────────────────────────── id_ed25519 🔐 authorized_keys └── your public key 🔓
6. How do we put the public key on the server?
A common command is:
ssh-copy-id -i ~/.ssh/id_ed25519.pub ubuntu@SERVER_IP
For example:
ssh-copy-id -i ~/.ssh/id_ed25519.pub ubuntu@203.0.113.25
This essentially says:
"Copy my public key to the server and add it to the list of keys allowed to log in."
The server ends up with:
/home/ubuntu/.ssh/authorized_keys
containing your public key.
7. Now we have this situation
YOUR COMPUTER SERVER │ │ │ │ │ id_ed25519 🔐 │ │ │ │ │ │ authorized_keys │ └── public key 🔓 │ │ └────────────────────────────────┘
Now the server knows:
"I will allow someone who can prove they have the private key corresponding to this public key."
8. Now we SSH
You run:
ssh ubuntu@203.0.113.25
SSH sees your private key:
~/.ssh/id_ed25519
The server has your public key:
~/.ssh/authorized_keys
SSH performs an authentication process to prove that your private key matches the public key the server trusts.
You don't manually send the private key to the server.
That's important.
9. If authentication succeeds
The server says:
✅ You're authorized.
You get a remote shell:
ubuntu@server:~$
Now:
ls
runs on the server, not your laptop.
10. What if you don't have the private key?
Suppose someone copies your public key:
public key 🔓
That's okay.
But if they don't have your private key:
private key 🔐
they can't authenticate using that key pair.
That's why the private key must be protected.
11. What does the whole flow look like?
Here's the complete picture:
YOUR COMPUTER 💻 │ │ ssh-keygen -t ed25519 │ ↓ Generate key pair / \ / \ ↓ ↓ id_ed25519 🔐 id_ed25519.pub 🔓 PRIVATE PUBLIC │ │ │ │ KEEP HERE │ │ │ │ ssh-copy-id │ │ │ ↓ │ SERVER 🖥️ │ │ │ ~/.ssh/authorized_keys │ │ │ PUBLIC KEY │ │ └─────── SSH ───────┘ │ ↓ Authentication │ ↓ ✅ Login
12. The commands in order
If you're actually setting it up, the conceptual sequence is:
Step 1 — Generate keys
ssh-keygen -t ed25519
Step 2 — Put public key on server
ssh-copy-id -i ~/.ssh/id_ed25519.pub ubuntu@SERVER_IP
Step 3 — Connect
ssh ubuntu@SERVER_IP
That's the basic flow.

ThingMeaning
sshConnect to a remote machine
ssh-keygenGenerate SSH keys
ed25519Type of SSH key algorithm
id_ed25519Your private key
id_ed25519.pubYour public key
authorized_keysServer's list of trusted public keys
ssh-copy-idCopies your public key to the server
Private keyKeep secret
Public keyCan be placed on the server
🧠 The one mental model you need
Think of it like a lock and key:
PUBLIC KEY 🔓 = lock
PRIVATE KEY 🔐 = your secret key
You put the lock on the server.
You keep the key with yourself.
When you SSH:
You 🔐 │ │ "I have the matching key." ↓ Server 🔓 │ ↓ ✅ Let me in
Don't worry about the cryptographic mathematics yet.
For DevOps, your foundation at this stage is simply:

Generate a key pair → keep the private key → put the public key on the server → SSH uses the pair to authenticate you.
🔑 SSH — Secure Shell
SSH lets you securely connect to remote Linux servers. Always use key-based authentication — never passwords in production.
# ── CONNECT ───────────────────────────────────
ssh user@server-ip                 # basic connect
ssh -i ~/.ssh/key.pem user@ip      # connect with specific key
ssh -p 2222 user@ip               # connect on non-default port

# ── KEY GENERATION ────────────────────────────
ssh-keygen -t ed25519 -C "email"    # generate SSH key pair
# creates ~/.ssh/id_ed25519 (private) + id_ed25519.pub (public)
ssh-copy-id user@server-ip          # copy public key to server's authorized_keys

# ── TUNNEL / PORT FORWARD ─────────────────────
ssh -L 5432:localhost:5432 user@ip  # local port forward (access remote DB locally)
ssh -N -D 8080 user@ip              # SOCKS proxy through SSH

🎭 Real Scenarios — Learn SSH by Solving the Problem First
Read the situation, think about what you'd actually run, then click ▶ Run to reveal the command and its real output.
1
The situation: A brand-new server rejects your connection with "Permission denied (publickey)" — and you're not sure why.
What would you run?
ssh -vvv deploy@203.0.113.10
debug1: Authentications that can continue: publickey
debug1: No more authentication methods to try.
Permission denied (publickey).
Why this command: Maximum verbosity shows exactly which authentication methods the server offered and that every key you tried was rejected — the fix is adding your public key to that server's authorized_keys, not generating a new one blindly.
2
The situation: A server you rebuilt yesterday now makes SSH refuse to connect with a "REMOTE HOST IDENTIFICATION HAS CHANGED!" warning.
What would you run?
ssh-keygen -R 203.0.113.10
# Host 203.0.113.10 found: line 4
/home/user/.ssh/known_hosts updated.
Why this command: The rebuild genuinely changed the server's host key, so the old fingerprint needs to be removed from known_hosts before reconnecting — always confirm the rebuild was legitimate first, never bypass this warning blindly.
3
The situation: You need to inspect a database from your own local DB client, but it only accepts connections from inside a private network.
What would you run?
ssh -L 5432:localhost:5432 deploy@bastion.example.com
Welcome to Ubuntu 22.04 LTS
# tunnel active — connect your local DB client to localhost:5432
Why this command: Local port forwarding tunnels the private-network-only database port to your own machine through the one server that can already reach it — no need to ever expose the database publicly.
4
The situation: You're about to kick off a 2-hour migration script over SSH, and you know your connection might drop before it's done.
What would you run?
tmux new -s migrate
(opens a persistent session — run the migration inside it, then detach with Ctrl+B D)
Why this command: tmux keeps the migration running on the server itself, completely independent of your own SSH connection — if it drops, you just reconnect and run "tmux attach -t migrate" to pick up exactly where you left off.
5
The situation: A brand-new production server just finished booting and needs to be locked down before anything else touches it.
What would you run?
sudo sed -i 's/PermitRootLogin yes/PermitRootLogin no/; s/PasswordAuthentication yes/PasswordAuthentication no/' /etc/ssh/sshd_config && sudo systemctl restart sshd
(no output — root login and password login are now both blocked)
Why this command: Disabling root login and password authentication closes off the two most common, most automated attack paths immediately — and the restart is what makes sshd actually pick up the new config.
6
The situation: You suspect a server is under a brute-force SSH attack and want to confirm your automated defenses are actually working.
What would you run?
sudo fail2ban-client status sshd
Currently failed: 3   Total failed: 214
Currently banned: 2   IP list: 198.51.100.7 203.0.113.44
Why this command: Seeing banned IPs here confirms fail2ban is actively catching and blocking the repeated failed attempts — exactly what it's supposed to do, not a sign anything is broken.
7
The situation: You're re-deploying the same mostly-unchanged frontend build folder to a server for the tenth time this week.
What would you run?
rsync -avz -e ssh ./dist/ deploy@203.0.113.10:/var/www/app/
sending incremental file list
dist/app.js
sent 41,204 bytes received 128 bytes 16,532.80 bytes/sec
Why this command: rsync only transfers files that actually changed since the last sync — for a mostly-unchanged folder deployed repeatedly, that's dramatically faster than scp re-uploading everything from scratch every single time.
8
The situation: You just added a brand-new SSH key to GitHub and want to be sure it actually works before you risk a real push.
What would you run?
ssh -T git@github.com
Hi ibrahiem17! You've successfully authenticated, but GitHub does not provide shell access.
Why this command: This performs a real handshake against GitHub using your key, without touching any actual repository — it isolates whether the key setup itself works before you risk a real git push on top of it.
