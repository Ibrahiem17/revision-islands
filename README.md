# Interview Islands

A static revision site (vanilla JS) for interview prep: a home "islands" map plus five topic pages (DSA, OOP, System Design, Database, DevOps) and a DevOps terminal-combat game. Built with Vite as a multi-page app and deployed on Vercel. It works fully offline-capable and with no backend: progress lives in `localStorage`. An optional, off-by-default Supabase backend can sync progress across devices (see "Cloud sync").

## Commands
- `npm install` - install dependencies
- `npm run dev` - dev server (source files served as-is; `predev` regenerates the manifest)
- `npm run build` - production build into `dist/` (`prebuild` regenerates `content/manifest.json`)
- `npm run preview` - serve `dist/` locally, closest to Vercel

## Structure
```
index.html                     home page
topics/{dsa,oop,system-design,database,devops}.html   topic pages (URLs unchanged)
topics/*.css, css/*.css        plain stylesheets (kept as <link> tags, cascade preserved)
content/
  <topic>/index.js             topic data: export default { title, icon, sections }
  devops/lessons/NAME.html     lazily fetched DevOps lesson panels (+ NAME.js / NAME.post.js)
  manifest.json                GENERATED by scripts/build-manifest.mjs - do not edit
  README.md                    content format reference
src/
  shared/                      progress.js, cloud.js, render.js, mascot.js, text.js, topic-page.js
  topics/<topic>.js            page entry: dynamic-imports only that topic's content
  home/                        home.js (island badges), scene-fx.js
  games/devops-combat/         lazy game chunk (loader.js, main.js, data/, dialogue/, sprites/)
js/devops-tabs.js              DevOps page core: lesson loader, tabs, quiz engine
scripts/build-manifest.mjs     builds content/manifest.json
api/                           Vercel serverless functions (health.js, progress.js, _lib/supabase.js)
supabase/schema.sql            progress table + row-level security
vite.config.js                 page inputs + classic-assets plugin
vercel.json                    cache headers
.env.example                   env var names (no values)
```

## Adding a topic
1. Create `content/<dir>/index.js` (`export default { title, icon, sections }`; format in `content/README.md`).
2. Create the page `topics/<dir>.html` (copy an existing one such as `oop.html`; it needs `#content`, `#search`, `#progress-fill`, `#progress-text`).
3. Create the entry `src/topics/<dir>.js`:
   `import { mountTopic } from "../shared/topic-page.js"; mountTopic("<key>", () => import("../../content/<dir>/index.js"));`
4. Add the page to `build.rollupOptions.input` in `vite.config.js`.
5. If the localStorage key differs from the folder name, add it to `KEYS` in `scripts/build-manifest.mjs` (e.g. `system-design` -> `systemDesign`), and use the same key in step 3.
6. Run `npm run build`; the manifest (used by the home page for progress badges) regenerates automatically. Add a link/island for it on `index.html` if desired.

## Adding a note with a diagram (System Design page)
1. In `content/system-design/index.js` give the note `diagram: "<key>"` (and optionally `diagramCaption: "..."`, which is searchable).
2. In `src/topics/system-design-diagrams.js` register `<key>: () => "<markup>"` (see `scalingSessions`). `src/topics/system-design.js` passes the registry to `mountTopic` as `{ collapsibleNotes: true, diagrams }`; `src/shared/render.js` renders it as `<figure class="note-diagram">` only when that registry has the key, so other topics are unaffected.
3. Draw in the ink style: inline SVG, `role="img"` + `<title>`/`<desc>`, thick black round-join strokes (`class="nd-k"`), flat fills, paper `#f8f4e8`/`#f0ebdd`, ink `#141210`, and mustard `#F2B01E` as the only accent (use the page CSS variables, never new colours). No faces. Show good/bad with hatching, stamps and ticks. Keep the viewBox ~300 units wide with text >= 12 units so it stays legible on a 340px phone (panels sit side by side on desktop, stack on phones).
4. Animate with CSS keyframes scoped to `.note-diagram.is-playing` (render.js adds it only while the figure is on screen, the tab is visible and motion is allowed). With the class absent the SVG must already be a complete static picture.
5. Frame, `FIG. n` tab and caption strip are styled in `topics/system-design.css` (`.note-diagram`); SVG part classes (`nd-*`) live there too.

## DSA page theme (riso / screen-print)
- `topics/dsa.html` + `topics/dsa.css` (palette tokens at the top; notes-engine restyle: floors = `.section`, `.note-block`, qa, code, tables, `.note-diagram`, mascot) + `src/topics/dsa.js` (`mountTopic(..., { collapsibleNotes: true })`).
- `src/topics/dsa-art.js`: the hero cutaway as four stacked inline SVG layers (back / shell / rooms / front). Colours come from CSS classes (`.m .t .pk ...`), one ink weight (`.k`), halftone `<pattern>`s (`.h-i .h-f .h-t .h-w .h-l`). Every character/object is a `<g id>`; `.asm` groups are slid in on load, idle motion lives on inner `.i-*` groups.
- `src/topics/dsa-fx.js`: injects the hero, GSAP assembly (CSS fallback `asm-css` without GSAP), idle loops gated by `.is-live` (IntersectionObserver + tab visibility), fine-pointer parallax, CTA scroll. `body.rm` / `prefers-reduced-motion` => static picture.

## Adding a DevOps lesson
1. In `topics/devops.html` add the tab button (`<div class="tab" onclick="showTab('NAME',this)">`) and an empty panel wrapper `<div class="panel" id="tab-NAME"><div class="lesson-status" role="status">Loading…</div></div>`.
2. Create `content/devops/lessons/NAME.html` with the panel's inner HTML. Inline `onclick` handlers and `<script>` tags work. CSS is page-wide, so put `<style>` in `topics/devops.html`, not in the fragment.
3. Optional: `NAME.js` / `NAME.post.js` beside it for lesson JS (classic scripts, run right after the HTML is inserted). Shared helpers belong in `js/devops-tabs.js`.
4. Done: the build finds every `*.html` in the folder, emits it as `assets/lesson-NAME-<hash>.txt` and injects the name->URL map as `window.DEVOPS_LESSONS`. `npm run dev` serves fragments raw.

## The game (`src/games/devops-combat/`)
- `loader.js` shows the loading box, applies `css/devops-game.css`, dynamic-imports `main.js` (also prefetched at idle) and offers Retry on failure.
- `main.js` holds all game logic in `startDevopsGame()` (combat, city loop, interiors, dialogue, UI, sound, save). Its header comment lists every module and searchable section marker. Nothing runs until the loader calls it.
- `data/` is static data: `bosses/<id>.js` (metadata + question bank), `bosses/index.js` (the `BOSSES` table), `rapid-recon.js`, `library-packs.js`, `npc-roster.js`, `house-homes.js`, `tower-*.js`. `dialogue/` holds NPC and roof lines. `sprites/` holds base64 art tables (kept as data URIs on purpose so they render synchronously).
- Save data is `localStorage['dgc_save_v1']` (sound prefs in `dgc_sound_v1`).

**Add a boss:** copy an existing `data/bosses/<id>.js` (e.g. `pager.js`), change its metadata and questions, import it in `data/bosses/index.js` and add it to `BOSSES` (key order matters: boss select and progression iterate it). Check `main.js` for anything keyed by boss id (search a current boss id such as `pager`) and add matching art/dialogue if needed. **Add questions/data:** edit the relevant file under `data/` (or `rapid-recon.js` for the mixed pool).

## Caching model
Vite bundles the ES modules into hashed chunks. Classic (non-module) scripts and local stylesheets are not bundled by Vite, so the `classic-assets` plugin in `vite.config.js` copies each verbatim to `dist/assets/<name>-<content-hash>.<ext>` and rewrites the HTML (same for lesson fragments, emitted as `.txt`). Every `/assets/*` file is therefore immutable, and a change always gets a new URL. `vercel.json` serves `/assets/*` as `public, max-age=31536000, immutable` and HTML (and `/`) as `max-age=0, must-revalidate`. `/api/*` functions are untouched by those rules and respond with `Cache-Control: no-store`.

## Cloud sync (optional, OFF by default)
With no env vars the site makes no network calls beyond loading its own files, and `cloud.js` is not even part of the bundle. What exists: `api/progress.js` (GET/PUT one JSON row per user, Bearer Supabase JWT validated server-side, 1 MB limit, 501 when unconfigured), `api/health.js`, `supabase/schema.sql` (table + RLS so users only touch their own row) and `src/shared/cloud.js` (debounced push on `onProgressChange`, pull + merge on start, last-write-wins by `updatedAt`; learned ids are unioned, the game save is replaced only if the remote copy is newer). There is **no login UI yet**, so even when enabled nothing syncs until a session is stored via `setSession({ access_token })`.

Enable it:
1. Create a project at supabase.com. Enable an auth provider (e.g. email) under Authentication.
2. In the SQL editor run `supabase/schema.sql`.
3. From Project Settings > API copy the project URL and the anon (public) key.
4. In Vercel > Project > Settings > Environment Variables set: `SUPABASE_URL`, `SUPABASE_ANON_KEY` (used by `api/*`), and `VITE_CLOUD_SYNC=true`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (baked in at build time; the anon key is public by design; never use the service_role key).
5. Redeploy (the `VITE_*` values are read at build time). Check `/api/health` returns `{ok:true}`; `/api/progress` returns 401 without a token.
6. For local work copy `.env.example` to `.env.local` (git-ignored) and use `vercel dev` to run the `api/` functions (`vite dev` does not serve them).

## Deployment
Vercel: framework "Other", build command `npm run build`, output directory `dist` (all in `vercel.json`). Files in `api/` deploy automatically as functions on the default Node runtime (`api/_lib` is not exposed as a route). Never commit `.env*` (only `.env.example`).

## Growing the site
- Login UI (email/magic link via Supabase JS or its auth REST endpoints) that calls `cloud.js` `setSession()`, plus a sync status indicator.
- Per-topic search across all content, and a global search on the home page.
- More topics/bosses via the recipes above.
- If the site outgrows vanilla modules, Astro (content-first, keeps the same `content/` data) or React islands for interactive parts can be adopted incrementally.
